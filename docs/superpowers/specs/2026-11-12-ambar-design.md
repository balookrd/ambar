# ambar: реплицируемые тома PVC для k3s поверх DRBD 9

Спека описывает CSI-драйвер `ambar`: что он делает, из чего состоит и как ведёт
себя при отказах узлов. Документ адресован тому, кто будет писать план
реализации и код. Дата: 2026-11-12.

## Окружение и требования

| Что | Значение |
|---|---|
| Кластер | k3s, сейчас три узла `k3s-1..3`, все три — server с etcd |
| Железо узла | NanoPi R5C: RK3568B2, 4 ГБ RAM, NVMe 128 ГБ |
| ОС и ядро | Debian 13 trixie, штатное ядро `6.12.116+deb13-arm64` |
| NVMe | один раздел ext4 `LABEL=k3s-data`, смонтирован в `/var/lib/rancher` |
| Сеть репликации | интерконнект `lan0`, 2.5GbE; адреса в документе взяты из диапазона для документации `192.0.2.0/24` (RFC 5737): `192.0.2.51–53/24` |
| Существующие StorageClass | `local-path` (том привязан к узлу), `nfs-client` (NAS, адрес `<nas_host>` в документе не приводится) |

Требования владельца:

- Число копий тома задаёт параметр `replicas: N`, N не меньше 2: N копий лежат на N узлах.
- В исправном состоянии запись подтверждается приложению после того, как она
  легла на диски всех N узлов с копией (`protocol: C`). После отказа k узлов с
  копией остаётся N−k копий; при `replicas: 2` после отказа одного такого узла
  запись идёт на один диск (`2026-11-12-drbd9-spike-results.md`, шаг 8 и
  опыт E2). Исключение — `protocol: A`, см. «Принятые решения».
- В каждый момент том монтирует один узел. Тома с одновременной записью с
  нескольких узлов не нужны.
- Под с томом может запуститься на любом узле кластера: узлы без копии
  подключаются к ресурсу без диска.
- Потребление памяти и CPU ниже, чем у Longhorn 1.12.2 на этих же узлах
  (замер 2026-11-09: поды 145–348 МиБ на узел, `fsync` 4 КиБ 13.6 мс).

## Принятые решения

| Решение | Причина |
|---|---|
| Репликацию выполняет модуль ядра DRBD 9 | Запись не проходит через userspace; у ресурса до трёх и более сторон и встроенный кворум |
| Данные тома — разреженный файл на NVMe, подключённый как loop-устройство | NVMe занят одним ext4; переразметка требует остановки k3s на каждом узле |
| Модуль DRBD 9 собирается заранее и поставляется в образе агента | На узлах нет компилятора; `boot.scr` переписывается на последнее ядро без фолбэка, сборка на узле в момент обновления недопустима |
| Состояние томов хранится в CRD | Своей базы нет; etcd уже есть |
| Проект переименован: `duovol`, затем `sklad`, сейчас `ambar` (2026-11-12) | Первое название означало «том на двух узлах» и не подходит при `replicas: N`. В старых заметках, коммитах и образах `duovol-drbd` и `sklad-drbd` речь о том же проекте |
| Отдельный репозиторий | Драйвер не связан с wire-протоколом `outline-proxy` и его vendored-крейтами |
| `replicas: N` — целое число не меньше 2: N копий лежат на N узлах, все остальные узлы кластера подключены к ресурсу без диска. Часть «все остальные узлы подключены» заменена решением 2026-11-13 о подключении по требованию (ниже) | Решение владельца 2026-11-12: под запускается на любом узле. Сторона без диска в роли `Primary` писала при `replicas: 2` на трёх узлах и сохранила уже имевшийся кворум, когда узел с копией пропал (шаг 8, опыт E2); заново запущенной устаревшей копии кворум она не дала (опыт C1, два прогона) `[проверить: tiebreaker сохраняет уже имевшийся кворум, но не даёт его заново запущенному узлу — предположение]`. `replicas: 3` без стороны без диска — шаг 4. Другие сочетания на стенде не запускались |
| `protocol: A` остаётся параметром StorageClass как исключение из требования о записи на диски узлов с копией | Решение владельца 2026-11-12. При `protocol: A` запись, подтверждённая приложению, но не покинувшая сетевой буфер, теряется при отказе узла. [проверить: `protocol: A` на стенде не запускался] |
| Том при потере кворума освобождает агент `ambar`: по истечении grace period (30 с) он удаляет поды с этим томом на своём узле; пока узел не видит другие узлы по сети репликации, на узле стоит taint `NoSchedule` | Решение владельца 2026-11-12. На стенде изоляция закрывала только TCP 7000, kubelet и API оставались доступны; после `EIO` точка монтирования остаётся, узел остаётся `Primary`, `umount` вручную проходит и узел уходит в `Secondary` (шаг 6, опыт E1). Узел, оставшийся `Primary` к возврату сети, переходит в `StandAlone`, если другой узел писал на том (шаг 7, опыты E1 и C2); если не писал, связи восстановились сами (опыт C2, прогон 1) |
| Агент каждого узла выполняет `drbdadm adjust` для ресурса с соединением в `StandAlone`, пока локальная роль — `Secondary`, ограниченное число попыток | Решение владельца 2026-11-12. `adjust` снимал `StandAlone` без отбрасывания данных, `Split-Brain detected` в `dmesg` не было (шаг 7, опыт E1); понадобился на обеих сторонах связи, `adjust` только на вернувшемся узле не хватило. `adjust` при роли `Primary` и смонтированном томе связь не снял: она снова ушла в `StandAlone` (опыт C2, прогон 2, один прогон) |
| `replicas` не меньше 2: при создании тома `replicas: 1` отклоняется | Решение владельца 2026-11-12 (вторая серия). Кворум при одной копии и узлах без диска на стенде не запускался; число непроверенных сочетаний сокращено. Тома без репликации остаются на `local-path` |
| Grace period без кворума — 30 с, значение по умолчанию настраиваемого параметра агента | Решение владельца. На стенде после изоляции узла писатель получил ошибку через 10–11 с (шаг 6, опыт E1); пауза записи без потери кворума длилась 4.6–5.6 с (шаг 8, опыт E2), 11.3 с и ~6 с (опыт C1, `replicas: 2`) |
| Узел помечается taint `ambar.balookrd.github.io/no-quorum` с эффектом `NoSchedule`. Агент ставит его на свой узел, пока узел не видит другие узлы по сети репликации, и снимает после восстановления связи | Решение владельца. Запущенные поды остаются на узле; новые поды на узел не планируются, в том числе поды без томов `ambar`; манифесты сервисов менять не нужно |
| Если с изолированного узла недоступен API server, агент ждёт его возврата и ничего не делает с подом и монтированием | Решение владельца. Остальные узлы видят узел как `NotReady`, Kubernetes создаёт замену пода по истечении `tolerationSeconds`, узел с кворумом открывает том (шаг 6: `dv-2` смонтировал том, пока `dv-1` был изолирован). После возврата связи агент освобождает том и переподключает ресурс |
| `drbdadm primary --force` выполняет только человек вручную; агент его не вызывает | Решение владельца. Устаревшая копия после перезапуска показывает свой диск как `UpToDate` (опыт C1), поэтому состояние диска не говорит, актуальны ли данные. Процедура и предупреждение: «Принудительное повышение вручную» |
| Файл тома разреженный, предел суммы размеров — `capacityBytes` | Решение владельца. Файлы на стенде создавались разреженными (`truncate -s`, `stand/spike/res.sh`). Поведение DRBD при заполнении раздела проверяется на стенде в плане реализации [проверить: поведение DRBD и ext4 при `ENOSPC` в файле тома] |
| Узел, добавленный в кластер после создания томов, автоматически подключается без диска ко всем существующим томам; каждый том создаётся с запасом места в метаданных DRBD под будущие узлы. Автоматическое подключение ко всем томам заменено решением 2026-11-13 о подключении по требованию (ниже); запас в метаданных остаётся | Решение владельца: под должен запускаться на новом узле. Битовая карта занимает 32 КиБ на 1 ГиБ тома на одну сторону (шаг 4: 64 КиБ при двух остальных сторонах с копией; шаг 8: 32 КиБ при одной). Сторона без диска, добавленная внутри запаса к работающему ресурсу из двух копий (`adjust` на двух узлах, `up` на новом), подключилась (`Connected`) и сообщила `size` 1048316 КиБ; опыт P5, один прогон, результаты, раздел «Опыты перед агентом (P1–P6)». Добавление стороны сверх запаса не запускалось. Размер запаса: «Открытые вопросы» |
| Split-brain определяется по отказу `adjust`: агент не читает журнал ядра | Решение владельца. Если соединение остаётся `StandAlone` после нескольких попыток `adjust`, пока том освобождён (локальная роль `Secondary`), агент выставляет метрику «нужна ручная проверка» и прекращает попытки; причину человек ищет в `dmesg`. `drbdsetup status --json` не отличает split-brain от `StandAlone` в E1 (опыт C3) |
| Отметку «том новый, начальная синхронизация не пропущена» хранит объект `ReplicatedVolume`: контроллер ставит её при создании тома и снимает после пропуска. Маркеры на узле остаются второй проверкой | Решение владельца 2026-11-13. С одними маркерами потеря каталога томов на всех узлах с копией приводит к пустому тому на месте прежнего (раздел «Чего агент фазы 1 не делает»). Имя и место поля определяет план фазы 2а |
| Узел без копии подключается к тому по требованию: когда на него назначен под с этим томом, и отключается после ухода пода | Решение владельца 2026-11-13, заменяет постоянное подключение всех узлов. Под по-прежнему запускается на любом узле. Число соединений DRBD растёт с числом томов в работе, а не с произведением числа томов на число узлов. Добавление стороны к работающему ресурсу: опыт P5 (один прогон). Отключение стороны от работающего ресурса на стенде не запускалось `[проверить: adjust после удаления стороны из файла ресурса при роли Primary на другом узле]` |
| При чётном числе копий контроллер назначает тому одного постоянного свидетеля: узел без диска, подключённый всё время жизни тома. При нечётном числе копий свидетеля нет | Решение владельца 2026-11-13. Без свидетеля том с `replicas: 2` при отказе одного из двух узлов теряет кворум (`quorum majority`), запись возвращает ошибку. Сторона без диска сохранила имевшийся кворум при отказе узла с копией (шаг 8, опыт E2). Чётные N больше 2 на стенде не запускались |
| Набор узлов с копией у существующего тома можно менять: добавить копию, удалить копию, перенести копию на другой узел | Решение владельца 2026-11-13. Реализуется отдельным планом фазы 2б после того, как драйвер фазы 2а создаёт, монтирует и удаляет тома; до 2б API отклоняет изменение набора копий. Удаление копии уничтожает данные на узле и требует, чтобы остальные копии были `UpToDate`. Смена роли стороны на стенде запускалась только в направлении diskful → diskless (`client: true`); обратное направление агент фазы 1 отклоняет |
| Перед `create-md --force` агент проверяет файл тома командой `drbdadm dump-md`: если метаданные DRBD в файле уже есть, агент возвращает ошибку и ничего не создаёт | Решение владельца 2026-11-13. Закрывает случай потерянного маркера `.img.ready` у файла с данными без маркера `.img.synced`. `[проверить: вывод и код возврата dump-md на пустом файле и на файле с метаданными; опыт на стенде до кода]` |
| Фаза 2 разделена на два плана: 2а (CRD, контроллер, CSI, манифесты; набор копий неизменяем) и 2б (смена набора копий) | Решение владельца 2026-11-13. Работающий PVC появляется по завершении 2а |

Отвергнутые варианты:

- Longhorn: потребление по замеру выше допустимого.
- Свой движок репликации в userspace (ublk, NBD): повторяет Longhorn, путь
  записи идёт через процесс.
- DRBD 8.4 из штатного ядра с арбитром через Lease: у ресурса две стороны, под
  работает только на двух узлах из трёх.
- Асинхронная репликация снапшотами: изолированный узел продолжает подтверждать
  записи, которые после его возврата выбрасываются.

## Проверенные факты

- Конфиг штатного ядра Debian (`config-6.12.85+deb13-arm64` из образа
  `rk3568-nanopi-r5c_trixie-13.4.img.xz`): `CONFIG_BLK_DEV_DRBD=m` (версия 8.4),
  `CONFIG_MODULE_SIG=y`, `CONFIG_MODULE_SIG_FORCE` не задан (неподписанный
  модуль загружается).
- DRBD 9.3.4 (тег `drbd-9.3.4`, `github.com/LINBIT/drbd`) собирается под
  `linux-headers-6.12.116+deb13-arm64` в контейнере `debian:trixie` arm64 за
  30 с без предупреждений. Результат: `drbd.ko`, `drbd_transport_tcp.ko`;
  `vermagic: 6.12.116+deb13-arm64 SMP mod_unload modversions aarch64`;
  `depends: lru_cache,libcrc32c`.

Команда сборки:

```bash
apt-get install -y --no-install-recommends git ca-certificates build-essential \
  kmod coccinelle python3 linux-headers-6.12.116+deb13-arm64
git clone --depth 1 --branch drbd-9.3.4 --recursive --shallow-submodules \
  https://github.com/LINBIT/drbd /src
make -j4 -C /src/drbd KDIR=/lib/modules/6.12.116+deb13-arm64/build SPAAS=false
```

`SPAAS=false` запрещает сборке обращаться к сервису LINBIT за патчем
совместимости; патч генерирует локальный `coccinelle`.

На стенде с ядром `6.12.116+deb13-arm64` модуль загружается
(`2026-11-12-drbd9-spike-results.md`, допущение 1); на R5C загрузка не проверена.

## Компоненты

### Агент `ambar`

Один бинарь на Rust. Работает как DaemonSet на каждом узле кластера (сейчас три): привилегированный
контейнер, `hostNetwork: true`, `hostPID` не нужен. В одном процессе:

| Часть | Что делает |
|---|---|
| Загрузчик модуля | При старте загружает DRBD 9 из образа, см. «Загрузка модуля» |
| CSI Identity, Controller, Node | gRPC на unix-сокете `/var/lib/kubelet/plugins/ambar/csi.sock` |
| Согласование | Следит за объектами `ReplicatedVolume` и приводит файл, loop-устройство и ресурс DRBD на своём узле к описанному состоянию |
| Статус и метрики | Читает `drbdsetup status --json`, пишет статус в CR, отдаёт метрики Prometheus |
| Освобождение тома | Если у смонтированного тома нет кворума дольше grace period (по умолчанию 30 с), удаляет поды с этим томом на своём узле; ставит и снимает taint `ambar.balookrd.github.io/no-quorum`, см. «Освобождение тома при потере кворума» |
| Переподключение | Выполняет `drbdadm adjust` для ресурса с соединением в `StandAlone`, пока локальная роль — `Secondary`, ограниченное число попыток; после них выставляет метрику «нужна ручная проверка», см. «StandAlone и split-brain» |

### Параметры агента

| Параметр | По умолчанию | Что делает |
|---|---|---|
| Grace period без кворума | 30 с | Время без кворума у смонтированного тома, после которого агент удаляет поды с этим томом на своём узле |
| Число попыток `adjust` | не определено, см. «Открытые вопросы» | После этого числа неудачных попыток агент прекращает `adjust` для ресурса и выставляет метрику «нужна ручная проверка» |
| Интервал между попытками `adjust` | не определено, см. «Открытые вопросы» | Пауза между попытками |

Имена параметров в конфигурации агента в спеке не заданы.

### Права агента (RBAC)

Манифесты RBAC лежат в `deploy/`. Для освобождения тома сервисному аккаунту
агента нужны права:

| Ресурс | Права | Зачем |
|---|---|---|
| `pods` | `delete`; чтение, чтобы найти поды, которые используют том на узле | Удалить поды при потере кворума |
| `nodes` | `get`, `patch` | Поставить и снять taint `ambar.balookrd.github.io/no-quorum` на своём узле (поле `spec.taints`) |

CSI Controller отвечает на каждом узле, но запросы получает только от
`external-provisioner`, у которого включён выбор лидера.

### Сайдкары

Штатные образы Kubernetes CSI:

- `node-driver-registrar` — в каждом поде DaemonSet, регистрирует драйвер в kubelet;
- `external-provisioner` — в каждом поде DaemonSet с `--leader-election`,
  активен один.

`external-attacher` не используется: объект `CSIDriver` объявляет
`attachRequired: false`. Без `VolumeAttachment` Kubernetes не ждёт 6 минут
перед принудительным отсоединением тома от недоступного узла.

### Утилиты DRBD

`drbdadm`, `drbdsetup`, `drbdmeta` собираются из исходников `drbd-utils` и
кладутся в образ агента. На хост утилиты не ставятся. Версия `drbd-utils`
выбирается совместимой с модулем 9.3.4; проверено с 9.35.0 (в Debian trixie
пакет 9.22.0).

Агент определяет результат команды `drbdadm`, повторно читая
`drbdsetup status --json`, а не по коду возврата. Что читается после каждой
команды:

| Команда | Что проверяется после неё |
|---|---|
| `drbdadm up` | ресурс присутствует в статусе |
| `drbdadm adjust` | код возврата равен нулю (ненулевой код — отказ, нулевой не доказывает успех), и статус совпадает с описанием: `node-id`, `minor` тома 0, набор соединений (имя и `peer-node-id`), диск (локальный не `Diskless` на узле с копией, `client` на узле без диска) |
| `drbdadm down` (в `ambar remove`) | ресурс отсутствует в статусе |
| `drbdadm create-md`, `drbdadm new-current-uuid` | статус не перечитывается; команда должна вернуть код 0, а результат подтверждает следующий `ambar apply`: после `create-md` есть маркер `.img.ready` и ресурс поднимается, после `new-current-uuid` статус показывает диск `UpToDate` и `apply` пишет маркер `.img.synced` |

Наблюдалось (`2026-11-12-drbd9-spike-results.md`, опыты C2 и C3, по одному
прогону): `drbdadm disconnect` вернул `rc=0`, когда ядро отказало (`Can not
disconnect a StandAlone device (-9)`); `drbdadm connect` вернул `rc=10` для
уже соединённой пары, хотя связь с `StandAlone`-пиром поднялась; `drbdadm
adjust` вернул `rc=0`, а соединение снова ушло в `StandAlone`.

### `ReplicatedVolume` (CRD, cluster-scoped, группа `ambar.balookrd.github.io/v1alpha1`)

```yaml
spec:
  sizeBytes: 2147483648
  protocol: C
  minor: 1000          # номер устройства: /dev/drbd1000
  port: 7000           # TCP-порт ресурса на lan0
  nodes:             # пример: replicas: 2 в кластере из трёх узлов
    - name: k3s-1
      nodeId: 0
      diskful: true
    - name: k3s-2
      nodeId: 1
      diskful: true
    - name: k3s-3
      nodeId: 2
      diskful: false
status:
  nodes:
    - name: k3s-1
      disk: UpToDate
      role: Primary
      connections: {k3s-2: Connected, k3s-3: Connected}
```

Решение 2026-11-13: в `spec.nodes` остаются узлы с копией, свидетель при чётном N и узлы с подом тома; абзац ниже описывает прежнюю схему и будет переписан планом фазы 2а.

В `spec.nodes` перечислены все узлы кластера: N узлов с `diskful: true`,
остальные с `diskful: false`.

`minor` и `port` выделяет CSI Controller при создании: наименьшее свободное
значение среди существующих объектов, начиная с 1000 и 7000. Имя объекта
совпадает с идентификатором тома CSI. На объекте стоит финализатор
`ambar.balookrd.github.io/cleanup`.

Описание тома, которое получает агент фазы 1 (`ambar apply --file`,
`src/model.rs`), кроме полей из примера содержит `nodes[].address` (адрес
стороны на `lan0`) и `maxPeers`; неизвестные поля агент отвергает. В примере
выше этих полей нет. Откуда они попадают в описание, не определено:
«Открытые вопросы».

Агент проверяет имена до любых действий на узле:

| Имя | Правило |
|---|---|
| Том (`name`) | 1–63 символа `a-z0-9-`, первый символ не `-`, не `all` (`drbdadm down all` действует на все ресурсы узла) |
| Узел (`nodes[].name`) | 1–63 символа `A-Za-z0-9._-`, первый символ — буква или цифра |

Имя узла в описании тома должно совпадать с выводом `uname -n` на этом узле:
агент читает имя из `/proc/sys/kernel/hostname`, а `drbdadm` выбирает секцию
`on <имя>` файла ресурса по нему.

Каталог `/etc/drbd.d` в контейнере агента (файлы `<том>.res` и
`<том>.res.applied`) должен быть постоянным путём хоста. Если файлы потеряны,
агент записывает их заново и выполняет `drbdadm adjust` для каждого настроенного
ресурса. Стенд подключает `/var/lib/rancher/ambar/res` (`stand/toolbox.yaml`).

### `ConfigMap ambar-nodes`

Карта узлов: имя узла Kubernetes, адрес на `lan0`, постоянный `nodeId` и бюджет
места под тома. Запись есть на каждый узел кластера; в примере кластер из трёх
узлов.

```yaml
nodes:
  - {name: k3s-1, address: 192.0.2.51, nodeId: 0, capacityBytes: 42949672960}
  - {name: k3s-2, address: 192.0.2.52, nodeId: 1, capacityBytes: 42949672960}
  - {name: k3s-3, address: 192.0.2.53, nodeId: 2, capacityBytes: 42949672960}
```

`address` из этой карты и `maxPeers` попадают в описание тома, которое читает
агент; источник обоих полей: «Открытые вопросы».

`capacityBytes` — предел суммы объявленных размеров томов с копией на узле.
Файлы томов разреженные, поэтому без предела сумма размеров может превысить
свободное место на NVMe, и тогда запись в том получит ошибку ввода-вывода
вместе с etcd и containerd на том же разделе.

## Загрузка модуля

Образ агента содержит модули по пути `/opt/ambar/modules/<версия ядра>/`:
`drbd.ko`, `drbd_transport_tcp.ko`. Под каждую версию ядра Debian, которая
стоит или будет стоять на узлах, в образе лежит свой каталог.

Порядок при старте агента:

1. Если существует `/sys/module/drbd`, прочитать `/sys/module/drbd/version`.
   Версия `9.*` — модуль drbd уже загружен: если нет
   `/sys/module/drbd_transport_tcp`, загрузить `drbd_transport_tcp.ko` из
   каталога под версию ядра (`insmod`; без файла — ошибка
   `no drbd_transport_tcp module for kernel <версия>`), затем перейти к шагу 5.
   Версия `8.*` —
   завершиться с ошибкой `in-tree drbd 8.4 is loaded`; тома на узле не
   обслуживаются.
2. Определить версию ядра (`uname -r`). Если каталога с модулем под неё нет,
   завершиться с ошибкой `no drbd module for kernel <версия>`.
3. Загрузить зависимости из дерева модулей хоста: `modprobe lru_cache`,
   `modprobe libcrc32c` (`/lib/modules` хоста смонтирован в контейнер только
   на чтение).
4. `insmod drbd.ko usermode_helper=disabled`, затем
   `insmod drbd_transport_tcp.ko`. `usermode_helper=disabled` отключает запуск
   `/sbin/drbdadm` ядром на хосте: обработчики событий драйвер не использует.
5. Продолжить запуск.

На каждом узле при установке создаётся файл
`/etc/modprobe.d/ambar-blacklist-drbd.conf`:

```text
blacklist drbd
install drbd /bin/false
```

Без него любой вызов `modprobe drbd` на узле загрузит штатный модуль версии
8.4. Метаданные томов версии 9 он не читает, а имя модуля то же, поэтому
модуль версии 9 после этого не загрузится до перезагрузки узла. [проверить:
не проверялось на стенде; файл на стенде создаёт `stand/k3s.sh`, `modprobe drbd`
не вызывался] Чёрный список хоста не действует на `modprobe` внутри
контейнера (`/etc/modprobe.d` в поде `toolbox` пуст), поэтому тот же файл
нужен в образе агента.

## Жизненный цикл тома

### Создание (`CreateVolume`)

1. Выбрать N узлов с копией данных: узел из `selected-node` (его передаёт
   планировщик) и N−1 узлов с наибольшим свободным бюджетом `capacityBytes`
   среди остальных. Все прочие узлы кластера становятся сторонами без диска.
   Если `replicas` меньше 2 или узлов в кластере меньше N, вернуть ошибку [проверить: код ошибки].
2. Проверить бюджет на выбранных узлах. При нехватке вернуть
   `RESOURCE_EXHAUSTED`.
3. Создать объект `ReplicatedVolume` с выделенными `minor` и `port`.
4. Дождаться, пока агенты всех узлов поднимут ресурс и диски копий перейдут в
   `UpToDate`. Срок ожидания — 60 с, затем `DEADLINE_EXCEEDED`; provisioner
   повторит вызов, операция идемпотентна по имени тома.

Что делает агент узла с копией данных, увидев новый объект:

1. Создать разреженный файл `/var/lib/rancher/ambar/volumes/<имя>.img`
   размером `sizeBytes` плюс место под внутренние метаданные DRBD. На стенде
   файл в 1 ГиБ при двух остальных сторонах с копией потерял на метаданных
   100 КиБ (`size` устройства 1048476 КиБ), при одной стороне с копией и одной
   без диска — 68 КиБ (1048508 КиБ); см. результаты, шаги 4 и 8. Метаданные создаются с запасом сторон под будущие узлы (`create-md --max-peers`, значение: «Открытые вопросы»); каждая сторона занимает 32 КиБ битовой карты на 1 ГиБ тома (шаги 4 и 8). С `create-md --max-peers=7` файл в 1 ГиБ даёт `size` устройства 1048316 КиБ (битовая карта 224 КиБ, 7 × 32 КиБ; опыт P2, один прогон, результаты, раздел «Опыты перед агентом (P1–P6)»). В опыте P5 узел без диска (`node-id` 2 при `--max-peers=7`), добавленный к работающему ресурсу из двух копий, после подключения сообщил `size` 1048316 КиБ, равный результату P2 (три стороны с диском); `size` на узлах с копией до добавления в P5 не записывался `[проверить: size на узлах с копией до и после добавления стороны]`. Формула для других размеров файла и значений `--max-peers` не проверялась `[проверить: другие размеры и значения]`.
2. Подключить файл как loop-устройство с прямым вводом-выводом
   (`losetup --direct-io=on`).
3. Сгенерировать из объекта файл ресурса `<имя>.res`. Если маркера
   `<имя>.img.ready` нет, выполнить `drbdadm create-md --force --max-peers=<maxPeers>`
   и записать маркер (раздел «Маркеры на узле»); для файла с маркером
   `create-md` не вызывается. Перед `create-md` агент проверяет файл командой
   `drbdadm dump-md`, если маркера `<имя>.img.creating` нет. Затем выполнить `drbdadm up <имя>`, если ресурса
   нет в ядре (создание тома, узел без диска, старт после перезагрузки узла), и
   `drbdadm adjust <имя>`, если ресурс в ядре настроен. На стенде ресурс поднимался командой `drbdadm up`
   (`stand/spike/res.sh`). `drbdadm adjust` на ресурсе, которого в ядре нет, поднимает его: `rc=0`, ресурс настроен и соединён (опыт P4, один прогон, результаты, раздел «Опыты перед агентом (P1–P6)»); агент для такого ресурса вызывает `up`. `drbdadm up` для файла без метаданных возвращает `rc=1` и `No valid meta data found`, оставляя ресурс наполовину настроенным: ресурс присутствует в `drbdsetup status`, локальный диск `Diskless`, обе связи `StandAlone` (опыт P6).

Агент узла без копии не создаёт файл тома, loop-устройство и ссылку на устройство и не вызывает `create-md`. В секции этого узла файла ресурса стоит `disk none`; ресурс поднимается командой `drbdadm up`, если его нет в ядре, и приводится в соответствие командой `drbdadm adjust`, если он настроен. Первое применение на узле без диска печатает `[WriteRes, Up, MarkApplied]` (`stand/agent-smoke.sh`, шаг b). На стенде `adjust` с `disk none` на неподнятом ресурсе поднял сторону без диска (`disk:Diskless client:yes`, опыт P4, результаты, раздел «Опыты перед агентом (P1–P6)»).

Начальная полная синхронизация пустых копий пропускается: агент узла с
наименьшим `nodeId` среди узлов с копией выполняет
`drbdadm new-current-uuid --clear-bitmap <имя>/0` только если все стороны
`Connected` и диски всех копий `Inconsistent`. Проверено на стенде с DRBD 9.3.4
для трёх копий и для двух копий со стороной без диска: одна команда на одном
узле переводит все копии из `Inconsistent` в `UpToDate`, остальные стороны
пишут в `dmesg` `disk( Inconsistent -> UpToDate ) [skip-initial-sync]`, досылки
нет.

#### Маркеры на узле

Агент хранит пять служебных файлов на каждый том. Маркеры и копия файла
ресурса записываются так: текст пишется во временный файл `.<имя файла>.tmp`
в том же каталоге, файл синхронизируется (`fsync`), переименовывается в
целевое имя, затем синхронизируется каталог.

| Файл | Каталог | Когда создаётся | Как используется |
|---|---|---|---|
| `<том>.img.ready` | `/var/lib/rancher/ambar/volumes/` | После `drbdadm create-md` и `fsync` файла `<том>.img`: `create-md` пишет через loop-устройство, поэтому синхронизируется сам файл. Сразу после создания файла, до `create-md`, агент также выполняет `fsync` файла и каталога | `create-md` выполняется только для файла `<том>.img` без этого маркера |
| `<том>.img.creating` | `/var/lib/rancher/ambar/volumes/` | Перед `drbdadm create-md` для файла без маркера `.img.ready`, после того как `drbdadm dump-md` показал, что метаданных в файле нет. Удаляется в действии `MarkReady` после записи `.img.ready` и при `ambar remove`; проход `ambar apply` удаляет его рядом с `.img.ready` и вместе с `.img.ready`/`.img.synced` при отсутствии файла тома | Запись «этот агент сам начал `create-md`». Если процесс прервался после `create-md` до записи `.img.ready`, следующий `ambar apply` при наличии маркера не вызывает `dump-md` и повторяет `create-md`: метаданные в файле создал этот же агент. Маркер не заставляет вызывать `create-md` для файла с `.img.ready` |
| `<том>.img.synced` | `/var/lib/rancher/ambar/volumes/` | На узле с копией, в проходе `ambar apply`, где не запланировано других шагов: статус совпадает с описанием тома, файл ресурса записан и применён. Условие на статус: `drbdsetup status` показывает диск тома 0 на этом узле как `UpToDate` либо диск тома 0 любой другой стороны как `UpToDate`, `Consistent` или `Outdated`. После `new-current-uuid --clear-bitmap` маркер пишет следующий запуск `ambar apply`, а не тот, что выполнил команду | Пока маркера нет, у тома на этом узле нет известного источника данных. При наличии маркера `new-current-uuid --clear-bitmap` не выполняется |
| `<том>.res.applied` | `/etc/drbd.d/` | После `drbdadm up`, если повторно прочитанный `drbdsetup status` показывает ресурс настроенным; после `drbdadm adjust`, если код возврата равен нулю, ресурс настроен и статус совпадает с описанием тома | Копия применённого `<том>.res`. Если она отличается от текста, построенного по описанию тома, агент выполняет `drbdadm adjust`. Под `include` по шаблону `*.res` файл не попадает |
| `<том>.lock` | `/var/lib/rancher/ambar/volumes/` | В начале `ambar apply` и `ambar remove` | Исключительная блокировка `flock` без ожидания на всё время команды. Если блокировку держит другой процесс или файл блокировки заменён (`ambar remove` удаляет его под блокировкой), команда завершается ошибкой `Busy` с кодом выхода 75 (`EX_TEMPFAIL`) и ничего не делает. Остальные ошибки завершаются с кодом 1 |

Агент узла с наименьшим `nodeId` среди узлов с копией выполняет
`new-current-uuid --clear-bitmap` при одновременном выполнении всех условий:

- маркера `<том>.img.synced` на узле нет;
- в этом проходе не запланировано других шагов: файл тома готов, loop-устройство
  и ссылка на месте, `<том>.res` и `<том>.res.applied` совпадают с текстом,
  построенным по описанию тома;
- статус совпадает с описанием: `node-id` узла, `minor` тома 0, набор
  соединений (имя и `peer-node-id`) равен набору остальных сторон тома,
  локальный диск не `Diskless`;
- локально: роль `Secondary`, диск тома 0 `Inconsistent`, `client: false`,
  устройство не открыто (`open: false`), `suspended: false`;
- есть хотя бы одно соединение; все соединения `Connected`, все стороны
  `Secondary`; у каждой стороны устройство тома 0 в состоянии репликации
  `Established` с диском `Inconsistent` либо `Diskless` с `peer-client: true`
  (сторона без диска).

Вместо повторной инициализации копии агент завершается ошибкой и ничего не
делает в двух случаях:

| Состояние на узле с копией | Ошибка | Причина |
|---|---|---|
| `<том>.img` есть, `<том>.img.ready` нет, `<том>.img.synced` есть | `ReadyMarkerLost` | `<том>.img.synced` пишется только после создания метаданных, значит метаданные были созданы и у тома был источник данных |
| `<том>.img` нет или нет `<том>.img.ready`, ресурс присутствует в `drbdsetup status` | `UninitialisedFileWithLiveResource` | `create-md` не выполняется под настроенным ресурсом; ресурс снимает оператор (`drbdadm down <том>`) |

Если `<том>.img` нет, `<том>.img.ready` или `<том>.img.synced` есть и ресурс
не настроен (`ambar remove` прерван после удаления файла тома, файл удалён
вручную), агент удаляет оба маркера, синхронизирует каталог и создаёт копию
заново.

Ограничение: если каталог томов потерян сразу на всех узлах с копией (например,
не смонтирован), каждая копия создаётся заново пустой, маркеров нет ни на одном
узле, и узел с наименьшим `nodeId` пропускает начальную синхронизацию: том
поднимается пустым.

Второе ограничение: маркер `<том>.img.synced` пишет первый `ambar apply`, который
видит у тома источник данных. До этого прохода защита от повторного пропуска
синхронизации на узле не действует. Если копия ведущего узла создана заново и
до следующего `apply` на этом узле потеряна и создана заново ещё и копия, с
которой шла досылка, оба диска `Inconsistent`, маркера у ведущего узла нет, и
условие пропуска выполняется: неполная копия объявляется равной пустой. То же
при `apply`, выполненном, пока узел с данными недоступен (`peer-disk-state`
`DUnknown`): маркер не пишется. Как часто агент вызывает `apply`, определяет
фаза 2; в фазе 1 его запускает оператор.

`ambar remove --name <том>` проверяет имя тома, берёт блокировку и, если
ресурс настроен, выполняет `drbdadm down`, затем повторно читает
`drbdsetup status`. Если ресурс остался в статусе, команда завершается ошибкой
`NotApplied` и ничего не удаляет. Иначе она отключает loop-устройства файла
тома (если файла уже нет — устройство, на которое указывает
`/dev/ambar/<том>`, при условии что `losetup` называет его файлом
`<том>.img` с пометкой `(deleted)` или без неё) и удаляет файлы в таком
порядке:

1. `<том>.img`, затем `fsync` каталога томов.
2. `<том>.img.ready` и `<том>.img.synced`, затем `fsync` каталога томов.
3. Ссылку `/dev/ambar/<том>`, `<том>.res`, `<том>.res.applied`, затем `fsync`
   `/etc/drbd.d/`.
4. `<том>.lock`, последним, пока блокировка ещё взята.

Если удаление прервано после шага 1, на узле остаются маркеры без файла тома;
следующий `ambar apply` их удаляет. Файл тома без `<том>.img.ready` после
прерванного удаления не остаётся.

### Монтирование (`NodeStageVolume`, `NodePublishVolume`)

1. `NodeStageVolume`: если на `/dev/drbd<minor>` нет файловой системы, создать
   ext4. Признак «нет файловой системы»: устройство открылось без ошибки, и
   сигнатуры файловой системы на нём нет [проверить: способ чтения сигнатуры].
   При любой ошибке открытия, включая `EMEDIUMTYPE`, `mkfs` не выполняется.
   Смонтировать устройство в каталог staging. Перевод узла в `Primary`
   выполняет DRBD при открытии устройства (`auto-promote yes`). Если том
   открыт на другом узле, открытие завершается ошибкой, и агент возвращает
   `FAILED_PRECONDITION`; kubelet повторяет вызов. Признак: `open(2)` на
   `/dev/drbd<minor>` возвращает `EMEDIUMTYPE` (в том числе только на чтение),
   `mount` завершается с кодом 32 и текстом `Can't open blockdev`, в `dmesg`
   `Auto-promote failed: Multiple primaries not allowed by config`. Тот же
   `mount` с кодом 32 и `Can't open blockdev` наблюдался и без кворума, и без
   доступа к `UpToDate`-данным (опыт C1); причина в этих случаях видна только в
   `dmesg` (`Auto-promote failed: No quorum (-25)` или `Need access to UpToDate
   data (-2)`) или в выводе `drbdadm primary` (`rc=11` и `rc=17`).
2. `NodePublishVolume`: bind-монтирование каталога staging в каталог пода.

### Размонтирование

`NodeUnpublishVolume` снимает bind-монтирование, `NodeUnstageVolume`
размонтирует устройство. DRBD возвращает узел в `Secondary` при закрытии
устройства.

### Чего агент фазы 1 не делает

- Соединение в `StandAlone` не обрабатывается: `ambar apply` не выполняет
  `adjust` для него, пока описание и остальной статус совпадают.
- Изменение `sizeBytes` у существующего тома игнорируется: файл тома не
  изменяется.
- Узел с копией, у которого в описании стало `diskful: false`, получает файл
  ресурса с `disk none` и `adjust`; файл `<том>.img`, маркеры и loop-устройство
  остаются.
- Узел без копии, у которого в описании стало `diskful: true`, получает
  `UninitialisedFileWithLiveResource`, пока ресурс настроен в ядре; нужен
  `drbdadm down <том>` вручную.
- Узел, которого нет в описании тома, получает `NotAMember`; ресурс на нём
  остаётся поднятым.
- Совпадение `minor` или `port` у разных томов не проверяется.
- Статус всех ресурсов узла читается при каждом вызове (`drbdsetup status
  --json` без имени ресурса).
- У команд `drbdadm`, `drbdsetup` и `losetup` нет тайм-аута.

### Удаление (`DeleteVolume`)

Controller удаляет объект `ReplicatedVolume`. Агент каждого узла по
финализатору выполняет `drbdadm down`, отключает loop-устройство, удаляет файл
и убирает запись своего узла из `status.nodes`. Controller снимает финализатор,
когда `status.nodes` пуст. Если узел недоступен, удаление ждёт его возврата.

### Старт агента после перезагрузки узла

Агент проходит по всем объектам `ReplicatedVolume`, где есть его узел,
подключает loop-устройства и выполняет `drbdadm up` для ресурса, которого в ядре
нет (после перезагрузки узла в ядре ресурсов нет), и `drbdadm adjust` для
настроенного. Проверка `stand/agent-smoke.sh --reboot`, один узел (`dv-2`):
после `limactl stop --force dv-2` и запуска узла `ambar load-module` напечатал
`loaded drbd 9.3.4 …`, `ambar apply` напечатал `[AttachLoop, LinkDevice, Up,
MarkApplied]`, диск перешёл в `UpToDate` (результаты, раздел
«Проверки агента на стенде»). DRBD досылает блоки,
изменённые за время отсутствия узла, по битовой карте. До завершения этого
прохода CSI Node отвечает на `NodeStageVolume` кодом `UNAVAILABLE`.

### Добавление узла в кластер

Решение 2026-11-13: новый узел подключается к тому по требованию, когда на него назначен под с этим томом; шаги 2 и 3 ниже выполняются для одного тома в этот момент, а не для всех томов при добавлении узла.

Узел, появившийся в кластере после создания томов, подключается ко всем существующим томам как сторона без диска, чтобы под с любым томом мог запуститься на нём.

1. Запись узла (адрес на `lan0`, постоянный `nodeId`) попадает в `ConfigMap ambar-nodes`, на узле запускается агент.
2. В `spec.nodes` каждого существующего `ReplicatedVolume` добавляется запись нового узла с `diskful: false`.
3. Агенты остальных узлов обновляют файл ресурса и добавляют сторону в работающий ресурс, агент нового узла поднимает ресурс с `disk none`. На стенде (опыт P5, один прогон, результаты, раздел «Опыты перед агентом (P1–P6)») после обновления файла ресурса `drbdadm adjust` на двух работающих узлах и `drbdadm up` на новом узле соединили все три стороны (`Connected`); в выборках счётчика через ~0.5 с запись на `Primary` росла каждый раз и ошибок не было (остановка короче интервала не видна); строк `quorum(` на узлах с копией при добавлении стороны (08:49:21–08:50:11) не появилось, отчёт о кворуме — `quorum:yes`; как добавление стороны меняет расчёт кворума, не изучалось `[проверить: расчёт кворума при добавлении стороны]`. Нужен ли `adjust` на каждом из двух узлов по отдельности, не проверялось `[проверить: adjust только на части узлов]`.

Проверка: в `status.nodes` нового узла у каждого тома соединения `Connected`.

Метаданные тома рассчитаны на число сторон, заданное при `create-md` (`--max-peers`). Поведение при числе узлов сверх этого запаса: [проверить: можно ли добавить сторону без пересоздания метаданных]. Размер запаса: «Открытые вопросы».

## Параметры ресурса DRBD

| Параметр | Значение | Что делает | Когда менять |
|---|---|---|---|
| `protocol` | из StorageClass | Момент подтверждения записи | Задаётся при создании тома |
| `quorum` | `majority` | Узел принимает запись, только пока видит большинство сторон ресурса | Не менять |
| `on-no-quorum` | `io-error` | Без кворума `fsync` возвращает `EIO` (буферизованная запись без `fsync` при этом проходила); журнал ext4 прерывается (`Aborting journal`). При `Errors behavior: Continue` точка монтирования остаётся `rw` (`findmnt`), новые записи получают `Read-only file system` или `Input/output error` | Не менять. Строка обязательна в `.res`: значение по умолчанию в 9.3.4 — `suspend-io` |
| `auto-promote` | `yes` | Роль `Primary` берётся при открытии устройства | Не менять |
| `allow-two-primaries` | `no` | При соединённых сторонах второй узел не может открыть устройство. При разрыве связи `Primary` могут оказаться два узла одновременно (опыт E1: `dv-1` с `quorum:no` и `dv-2` с `quorum:yes`, оба `open:yes`); запись на изолированном узле останавливают только `quorum majority` и `on-no-quorum io-error` | Не менять |
| метаданные | `internal` | Метаданные DRBD лежат в конце файла тома | Не менять |

Выбор `io-error` против `suspend-io` проверен на стенде (DRBD 9.3.4, по одному
прогону). С `suspend-io` процесс на изолированном узле висит в `fsync` в
состоянии `D` до возврата сети, `SIGKILL` его не снимает, `umount` возвращает
`target is busy`, устройство остаётся открытым и узел остаётся `Primary` до
возврата сети. С `io-error` писатель получает `EIO` через 10–11 с после
изоляции, после чего `umount` проходит и узел уходит в `Secondary`.

Состояние соединений после возврата сети зависит не от политики, а от роли
изолированного узла в этот момент. Узел в `Secondary` соединился сам. Узел,
оставшийся `Primary` (при `suspend-io` всегда, при `io-error` — если том ещё
смонтирован), пишет в `dmesg` сам `I shall become SyncTarget, but I am primary!`,
и его соединения переходят в `StandAlone`; после размонтирования они сами не
восстанавливаются. Условие: к моменту возврата сети другой узел стал `Primary`
и писал на том (на стенде `dv-2`, опыт E1 и шаг 7). В шаге 7 в `StandAlone`
перешла одна связь из двух (`dv-1`↔`dv-3`), в опыте E1 обе. Их восстановил
`drbdadm adjust <имя>`: в E1 на `dv-1`, `dv-2`, `dv-3` после размонтирования
на `dv-1`, в шаге 7 на `dv-1` и `dv-3` — на обеих сторонах связи; `adjust`
только на вернувшемся узле оставил соединения в `StandAlone`. `adjust` на
трёх узлах при смонтированном томе и роли `Primary` вернул `rc=0`, связи снова
перешли в `StandAlone` с тем же сообщением (опыт C2, прогон 2, один прогон);
после `umount` на узле `adjust` на трёх узлах соединил всех за ~2 с. Если
другие узлы за время изоляции на том не писали, связи изолированного
`Primary` восстановились сами без `adjust` (опыт C2, прогон 1, один прогон).

### Освобождение тома при потере кворума

Без кворума `on-no-quorum io-error` возвращает `EIO` на `fsync` через 10–11 с
после изоляции, но точка монтирования остаётся, устройство открыто, узел
остаётся `Primary` (шаг 6, опыт E1). Изоляция на стенде закрывала только
TCP 7000: kubelet и API оставались доступны, и под никто не трогал. Узел,
оставшийся `Primary` к возврату сети, переходит в `StandAlone`, если другой
узел за это время писал на том.

Порядок, который выполняет агент узла:

1. Агент читает `devices[].quorum` из `drbdsetup status --json` для томов,
   смонтированных на узле.
2. Если кворума нет дольше grace period (по умолчанию 30 с, параметр агента), агент удаляет через API поды на своём узле, которые используют этот том.
3. Агент ставит на свой узел taint `ambar.balookrd.github.io/no-quorum` с эффектом `NoSchedule`, пока узел не видит другие узлы по сети репликации. Запущенные поды остаются на узле. Новые поды на узел не планируются, в том числе поды без томов `ambar`; манифесты сервисов менять не нужно. Момент установки относительно grace period: «Открытые вопросы».
4. kubelet размонтирует том, DRBD переводит узел в `Secondary`. [проверить:
   размонтирование kubelet после удаления пода не проверялось, на стенде
   `umount` выполнялся вручную]
5. Контроллер пода (Deployment, StatefulSet) создаёт под на узле, где есть
   кворум.
6. После восстановления связи с другими узлами по сети репликации агент снимает taint. Условие снятия, если кворум вернулся не у всех томов узла: «Открытые вопросы».

Решение освобождать том подкреплено двумя записанными наблюдениями (опыт C2,
по одному прогону на случай):

- Другие узлы за время изоляции писали на том. `adjust` при ещё
  смонтированном томе и роли `Primary` вернул `rc=0`, связи снова ушли в
  `StandAlone` (`I shall become SyncTarget, but I am primary!`); после `umount`
  узел стал `Secondary`, `adjust` на трёх узлах соединил всех за ~2 с.
- Другие узлы на том не писали. Связи вернулись сами за ~2 с после снятия
  изоляции, но ext4 на изолированном узле осталась с прерванным журналом
  (`Detected aborted journal`) и возвращала `EIO` на запись и чтение, пока не
  выполнены `umount` и `mount`; после повторного `mount` ядро пишет `mounting
  fs with errors, running e2fsck is recommended`.

Если с изолированного узла недоступен API server, агент не может ни удалить под, ни поставить taint. Он ждёт возврата API и ничего не делает локально с подом и монтированием. Остальные узлы видят узел как `NotReady`; Kubernetes создаёт замену пода по истечении `tolerationSeconds`, узел с кворумом открывает том (шаг 6: `dv-2` смонтировал том, пока `dv-1` был изолирован). После возврата связи агент освобождает том (шаги 2–4) и переподключает ресурс, см. «StandAlone и split-brain».

Грace period и параметры `adjust` описаны в «Параметры агента», права на удаление подов и изменение узлов — в «Права агента (RBAC)».

### StandAlone и split-brain

`StandAlone` на стенде наблюдался в четырёх ситуациях
(`2026-11-12-drbd9-spike-results.md`). Настоящий split-brain получен один раз,
при `quorum off` (опыт C3); в проектной конфигурации (`quorum majority`) он не
получен и не проверялся.

| Ситуация | Что в `StandAlone` | Сообщение ядра | Что сняло |
|---|---|---|---|
| Шаг 7: `suspend-io`, узел `Primary` при возврате сети, другой узел писал | одна связь из двух (`dv-1`↔`dv-3`) | `Split-Brain detected` в `dmesg` нет | `drbdadm adjust` на обеих сторонах связи, данные не отбрасывались |
| Опыт E1: `io-error`, том не размонтирован до возврата сети, другой узел писал | обе связи `dv-1` | `I shall become SyncTarget, but I am primary!` | размонтирование и `drbdadm adjust` на трёх узлах, данные не отбрасывались |
| Опыт C2, прогон 2: то же, `adjust` сначала при смонтированном томе | обе связи `dv-1`, затем снова после `adjust` | `I shall become SyncTarget, but I am primary!` | `adjust` при смонтированном томе не помог; после `umount` `adjust` на трёх узлах соединил всех за ~2 с |
| Опыт C3: `quorum off`, обе стороны писали при изоляции, обе `Secondary` | обе связи жертвы `dv-1` и связи выживших с ней | `uuid_compare()=split-brain-auto-recover by rule=bitmap-both`, `Split-Brain detected but unresolved, dropping connection!` | на жертве `disconnect` и `connect --discard-my-data`, на двух других узлах `connect`; данные жертвы отброшены |

Агент каждого узла выполняет `drbdadm adjust <имя>` для ресурса, у которого
есть соединение в `StandAlone`, пока локальная роль узла — `Secondary`. На узле
в роли `Primary` (том смонтирован) агент `adjust` не вызывает: он выполняется
после освобождения тома. На стенде `adjust` потребовался на обеих сторонах
связи: в опыте E1 на трёх узлах, в шаге 7 на `dv-1` и `dv-3`; `adjust` только
на вернувшемся узле оставил соединения в `StandAlone`. Результат `adjust`
агент читает по `connection-state`, не по коду возврата (см. «Утилиты DRBD»).

Split-brain агент определяет по отказу `adjust`, журнал ядра не читает. Если соединение остаётся `StandAlone` после нескольких попыток `adjust`, пока том освобождён (локальная роль `Secondary`), агент выставляет метрику `ambar_volume_manual_check_needed` и прекращает попытки. Число попыток и интервал между ними — параметры агента, значения по умолчанию: «Открытые вопросы». Причину человек находит в `dmesg` на узлах; сообщения ядра, которыми различаются случаи, перечислены в таблице выше. Метрика не отличает split-brain от других причин, по которым `adjust` не снимает `StandAlone`.

Что записано о различении случаев (опыты E1 и C3, по одному прогону):

- В `drbdsetup status --json` нет поля, которым `StandAlone` после split-brain
  отличался бы от `StandAlone` из E1; набор ключей совпадает, различаются роль,
  `open`, `quorum` и счётчики.
- В захвате `events2` опыта C3 есть только `connection:Disconnecting` →
  `StandAlone`, отличающего признака нет; `events2` для E1 не снимался.
- Различие записано только в тексте сообщения ядра (см. таблицу).
- Гипотеза, не проверенная как признак: при split-brain у сторон разные
  текущие UUID при общем UUID битовой карты, в E1 текущий UUID одной стороны
  стоял в истории другой. `drbdadm get-gi` снимался только после C3
  `[проверить: годится ли сравнение UUID как признак split-brain]`.

### Разрешение split-brain вручную

Условие: метрика `ambar_volume_manual_check_needed` равна `1`. Человек смотрит `dmesg` на узлах ресурса (в C3 — `Split-Brain detected but unresolved, dropping connection!`) и выбирает копию, которую нужно отбросить.

**Внимание.** `connect --discard-my-data` отбрасывает на выбранном узле все записи, которых нет на остальных узлах. В C3 потеряны записи 897–15875, подтверждённые писателем на выбранном узле после изоляции. Узел для отбрасывания выбирает человек, агент этого не проверяет.

Процедура, выполненная в C3:

```bash
# on the node whose data is discarded, inside the agent container
drbdadm disconnect <имя>
drbdadm connect --discard-my-data <имя>
# on every other node whose connection to it is StandAlone
drbdadm connect <имя>
```

В C3 одна пара команд на жертве оставила `dv-2` и `dv-3` в `StandAlone`
(~20 с, вывод проверки не записан); связь поднялась после `connect` на двух
других узлах. Потеряны записи 897–15875, подтверждённые писателем на жертве
после изоляции; это следствие `quorum off`.

### Принудительное повышение вручную

Случай: узел с новейшей копией потерян безвозвратно, оставшиеся устаревшая копия и узел без диска кворума не получают (`replicas: 2`, опыт C1: `1 of 2 nodes visible, need 2 for quorum`), `mount` и `drbdadm primary` отклонены. Если узел с новейшей копией вернётся, `--force` не нужен: кворум восстанавливается (`Restored quorum from before reboot`), split-brain в C1 не возник. Агент `drbdadm primary --force` не вызывает.

**Внимание.** Устаревшая копия после перезапуска показывает свой диск как `UpToDate` (опыт C1), поэтому состояние диска не говорит, актуальны ли данные. Принудительное повышение копии, которая старше потерянной, теряет все записи, сделанные после её последней синхронизации, в том числе записи, подтверждённые приложению. Агент условие не проверяет. [проверить: что произойдёт, если потерянный узел потом вернётся; `primary --force` на стенде не выполнялся]

1. Убедитесь, что узел с новейшей копией не вернётся.
2. Определите, какая из оставшихся копий новее. [проверить: способ; на стенде не записан, сравнение UUID через `drbdadm get-gi` не проверено как признак]
3. Выполните на выбранном узле внутри контейнера агента (`<имя>` — имя ресурса):

```bash

```

## Ограничения

- Время переезда пода с упавшего узла определяет Kubernetes: под выселяется
  через `tolerationSeconds` (по умолчанию 300 с). Поды с томами `ambar`
  задают меньшее значение для `node.kubernetes.io/unreachable` и
  `node.kubernetes.io/not-ready`.
- Deployment с томом `ambar` использует стратегию `Recreate`. При
  `RollingUpdate` с `maxSurge` новый под на другом узле не откроет том, пока
  жив старый.
- Под StatefulSet на недоступном узле Kubernetes не пересоздаёт без
  принудительного удаления. Автоматическое принудительное удаление драйвер не
  выполняет; агент удаляет поды только на своём узле при потере кворума.
- Под без контроллера (Deployment, StatefulSet), удалённый агентом при потере
  кворума, не пересоздаётся.
- Если с изолированного узла недоступен API server, агент ждёт его возврата и ничего не делает с подом и монтированием: том остаётся смонтированным на изолированном узле, замена пода появляется на другом узле после `tolerationSeconds`.
- `replicas` не меньше 2; тома без репликации остаются на `local-path`.
- Taint `ambar.balookrd.github.io/no-quorum` с эффектом `NoSchedule` действует на все новые поды узла, а не только на поды с томами `ambar`.
- `drbdadm primary --force` выполняет только человек; потеря узла с новейшей копией при `replicas: 2` требует ручной процедуры.
- Узел, добавленный сверх запаса сторон в метаданных тома (`--max-peers`), подключается к тому [проверить: возможно ли без пересоздания метаданных].
- Под каждую новую версию ядра нужен образ агента с модулем под неё. Порядок
  обновления узла: выкатить образ с новым модулем, затем `apt full-upgrade` и
  перезагрузка. При обратном порядке агент на узле завершится с ошибкой
  `no drbd module for kernel`, тома на узле не поднимутся, два других узла
  продолжат работу.
- В первую версию не входят: снапшоты, расширение тома, бэкап на NAS, тома
  `ReadWriteMany`, шифрование.

## Проверка

### Модульные тесты

- Генерация файла ресурса из `ReplicatedVolume`: N копий и M сторон без диска
  (три копии; две копии и сторона без диска), протоколы `C` и `A`.
- Разбор `drbdsetup status --json` на записанных образцах вывода.
- Выбор узлов и проверка бюджета в `CreateVolume`: узел из `selected-node`
  плюс N−1 узлов с наибольшим свободным бюджетом, остальные без диска.
- Условие запуска `drbdadm adjust` агентом: `StandAlone`, роль `Secondary`, число попыток не исчерпано; после исчерпания попыток агент выставляет `ambar_volume_manual_check_needed` = `1` и прекращает попытки.
- `CreateVolume` с `replicas: 1` возвращает ошибку.
- Постановка и снятие taint `ambar.balookrd.github.io/no-quorum` при потере и возврате связи по сети репликации.
- Появление узла в `ambar-nodes` добавляет запись с `diskful: false` в `spec.nodes` существующих объектов `ReplicatedVolume`.
- Выделение `minor` и `port`.
- Выбор каталога модуля по версии ядра и отказ при загруженном модуле 8.4.

### Стенд

Три ВМ Debian trixie arm64 на маке с k3s. ВМ ставят тот же пакет ядра
`linux-image-6.12.116+deb13-arm64`, что и узлы, поэтому на стенде загружается
тот же `drbd.ko`.

Писатель-проба: под, который в цикле дописывает запись в файл, вызывает
`fsync` и после успешного `fsync` отправляет номер записи наружу (в журнал
вне тома). После каждого сценария все номера из журнала должны быть в файле.

Сценарии:

1. Создание, монтирование, запись, удаление тома при `replicas: 3` и `2`; `StorageClass` с `replicas: 1` отклоняется при создании тома.
2. Выключение ВМ с подом: под поднимается на другом узле, подтверждённые
   записи на месте.
3. Блокировка `lan0` на узле с подом: запись получает ошибку, под поднимается
   на другом узле, после снятия блокировки узел досинхронизируется.
4. Убийство агента на узле с подом: запись не прерывается.
5. Перезагрузка узла без пода: досылка по битовой карте, без полной
   синхронизации.
6. Одновременное выключение всех ВМ и старт: тома монтируются.
7. Загрузка узла с заранее загруженным штатным `drbd` 8.4: агент завершается
   с ошибкой, остальные узлы работают.
8. N копий и стороны без диска: при `replicas: 2` под запускается на узле без
   копии, открывает устройство и пишет. Стенд состоит из трёх ВМ, поэтому
   другие сочетания N и числа сторон без диска, кроме 3 копий без стороны без
   диска и 2 копий с одной, на нём не воспроизвести.
9. Освобождение тома агентом: блокировка TCP 7000 на узле с подом; после grace
   period (30 с) агент удаляет под и ставит taint `ambar.balookrd.github.io/no-quorum`, kubelet размонтирует том, узел
   уходит в `Secondary`, под поднимается на узле с кворумом, подтверждённые
   записи на месте.
10. Автоматический `adjust` после `StandAlone`: после сценария 9 снять
    блокировку; агенты выполняют `adjust`, все соединения `Connected` без
    команд оператора.
11. Taint: в сценарии 9 `kubectl describe node` показывает
    `ambar.balookrd.github.io/no-quorum:NoSchedule` во время блокировки; под без тома
    `ambar`, созданный в это время, на узел не планируется; после снятия
    блокировки и восстановления связи taint снят.
12. Агент прекращает `adjust`: ресурс с `quorum off` как в опыте C3, обе стороны
    пишут при изоляции; после снятия блокировки и освобождения тома соединение
    остаётся `StandAlone` после всех попыток, `ambar_volume_manual_check_needed`
    равна `1`, новых `adjust` нет.
13. Добавление узла: к стенду добавляется четвёртая ВМ (только для этого
    сценария); сторона без диска подключается ко всем существующим томам без
    команд оператора, под с томом запускается на ней, открывает устройство и
    пишет. Частично закрыт опытом P5 (один прогон, без агента, три ВМ):
    `adjust` на двух узлах и `up` на новом соединили три стороны, том
    читался через новый узел. Не закрыто: добавление агентом, четвёртая ВМ, под
    с записью через новую сторону.
14. Полная изоляция узла (сеть репликации и API server): агент не меняет под и
    монтирование; замена пода запускается на узле с кворумом после
    `tolerationSeconds`; после возврата связи агент освобождает том, ресурс
    соединяется.
15. Заполнение раздела с файлами томов: [проверить: поведение DRBD и ext4 при
    `ENOSPC` в файле тома].

Если цель по `fsync` не достигнута, отдельно замеряется вклад loop-устройства
(том без остальных копий) и вклад сети.

## Что проверяется первым

Пункты, от которых зависит остальная реализация; каждый закрывается на стенде
до написания CSI-части:

1. Модуль 9.3.4 загружается на ядре `6.12.116+deb13-arm64` с
   `usermode_helper=disabled`.
2. Ресурс из трёх сторон поверх loop-устройств с `--direct-io=on` поднимается
   и синхронизируется.
3. Пропуск начальной синхронизации через `new-current-uuid --clear-bitmap`.
4. Сторона без диска при `replicas: 2` может открыть устройство на запись и
   сохраняет кворум, который у неё уже был, при пропадании узла с копией.
5. Поведение `on-no-quorum io-error` против `suspend-io` для ext4 и kubelet
   (для kubelet не проверено: все проверки использовали `mount` на хосте).
6. `drbdadm` и `drbdsetup` работают из контейнера без установки на хост.

Результаты проверки на стенде: `2026-11-12-drbd9-spike-results.md`.
