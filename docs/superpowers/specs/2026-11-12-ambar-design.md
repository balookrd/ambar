# ambar: реплицируемые тома PVC для k3s поверх DRBD 9

Спека описывает CSI-драйвер `ambar`: что он делает, из чего состоит и как ведёт
себя при отказах узлов. Документ адресован тому, кто пишет план реализации и
код. Дата: 2026-11-12; приведена к коду фазы 2б 2026-11-18.

| Фаза | Что даёт | Состояние |
|---|---|---|
| 0. Образ и стенд | модуль DRBD 9 в образе, стенд из ВМ Lima | исполнена |
| 1. Ядро агента | согласование одного тома на узле через CLI (`ambar apply`, `ambar remove`) | исполнена |
| 2а. Kubernetes | CRD `ReplicatedVolume`, цикл согласования агента, CSI Identity, Controller и Node, манифесты `deploy/` | исполнена; на стенде из четырёх ВМ том создаётся, монтируется и удаляется через PVC (результаты, разделы «Проверки CSI на стенде» и «Повторная проверка CSI после второго раунда исправлений») |
| 2б. Смена набора копий | добавление, удаление и перенос копии у существующего тома | исполнена; CLI `ambar replica add`, `remove`, `move` с правилами безопасности и переназначением свидетеля (результаты, раздел «Проверки смены набора копий на стенде») |
| 3. Отказы | освобождение тома при потере кворума, taint, `adjust` при `StandAlone`, метрики | не начата |
| 4. Замер на R5C | память, `fsync`, сравнение с Longhorn | не начата, нужны узлы |

Разделы и строки с пометкой «дизайн фазы 3» описывают поведение, которого в
коде нет. Остальной текст описывает код в `src/` и манифесты в `deploy/`.
«Результаты» в ссылках — документ `2026-11-12-drbd9-spike-results.md`.

## Окружение и требования

| Что | Значение |
|---|---|
| Кластер | k3s, сейчас три узла `k3s-1..3`, все три — server с etcd |
| Железо узла | NanoPi R5C: RK3568B2, 4 ГБ RAM, NVMe 128 ГБ |
| ОС и ядро | Debian 13 trixie, штатное ядро `6.12.116+deb13-arm64` |
| NVMe | один раздел ext4 `LABEL=k3s-data`, смонтирован в `/var/lib/rancher` |
| Сеть репликации | интерконнект `lan0`, 2.5GbE; адреса в документе взяты из диапазона для документации `192.0.2.0/24` (RFC 5737): `192.0.2.51–53/24` |
| Существующие StorageClass | `local-path` (том привязан к узлу), `nfs-client` (NAS, адрес `<nas_host>` в документе не приводится) |

Требования владельца:

- Число копий тома задаёт параметр `replicas: N`, N не меньше 2: N копий лежат на N узлах.
- В исправном состоянии запись подтверждается приложению после того, как она
  легла на диски всех N узлов с копией (`protocol: C`). После отказа k узлов с
  копией остаётся N−k копий; при `replicas: 2` после отказа одного такого узла
  запись идёт на один диск (`2026-11-12-drbd9-spike-results.md`, шаг 8 и
  опыт E2). Исключение — `protocol: A`, см. «Принятые решения».
- В каждый момент том монтирует один узел. Тома с одновременной записью с
  нескольких узлов не нужны.
- Под с томом может запуститься на любом узле кластера: узел без копии
  подключается к ресурсу без диска, когда на него назначен под с этим томом.
- Потребление памяти и CPU ниже, чем у Longhorn 1.12.2 на этих же узлах
  (замер 2026-11-09: поды 145–348 МиБ на узел, `fsync` 4 КиБ 13.6 мс).

## Принятые решения

Строки с номером R1–R18 — технические решения плана фазы 2а
(`docs/superpowers/plans/2026-11-13-ambar-phase2a-kubernetes.md`), строки
R19–R31 — технические решения плана фазы 2б
(`docs/superpowers/plans/2026-11-14-ambar-phase2b-replica-set.md`) в том виде,
в каком они реализованы; где ревью изменили решение плана, строка называет
дату замены. Строки без номера — решения владельца и решения, принятые при
ревью.

| Решение | Причина |
|---|---|
| Репликацию выполняет модуль ядра DRBD 9 | Запись не проходит через userspace; у ресурса до трёх и более сторон и встроенный кворум |
| Данные тома — разреженный файл на NVMe, подключённый как loop-устройство | NVMe занят одним ext4; переразметка требует остановки k3s на каждом узле |
| Модуль DRBD 9 собирается заранее и поставляется в образе агента | На узлах нет компилятора; `boot.scr` переписывается на последнее ядро без фолбэка, сборка на узле в момент обновления недопустима |
| Состояние томов хранится в CRD | Своей базы нет; etcd уже есть |
| Проект переименован: `duovol`, затем `sklad`, сейчас `ambar` (2026-11-12) | Первое название означало «том на двух узлах» и не подходит при `replicas: N`. В старых заметках, коммитах и образах `duovol-drbd` и `sklad-drbd` речь о том же проекте |
| Отдельный репозиторий | Драйвер не связан с wire-протоколом `outline-proxy` и его vendored-крейтами |
| `replicas: N` — целое число не меньше 2: N копий лежат на N узлах. Остальные узлы подключаются к ресурсу без диска по требованию (строка «Узел без копии подключается к тому по требованию») | Решение владельца 2026-11-12: под запускается на любом узле. Сторона без диска в роли `Primary` писала при `replicas: 2` на трёх узлах и сохранила уже имевшийся кворум, когда узел с копией пропал (шаг 8, опыт E2); заново запущенной устаревшей копии кворум она не дала (опыт C1, два прогона) `[проверить: tiebreaker сохраняет уже имевшийся кворум, но не даёт его заново запущенному узлу — предположение]`. `replicas: 3` без стороны без диска — шаг 4. Другие сочетания на стенде не запускались |
| `protocol: A` остаётся параметром StorageClass как исключение из требования о записи на диски узлов с копией | Решение владельца 2026-11-12. При `protocol: A` запись, подтверждённая приложению, но не покинувшая сетевой буфер, теряется при отказе узла. [проверить: `protocol: A` на стенде не запускался] |
| Дизайн фазы 3. Том при потере кворума освобождает агент `ambar`: по истечении grace period (30 с) он удаляет поды с этим томом на своём узле; пока узел не видит другие узлы по сети репликации, на узле стоит taint `NoSchedule` | Решение владельца 2026-11-12. На стенде изоляция закрывала только TCP 7000, kubelet и API оставались доступны; после `EIO` точка монтирования остаётся, узел остаётся `Primary`, `umount` вручную проходит и узел уходит в `Secondary` (шаг 6, опыт E1). Узел, оставшийся `Primary` к возврату сети, переходит в `StandAlone`, если другой узел писал на том (шаг 7, опыты E1 и C2); если не писал, связи восстановились сами (опыт C2, прогон 1) |
| Дизайн фазы 3. Агент каждого узла выполняет `drbdadm adjust` для ресурса с соединением в `StandAlone`, пока локальная роль — `Secondary`, ограниченное число попыток | Решение владельца 2026-11-12. `adjust` снимал `StandAlone` без отбрасывания данных, `Split-Brain detected` в `dmesg` не было (шаг 7, опыт E1); понадобился на обеих сторонах связи, `adjust` только на вернувшемся узле не хватило. `adjust` при роли `Primary` и смонтированном томе связь не снял: она снова ушла в `StandAlone` (опыт C2, прогон 2, один прогон) |
| `replicas` не меньше 2: при создании тома `replicas: 1` отклоняется | Решение владельца 2026-11-12 (вторая серия). Кворум при одной копии и узлах без диска на стенде не запускался; число непроверенных сочетаний сокращено. Тома без репликации остаются на `local-path`. На стенде `replicas: "1"` дал событие `ProvisioningFailed` с `InvalidArgument` (результаты, «Проверки CSI на стенде», шаг i) |
| Дизайн фазы 3. Grace period без кворума — 30 с, значение по умолчанию настраиваемого параметра агента | Решение владельца. На стенде после изоляции узла писатель получил ошибку через 10–11 с (шаг 6, опыт E1); пауза записи без потери кворума длилась 4.6–5.6 с (шаг 8, опыт E2), 11.3 с и ~6 с (опыт C1, `replicas: 2`) |
| Дизайн фазы 3. Узел помечается taint `ambar.balookrd.github.io/no-quorum` с эффектом `NoSchedule`. Агент ставит его на свой узел, пока узел не видит другие узлы по сети репликации, и снимает после восстановления связи | Решение владельца. Запущенные поды остаются на узле; новые поды на узел не планируются, в том числе поды без томов `ambar`; манифесты сервисов менять не нужно |
| Дизайн фазы 3. Если с изолированного узла недоступен API server, агент ждёт его возврата и ничего не делает с подом и монтированием | Решение владельца. Остальные узлы видят узел как `NotReady`, Kubernetes создаёт замену пода по истечении `tolerationSeconds`, узел с кворумом открывает том (шаг 6: `dv-2` смонтировал том, пока `dv-1` был изолирован). После возврата связи агент освобождает том и переподключает ресурс |
| `drbdadm primary --force` выполняет только человек вручную; агент его не вызывает | Решение владельца. Устаревшая копия после перезапуска показывает свой диск как `UpToDate` (опыт C1), поэтому состояние диска не говорит, актуальны ли данные. Процедура и предупреждение: «Принудительное повышение вручную» |
| Файл тома разреженный, предел суммы размеров — `capacityBytes` | Решение владельца. Файлы на стенде создавались разреженными (`truncate -s`, `stand/spike/res.sh`). [проверить: поведение DRBD и ext4 при `ENOSPC` в файле тома] |
| Каждый том создаётся с запасом места в метаданных DRBD под будущие стороны (`maxPeers`, R3). Узел, добавленный в кластер после создания тома, подключается к нему без диска по требованию, пока участников тома не больше `maxPeers + 1` | Решение владельца: под должен запускаться на новом узле. Битовая карта занимает 32 КиБ на 1 ГиБ тома на одну сторону (шаг 4: 64 КиБ при двух остальных сторонах с копией; шаг 8: 32 КиБ при одной). Сторона без диска, добавленная внутри запаса к работающему ресурсу из двух копий (`adjust` на двух узлах, `up` на новом), подключилась (`Connected`) и сообщила `size` 1048316 КиБ (опыт P5, один прогон, результаты, раздел «Опыты перед агентом (P1–P6)»). Четвёртый узел стенда подключался к томам как `Client` (результаты, «Проверки CSI на стенде», шаг e). Добавление стороны сверх запаса не запускалось |
| Дизайн фазы 3. Split-brain определяется по отказу `adjust`: агент не читает журнал ядра | Решение владельца. Если соединение остаётся `StandAlone` после нескольких попыток `adjust`, пока том освобождён (локальная роль `Secondary`), агент выставляет метрику «нужна ручная проверка» и прекращает попытки; причину человек ищет в `dmesg`. `drbdsetup status --json` не отличает split-brain от `StandAlone` в E1 (опыт C3) |
| Отметку «том новый, начальная синхронизация не пропущена» хранит объект `ReplicatedVolume` в поле `spec.initialSync` (R7). Маркеры на узле остаются второй проверкой | Решение владельца 2026-11-13. С одними маркерами потеря каталога томов на всех узлах с копией приводит к пустому тому на месте прежнего (раздел «Маркеры на узле») |
| Узел без копии подключается к тому по требованию: когда на него назначен под с этим томом, и отключается после ухода пода | Решение владельца 2026-11-13, заменило постоянное подключение всех узлов кластера ко всем томам. Число соединений DRBD растёт с числом томов в работе, а не с произведением числа томов на число узлов. Добавление стороны к работающему ресурсу: опыт P5 (один прогон). Отключение стороны без диска от работающего ресурса при писателе на другом узле: опыт P8 (один прогон): после `adjust` на двух узлах с копией соединение с ушедшим узлом исчезло из статуса, `acked` писателя рос в выборках через ~0.5 с, `quorum:yes` (результаты, раздел «Опыты перед CSI (P7–P10)») |
| При чётном числе копий контроллер назначает тому одного постоянного свидетеля: узел без диска, подключённый всё время жизни тома. При нечётном числе копий свидетеля нет | Решение владельца 2026-11-13. Без свидетеля том с `replicas: 2` при отказе одного из двух узлов теряет кворум (`quorum majority`), запись возвращает ошибку. Сторона без диска сохранила имевшийся кворум при отказе узла с копией (шаг 8, опыт E2). Чётные N больше 2 на стенде не запускались. Если вне копий в `ambar-nodes` нет узла (N равно числу узлов), свидетеля нет: `placement::place` не возвращает ошибку |
| Набор узлов с копией у существующего тома можно менять: добавить копию, удалить копию, перенести копию на другой узел | Решение владельца 2026-11-13, реализовано в фазе 2б (R19–R31) через CLI `ambar replica add`, `remove`, `move`. Смена набора копий выполняется на лету под работающей нагрузкой без остановки записи |
| Перед `create-md --force` агент читает метаданные файла тома командой `drbdadm dump-md` и делит результат на `Metadata::Absent`, `Metadata::Fresh` и `Metadata::Used`. `create-md` выполняется только для `Absent` (P7) и `Fresh` (состояние сразу после `create-md`, P10 (1)). `Used` (метаданные, которые были частью тома, «unclean», вывод, который агент не разобрал) даёт ошибку `MetadataPresent`; любой другой отказ `dump-md` — ошибку проверки (`DrbdError::MetadataCheck`). Во всех этих случаях агент ничего не пишет. Заменило 2026-11-13 промежуточный маркер `.img.creating` | Решение владельца 2026-11-13, уточнено после опытов P7 и P10. Закрывает случай потерянного маркера `.img.ready` у файла с данными без маркера `.img.synced`. Маркер `.img.creating` не отличал прерванный `create-md` от файла с данными, а метаданные сами показывают, поднимался ли ресурс (P10 (2)–(6)) |
| Фаза 2 разделена на два плана: 2а (CRD, контроллер, CSI, манифесты; набор копий неизменяем) и 2б (смена набора копий) | Решение владельца 2026-11-13. Работающий PVC появляется по завершении 2а; смена копий добавлена в 2б |
| R1. Запись узла в `spec.nodes` имеет поле `kind`: `Replica` (копия данных), `Retiring` (копия данных в процессе снятия), `Witness` (постоянный узел без диска при чётном N), `Client` (узел без диска на время работы пода). Поля `diskful` в объекте нет; в описании тома для `Reconciler` узел с копией — это `kind: Replica` (`to_volume_spec`) | Свидетеля нельзя отключать при уходе пода, клиента нужно, снимаемую копию нужно изолировать; по одному признаку «без диска» их не различить |
| R2. `address` и `maxPeers` записаны в объекте: адрес копируется из `ConfigMap ambar-nodes`, когда узел становится участником тома (создание, `join_as_client`, `replica add`); `maxPeers` задаётся при создании и не меняется | Агент собирает описание тома из одного объекта |
| R3. `maxPeers` — параметр `StorageClass`, по умолчанию `7`. При создании тома значение должно быть не меньше числа узлов в `ambar-nodes` минус один и не больше 31, иначе `INVALID_ARGUMENT` | `create-md --max-peers=7` проверен на стенде (опыты P2, P5, P7–P10); другие значения не запускались. Нижняя граница оставляет место каждому узлу кластера на момент создания для подключения клиентом (уточнение кода, 2026-11-13) |
| R4. `nodeId` узла постоянный и берётся из `ConfigMap ambar-nodes`; узел без записи в ней не становится участником тома | `nodeId` стороны DRBD нельзя менять у работающего ресурса; один источник номеров на кластер |
| R5. `ConfigMap ambar-nodes` хранит список в ключе `nodes` как JSON-массив | В крейте есть `serde_json`, YAML-парсер не нужен; JSON-массив является и корректным YAML |
| R6. `minor` и `port` выделяются одним индексом: `minor = 1000 + i`, `port = 7000 + i`, `i` — наименьший свободный среди существующих объектов, включая удаляемые. Агент не применяет том, у которого `minor` или `port` совпадает с другим объектом (`Refusal::Collision`), и отказывает обоим объектам пары | Закрывает вопрос ревью о коллизиях. Агенты проверяют совпадение по кэшу `watch`, поэтому более новый объект с совпадающим `minor` или `port` может быть применён раньше, чем агент увидит более старый; у нового объекта данных нет. Отказ обоим — ограничение, см. «Чего драйвер после фазы 2а не делает» |
| R7. Отметка «том новый»: поле `spec.initialSync` со значениями `Skip` и `Done`. `CreateVolume` создаёт объект со `Skip`; агент-лидер, у которого есть маркер `.img.synced`, меняет значение на `Done` JSON-патчем. Отсутствующее поле читается как `Done`. Правило CRD запрещает переход `Done` → `Skip` | Решение владельца; значение по умолчанию запрещает пропуск синхронизации |
| R8. Членство узла в томе при `NodeStageVolume` добавляет агент этого узла: дописывает себя в `spec.nodes` с `kind: Client`. При `NodeUnstageVolume` агент удаляет свою запись `Client`. Дополнено 2026-11-14: при окончательной ошибке `NodeStageVolume` членство снимается по состоянию узла (строка «Снятие членства `Client` после неудачного `NodeStageVolume`») | `attachRequired: false`, вызова `ControllerPublishVolume` нет |
| R9. Финализаторы — по одному на узел с копией: `ambar.balookrd.github.io/replica-<имя узла>`. Агент узла снимает свой финализатор после удаления локальной копии. Единого финализатора и ожидания пустого `status.nodes` нет. - Longhorn: потребление по замеру выше допустимого.
- Свой движок репликации в userspace (ublk, NBD): повторяет Longhorn, путь
  записи идёт через процесс.

- Подключение всех узлов кластера ко всем томам как сторон без диска (спека

- Поле `diskful` в записи узла и единый финализатор `ambar.balookrd.github.io/cleanup`

## Проверенные факты

- Конфиг штатного ядра Debian (`config-6.12.85+deb13-arm64` из образа
  `rk3568-nanopi-r5c_trixie-13.4.img.xz`): `CONFIG_BLK_DEV_DRBD=m` (версия 8.4),
  `CONFIG_MODULE_SIG=y`, `CONFIG_MODULE_SIG_FORCE` не задан (неподписанный
  модуль загружается).
- DRBD 9.3.4 (тег `drbd-9.3.4`, `github.com/LINBIT/drbd`) собирается под
  `linux-headers-6.12.116+deb13-arm64` в контейнере `debian:trixie` arm64 за
  30 с без предупреждений. Результат: `drbd.ko`, `drbd_transport_tcp.ko`;
  `vermagic: 6.12.116+deb13-arm64 SMP mod_unload modversions aarch64`;
  `depends: lru_cache,libcrc32c`.

Команда сборки:

```bash
apt-get install -y --no-install-recommends git ca-certificates build-essential \
  kmod coccinelle python3 linux-headers-6.12.116+deb13-arm64
git clone --depth 1 --branch drbd-9.3.4 --recursive --shallow-submodules \
  https://github.com/LINBIT/drbd /src
make -j4 -C /src/drbd KDIR=/lib/modules/6.12.116+deb13-arm64/build SPAAS=false
```

`SPAAS=false` запрещает сборке обращаться к сервису LINBIT за патчем
совместимости; патч генерирует локальный `coccinelle`.

На стенде с ядром `6.12.116+deb13-arm64` модуль загружается
(`2026-11-12-drbd9-spike-results.md`, допущение 1); на R5C загрузка не проверена.

## Компоненты

### Агент `ambar`

Один бинарь на Rust. Команда `ambar agent` работает в DaemonSet `ambar` на
каждом узле кластера: привилегированный контейнер, `hostNetwork: true`,
`hostPID` не нужен. В одном процессе:

| Часть | Что делает | Код |
|---|---|---|
| Проверки при старте | `NODE_NAME` равен `/proc/sys/kernel/hostname`, каталог томов существует; иначе агент завершается с ошибкой до загрузки модуля и до обращения к API server | `agent::run::preflight` |
| Загрузчик модуля | Загружает DRBD 9 из образа, см. «Загрузка модуля» | `src/module_loader.rs` |
| Цикл согласования | Следит за объектами `ReplicatedVolume`; для каждого имени тома читает объект и состояние узла, решает, что делать (`agent::decide::decide`), выполняет решение (`reconcile::Reconciler`) и пишет запись своего узла в `status.nodes` | `src/agent/` |
| CSI Identity, Controller, Node | gRPC на unix-сокете `/var/lib/kubelet/plugins/ambar/csi.sock` | `src/csi/` |
| Освобождение тома, `adjust` при `StandAlone`, taint, метрики | Дизайн фазы 3, в коде нет; см. «Освобождение тома при потере кворума», «StandAlone и split-brain», «Метрики» | — |

Команды бинаря:

| Команда | Что делает |
|---|---|
| `ambar agent` | Агент узла. Флаги: `--node-name` (переменная `NODE_NAME`), `--csi-socket` (по умолчанию `/var/lib/kubelet/plugins/ambar/csi.sock`), `--namespace` (переменная `POD_NAMESPACE`, по умолчанию `ambar-system`; из него читается `ConfigMap ambar-nodes`), `--modules-dir` (по умолчанию `/opt/ambar/modules`). Работает до `SIGTERM` или `SIGINT`: начатый проход согласования доходит до конца |
| `ambar load-module` | Загружает модуль DRBD 9 (`--modules-dir`) |
| `ambar apply --file <файл>` | Приводит узел к описанию тома из JSON-файла (CLI фазы 1) |
| `ambar remove --name <том>` | Снимает ресурс тома на узле и удаляет локальную копию без проверок цикла согласования: решение оператора |
| `ambar status --name <том>` | Печатает состояние DRBD тома на узле |
| `ambar crd` | Печатает CRD `ReplicatedVolume` в JSON; `deploy/crd.json` — её вывод |
| `ambar replica <add\|remove\|move>` | Управление репликами тома: добавление (`add <том> <узел>`), снятие (`remove <том> <узел>`) или перенос (`move <том> <откуда> <куда>`). Флаги: `--namespace` (env `POD_NAMESPACE`, по умолчанию `ambar-system`), `--timeout` (в секундах, по умолчанию 0 — без ограничения). Коды выхода: 0 — выполнено, 1 — отказ правил, таймаут или ошибка API |

Коды выхода `apply` и `remove`: 0 — выполнено, 75 — том заблокирован другим
процессом `ambar`, 1 — любая другая ошибка. Коды выхода `replica`: 0 — выполнено,
1 — отказ, таймаут или ошибка API.

Цикл согласования. Одна задача выполняет проход (`Agent::reconcile_one`) для
имён из очереди по одному. Имя ставится в очередь сразу, когда watch сообщает
об объекте, и повторно после прохода:

| Исход прохода | Повтор через |
|---|---|
| Проход выполнил шаги (`Progress`) | 1 с |
| Копия удерживается из-за состояния DRBD: этот узел `Primary`, сторона `Primary`, сторона не соединена (`KeptDrbd`) | 5 с |
| Ошибка | 5 с |
| Узел приведён к описанию (`Settled`) или копия удерживается по другой причине (`Kept`) | 30 с |
| Отказ (`Refused`) | 60 с |
| Объекта нет и на узле ничего нет (`Gone`) | не повторяется |

Раз в 30 с в очередь ставятся имена всех объектов и всех локальных остатков:
так находятся остатки объектов, которых уже нет. Признак готовности `ready`
становится истинным, когда каждое имя первого списка прошло один проход без
ошибки API или трижды завершилось ошибкой API. Проход одного тома выполняется
под блокировкой этого тома внутри процесса (`Agent::locks`) и под `flock`
файла `<том>.lock`.

### Параметры агента

Настраиваются только флаги команды `ambar agent` (таблица выше). Остальные
значения заданы в коде:

| Значение | Где | Что делает |
|---|---|---|
| 120 с | `exec::DEFAULT_COMMAND_TIMEOUT` | Тайм-аут внешней команды; по истечении группа процессов команды получает `SIGKILL` |
| 120 с + 1 с на каждый начатый ГиБ, не меньше 120 с | `drbd::adm::create_md_timeout` | Тайм-аут `drbdadm create-md` |
| 60 с, опрос раз в 500 мс | `ControllerService::new` | Ожидание `UpToDate` всех копий в `CreateVolume` и исчезновения объекта в `DeleteVolume` |
| 30 с, опрос раз в 500 мс | `NodeService::new` (`stage_wait`) | Ожидание, пока ресурс станет пригодным для монтирования, в `NodeStageVolume` |
| 30 с | `agent::kube::API_CALL_TIMEOUT` | Предел одного вызова API-сервера (`get`, `list`, `list_fresh` по страницам, `create`, `delete`, JSON-патчи, apply статуса, чтение ConfigMap `ambar-nodes`); `watch` не ограничен. По истечении вызов завершается ошибкой «the API server did not answer within 30 s», которую вызывающий код обрабатывает как любую ошибку API: проход агента повторяется через 5 с, CSI отвечает `UNAVAILABLE`. Без предела запрос к API-серверу, потерявшему питание после приёма запроса, держал бы замок вызывающего (мьютекс размещения, замок тома, очередь `reconcile`) бесконечно |
| 5 с | `csi::SHUTDOWN_GRACE` | Предел ожидания сервера gRPC после сигнала остановки |
| 1, 5, 30, 60 с | `src/agent/run.rs` | Задержки повтора прохода, см. «Агент `ambar`» |

`terminationGracePeriodSeconds: 150` в `deploy/daemonset.yaml` больше тайм-аута
команды: проход с командой до 120 с доходит до конца после `SIGTERM`.

### Сайдкары

Штатные образы Kubernetes CSI, закреплённые по digest в `deploy/daemonset.yaml`:

| Контейнер | Версия | Аргументы |
|---|---|---|
| `node-driver-registrar` | v2.18.0 | `--csi-address=/csi/csi.sock`, `--kubelet-registration-path=/var/lib/kubelet/plugins/ambar/csi.sock` |
| `csi-provisioner` (`external-provisioner`) | v6.4.0 | `--leader-election`, `--leader-election-namespace=$(POD_NAMESPACE)` (Lease в пространстве имён пода), `--strict-topology`, `--timeout=90s`, `--default-fstype=ext4` |

`external-provisioner` работает в каждом поде DaemonSet, активен один (выбор
лидера). CSI Controller отвечает на каждом узле, запросы получает только от
активного provisioner. `--timeout=90s` больше 60 с, которые `CreateVolume`
ждёт копий.

`external-attacher` не используется: объект `CSIDriver` объявляет
`attachRequired: false`. Без `VolumeAttachment` Kubernetes не ждёт 6 минут
перед принудительным отсоединением тома от недоступного узла `[проверить: на
стенде не проверялось]`.

Контейнер `ambar` запускается с `--csi-socket=/var/lib/kubelet/plugins/ambar/csi.sock`
(тот же путь, что у проверки готовности и у обоих сайдкаров; это и значение по
умолчанию `ambar agent`).

Проверка готовности контейнера `ambar`: `test -S /var/lib/kubelet/plugins/ambar/csi.sock`,
период 5 с. Сокет привязывается одновременно с циклом согласования и не ждёт
его первого прохода: Pod становится `Ready`, когда сокет есть, а
`NodeStageVolume` до конца первого прохода отвечает `UNAVAILABLE` (шаг 1).
Проверка не обращается к сокету; файл сокета, оставшийся после `SIGKILL`, даёт
`Ready` раньше времени, обычная остановка файл удаляет. Проверки живости нет:
проход может выполнять внешнюю команду до 120 с, перезапуск по проверке
оборвал бы его. `minReadySeconds: 10` в `DaemonSet`: плавное обновление
переходит к следующему узлу через 10 с после `Ready` предыдущего.

Монтирования контейнера `ambar`: `/dev`, `/lib/modules` (только чтение),
`/var/lib/rancher/ambar/res` хоста в `/etc/drbd.d`, каталог томов
`/var/lib/rancher/ambar/volumes` (оба с `type: Directory`) и `/var/lib/kubelet`
с `mountPropagation: Bidirectional`. Каталог сокета
`/var/lib/kubelet/plugins/ambar` входит в монтирование `/var/lib/kubelet` и
второй раз в контейнер `ambar` не монтируется. На стенде при втором
монтировании этого каталога рядом с двунаправленным число монтирований
`plugins/ambar` на узлах было 2^n − 1 (от 4095 до 32767), создание контейнера
занимало до ~100 с; после удаления второго монтирования три перезапуска подов
число не меняли (результаты, «Проверки CSI на стенде», «Удвоение монтирований
в поде агента»; механизм `[проверить: не изолирован отдельным опытом]`).

### Утилиты DRBD

`drbdadm`, `drbdsetup`, `drbdmeta` собираются из исходников `drbd-utils` и
кладутся в образ агента. На хост утилиты не ставятся. Версия `drbd-utils`
выбирается совместимой с модулем 9.3.4; проверено с 9.35.0 (в Debian trixie
пакет 9.22.0). Каждая команда выполняется с тайм-аутом (R14).

Агент определяет результат команды `drbdadm`, повторно читая
`drbdsetup status --json`, а не по коду возврата. Статус читается для всех
ресурсов узла, из вывода берётся ресурс тома. Что читается после каждой
команды:

| Команда | Что проверяется после неё |
|---|---|
| `drbdadm dump-md` | Не меняет состояние. Выполняется перед `create-md`; код 0 и вывод дают `Fresh` или `Used`, код 255 с `Found meta data is "unclean"` на stderr — `Used`, код 255 с `No valid meta data found` — `Absent`, любой другой результат — ошибка проверки (см. «Создание (`CreateVolume`)») |
| `drbdadm up` | ресурс присутствует в статусе |
| `drbdadm adjust` | код возврата равен нулю (ненулевой код — отказ, нулевой не доказывает успех), и статус совпадает с описанием: `node-id`, `minor` тома 0, набор соединений (имя и `peer-node-id`), диск (локальный не `Diskless` на узле с копией, `client` на узле без диска) |
| `drbdadm down` (в `ambar remove`, `Reconciler::remove_checked`) | ресурс отсутствует в статусе |
| `drbdadm create-md`, `drbdadm new-current-uuid` | статус не перечитывается; команда должна вернуть код 0, а результат подтверждает следующий проход: после `create-md` есть маркер `.img.ready` и ресурс поднимается, после `new-current-uuid` статус показывает диск `UpToDate` и проход пишет маркер `.img.synced` |

Наблюдалось (`2026-11-12-drbd9-spike-results.md`, опыты C2 и C3, по одному
прогону): `drbdadm disconnect` вернул `rc=0`, когда ядро отказало (`Can not
disconnect a StandAlone device (-9)`); `drbdadm connect` вернул `rc=10` для
уже соединённой пары, хотя связь с `StandAlone`-пиром поднялась; `drbdadm
adjust` вернул `rc=0`, а соединение снова ушло в `StandAlone`.

### `StorageClass`

| Параметр | Значения | По умолчанию | Что делает |
|---|---|---|---|
| `replicas` | целое число N, 2 ≤ N ≤ число узлов в `ambar-nodes` | `3` | Число узлов с копией данных (`kind: Replica`). При чётном N тому назначается свидетель. `replicas: 1` и N больше числа узлов отклоняются кодом `INVALID_ARGUMENT`; тома без репликации остаются на `local-path` |
| `protocol` | `C`, `A` | `C` | `C`: запись подтверждается после записи на диски сторон с копией. `A`: после локального диска и отправки в сокет; при падении узла теряется содержимое сетевого буфера, то есть записи, подтверждённые приложению, но не покинувшие узел. `A` — исключение из требования о записи на диски узлов с копией |
| `maxPeers` | целое число, от числа узлов в `ambar-nodes` минус один до 31 | `7` | Число сторон, под которое создаются метаданные (`create-md --max-peers`); у тома не больше `maxPeers + 1` участников. Не меняется после создания |
| `csi.storage.k8s.io/fstype` | `ext4` | `ext4` | Файловая система тома. Драйвер принимает пустое значение и `ext4`; `external-provisioner` запущен с `--default-fstype=ext4` |

Другие ключи параметров отклоняются (`INVALID_ARGUMENT`, `unknown parameter`),
кроме ключей с префиксом `csi.storage.k8s.io/`, которые драйвер пропускает.
Значения `replicas` и `maxPeers` разбираются как неотрицательные целые,
`protocol` — только `A` или `C`.

Размер тома: `capacity_range.required_bytes`, округлённый вверх до кратного
4096; `0` — 1 ГиБ. Отрицательное значение, размер больше 2^50 байт и
`limit_bytes` меньше округлённого размера отклоняются кодом `OUT_OF_RANGE`.

`volumeBindingMode: WaitForFirstConsumer`, чтобы одна из копий оказалась на
узле, куда назначен под. `allowVolumeExpansion: false`, `reclaimPolicy:
Delete`. В `deploy/storageclass.yaml` два класса: `ambar-r3` (`replicas: "3"`)
и `ambar-r2` (`replicas: "2"`).

Режимы доступа: тип доступа только `mount` (блочные тома отклоняются), режимы
CSI `SINGLE_NODE_WRITER`, `SINGLE_NODE_SINGLE_WRITER`,
`SINGLE_NODE_MULTI_WRITER`, `SINGLE_NODE_READER_ONLY`; остальные отклоняются
кодом `INVALID_ARGUMENT`. Режимы PVC, под которые рассчитан драйвер:
`ReadWriteOnce`, `ReadWriteOncePod`.

### `ReplicatedVolume` (CRD, cluster-scoped, группа `ambar.balookrd.github.io/v1alpha1`)

Короткое имя `rv`. Имя объекта совпадает с идентификатором тома CSI
(`pvc-<UUID>`, где `<UUID>` задаёт `external-provisioner`). CRD генерирует
`ambar crd` (`src/crd.rs`), результат лежит в `deploy/crd.json`.

Пример: `replicas: 2` в кластере из четырёх узлов (четвёртый узел —
`192.0.2.54`), под тома запущен на `k3s-4`.

```yaml
apiVersion: ambar.balookrd.github.io/v1alpha1
kind: ReplicatedVolume
metadata:
  name: pvc-<UUID>
  finalizers:
    - ambar.balookrd.github.io/replica-k3s-1
    - ambar.balookrd.github.io/replica-k3s-2
  annotations:
    ambar.balookrd.github.io/formatted: "true"
spec:
  sizeBytes: 2147483648
  protocol: C
  minor: 1000          # /dev/drbd1000
  port: 7000           # TCP-порт ресурса на lan0
  maxPeers: 7
  initialSync: Done
  nodes:
    - {name: k3s-1, nodeId: 0, address: 192.0.2.51, kind: Replica}
    - {name: k3s-2, nodeId: 1, address: 192.0.2.52, kind: Replica}
    - {name: k3s-3, nodeId: 2, address: 192.0.2.53, kind: Witness}
    - {name: k3s-4, nodeId: 3, address: 192.0.2.54, kind: Client}
status:
  nodes:
    - name: k3s-4
      role: Primary
      disk: Diskless
      quorum: true
      connections:
        - {peer: k3s-1, state: Connected, peerDisk: UpToDate}
        - {peer: k3s-2, state: Connected, peerDisk: UpToDate}
        - {peer: k3s-3, state: Connected, peerDisk: Diskless}
      message: ""
```

| Поле | Что задаёт | Кто пишет |
|---|---|---|
| `spec.sizeBytes` | Размер тома в байтах, кратен 4096, от 4096 до 2^50 | Controller при создании |
| `spec.protocol` | `C` или `A` | Controller при создании |
| `spec.minor` | Номер устройства `/dev/drbd<minor>`, 0–1048575; выделяется как `1000 + i` | Controller при создании |
| `spec.port` | TCP-порт ресурса, 1024–65535; выделяется как `7000 + i` | Controller при создании |
| `spec.maxPeers` | `create-md --max-peers`, 1–31 | Controller при создании |
| `spec.initialSync` | `Skip` — лидер может пропустить начальную синхронизацию; `Done` — не может. Отсутствующее поле — `Done` | Controller (`Skip`), агент-лидер (`Done`) |
| `spec.nodes[]` | Участники тома: `name` (до 55 символов), `nodeId` (0–31), `address` (адрес на `lan0`, до 45 символов), `kind` (`Replica`, `Retiring`, `Witness`, `Client`). Список с ключом `name`, от 2 до 32 записей | Controller (`Replica`, `Witness`), агент узла (`Client`), CLI `ambar replica` (`Replica`, `Retiring`, `Witness`) |
| `metadata.finalizers` | `ambar.balookrd.github.io/replica-<узел>` для каждого `Replica` и `Retiring` | Controller при создании, CLI при добавлении копии; каждый агент снимает свой после удаления копии |
| `metadata.annotations["ambar.balookrd.github.io/formatted"]` | `"true"`: на томе создавалась файловая система; `mkfs` больше не выполняется | Агент узла, выполнившего `mkfs` или увидевшего ext4 без аннотации |
| `status.nodes[]` | Запись узла: `name`, `role` (`Primary`, `Secondary`, `Unknown`), `disk` (состояние локального диска тома 0, `Diskless` у узла без диска), `quorum`, `connections[]` (`peer`, `state`, `peerDisk`), `message` (последняя ошибка или причина, по которой копия удерживается; пусто после успешного прохода). Список с ключом `name` | Агент своего узла, server-side apply с менеджером полей `ambar-<узел>` |

Правила валидации CRD (`x-kubernetes-validations`). Первые семь сравнивают с
прежним объектом (`oldSelf`) и действуют только при изменении, остальные шесть —
и при создании:

| Правило | Сообщение |
|---|---|
| `sizeBytes`, `minor`, `port`, `maxPeers`, `protocol` не меняются | `sizeBytes, minor, port, maxPeers and protocol are immutable` |
| У записи с тем же именем не меняются `nodeId` и адрес | `a member node cannot change nodeId or address` |
| Разрешены только переходы вида `Witness → Replica`, `Client → Replica`, `Replica → Retiring`, `Client → Witness`, `Witness → Client` | `this change of a node's kind is not allowed` |
| В `Retiring` узел может перейти только из существовавшего участника (`Replica`) | `a node can become Retiring only from Replica` |
| Узел `Replica` удаляется только через переход в `Retiring` | `a Replica node is removed only through Retiring` |
| Набор узлов `Replica`, `Retiring` и `Witness` меняется только когда `initialSync` равен `Done` | `the set of Replica, Retiring and Witness nodes changes only when initialSync is Done` |
| `initialSync` не возвращается из `Done` в `Skip` | `initialSync cannot go back to Skip` |
| Не меньше двух записей `Replica` | `at least two Replica nodes are required` |
| Не более одного узла `Retiring` | `at most one node can be Retiring` |
| `nodeId` уникален | `nodeId must be unique among nodes` |
| `address` уникален (сравнение строк) | `address must be unique among nodes` |
| `sizeBytes` кратен 4096 | `sizeBytes must be a multiple of 4096` |
| `maxPeers` не меньше числа записей минус один | `maxPeers must be at least the number of other nodes` |

Записи `Client` добавляются и удаляются без ограничений, кроме перечисленных.
CRD не проверяет, что `address` — IP-адрес, и не проверяет набор символов имён:
это делает агент перед любыми действиями на узле (`crd::to_volume_spec`,
`VolumeSpec::validate`), объект с ошибкой получает отказ `InvalidSpec`. Узел,
указанный в `spec.nodes` дважды, тоже получает `InvalidSpec`.

| Имя | Правило |
|---|---|
| Том (`metadata.name`) | 1–63 символа `a-z0-9-`, первый символ не `-`, не `all` (`drbdadm down all` действует на все ресурсы узла) |
| Узел (`nodes[].name`) | 1–55 символов `A-Za-z0-9._-`, первый и последний символ — буква или цифра. 55 = 63 − длина `replica-`: имя финализатора должно оставаться квалифицированным именем |

Имя узла в объекте должно совпадать с выводом `uname -n` на этом узле: агент
сравнивает `NODE_NAME` с `/proc/sys/kernel/hostname` при старте, а `drbdadm`
выбирает секцию `on <имя>` файла ресурса по имени хоста.

Каталог `/etc/drbd.d` в контейнере агента (файлы `<том>.res` и
`<том>.res.applied`) — постоянный путь хоста `/var/lib/rancher/ambar/res`
(`deploy/daemonset.yaml`). Если файлы потеряны, агент записывает их заново и
выполняет `drbdadm adjust` для каждого настроенного ресурса.

### `ConfigMap ambar-nodes`

Карта узлов в пространстве имён агента (`ambar-system`): имя узла Kubernetes,
адрес на `lan0`, постоянный `nodeId` и бюджет места под тома. Ключ `nodes`
содержит JSON-массив, по одной записи на узел кластера. Пример для кластера из
трёх узлов:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ambar-nodes
  namespace: ambar-system
data:
  nodes: |
    [
      {"name": "k3s-1", "address": "192.0.2.51", "nodeId": 0, "capacityBytes": 42949672960},
      {"name": "k3s-2", "address": "192.0.2.52", "nodeId": 1, "capacityBytes": 42949672960},
      {"name": "k3s-3", "address": "192.0.2.53", "nodeId": 2, "capacityBytes": 42949672960}
    ]
```

| Поле | Что задаёт |
|---|---|
| `name` | Имя узла Kubernetes, равное `uname -n` узла; правило имени как у `nodes[].name` объекта (1–55 символов) |
| `address` | IP-адрес узла на сети репликации |
| `nodeId` | Номер стороны DRBD, 0–31; не меняется у узла |
| `capacityBytes` | Предел суммы `sizeBytes` томов, у которых узел — `Replica` |

Список отклоняется целиком, если он пуст, если в записи есть неизвестное поле,
если имя не проходит правило, `nodeId` больше 31, или имя, `nodeId` либо адрес
повторяются (`config::ClusterNodes::from_json`). Агент читает ConfigMap при
каждом `CreateVolume` и при каждом подключении клиента и ничего не кеширует:
правка карты действует без перезапуска. Образец — `deploy/nodes-configmap.example.yaml`;
для стенда объект создаёт `stand/install.sh`.

`capacityBytes` — предел суммы объявленных размеров томов с копией на узле
(включая удаляемые объекты; свидетель и клиент бюджет не занимают). Файлы томов
разреженные, поэтому без предела сумма размеров может превысить свободное место
на NVMe, и тогда запись в том получит ошибку ввода-вывода вместе с etcd и
containerd на том же разделе.

## Загрузка модуля

Образ агента содержит модули по пути `/opt/ambar/modules/<версия ядра>/`:
`drbd.ko`, `drbd_transport_tcp.ko`. Под каждую версию ядра Debian, которая
стоит или будет стоять на узлах, в образе лежит свой каталог.

Порядок при старте агента:

1. Если существует `/sys/module/drbd`, прочитать `/sys/module/drbd/version`.
   Версия `9.*` — модуль drbd уже загружен: если нет
   `/sys/module/drbd_transport_tcp`, загрузить `drbd_transport_tcp.ko` из
   каталога под версию ядра (`insmod`; без файла — ошибка
   `no drbd_transport_tcp module for kernel <версия>`), затем перейти к шагу 5.
   Версия `8.*` —
   завершиться с ошибкой `in-tree drbd 8.4 is loaded`; тома на узле не
   обслуживаются.
2. Определить версию ядра (`uname -r`). Если каталога с модулем под неё нет,
   завершиться с ошибкой `no drbd module for kernel <версия>`.
3. Загрузить зависимости из дерева модулей хоста: `modprobe lru_cache`,
   `modprobe libcrc32c` (`/lib/modules` хоста смонтирован в контейнер только
   на чтение).
4. `insmod drbd.ko usermode_helper=disabled`, затем
   `insmod drbd_transport_tcp.ko`. `usermode_helper=disabled` отключает запуск
   `/sbin/drbdadm` ядром на хосте: обработчики событий драйвер не использует.
5. Продолжить запуск.

На каждом узле при установке создаётся файл
`/etc/modprobe.d/ambar-blacklist-drbd.conf`:

```text
blacklist drbd
install drbd /bin/false
```

Без него любой вызов `modprobe drbd` на узле загрузит штатный модуль версии
8.4. Метаданные томов версии 9 он не читает, а имя модуля то же, поэтому
модуль версии 9 после этого не загрузится до перезагрузки узла. [проверить:
не проверялось на стенде; файл на стенде создаёт `stand/k3s.sh`, `modprobe drbd`
не вызывался] Чёрный список хоста не действует на `modprobe` внутри
контейнера (`/etc/modprobe.d` в поде `toolbox` пуст), поэтому тот же файл
нужен в образе агента.

## Жизненный цикл тома

### Создание (`CreateVolume`)

`CreateVolume` (`src/csi/controller.rs`) проверяет запрос, размещает том,
создаёт объект `ReplicatedVolume` и ждёт, пока агенты поднимут копии. Шаги по
порядку; первый неудачный шаг отвечает:

| Шаг | Что делает | Код ответа при отказе |
|---|---|---|
| 1 | Имя тома проходит правило имени тома | `INVALID_ARGUMENT` |
| 2 | Каждая `volume_capabilities`: тип `mount` с `fs_type` пустым или `ext4`, режим `SINGLE_NODE_*`; список не пуст | `INVALID_ARGUMENT` |
| 3 | `volume_content_source` не задан (тома из снапшота или другого тома не создаются) | `INVALID_ARGUMENT` |
| 4 | Параметры `StorageClass` разбираются (`placement::parse_parameters`), размер округляется (`placement::round_up_size`) | `INVALID_ARGUMENT` для параметров; `OUT_OF_RANGE` для отрицательного размера, размера больше 2^50 и `limit_bytes` меньше размера |
| 5 | Под мьютексом `placing`: объект с этим именем читается. Удаляемый объект | `ABORTED` |
| 5 | Объект есть, но `sizeBytes`, `protocol`, `maxPeers` или число `Replica` отличаются от запроса | `ALREADY_EXISTS` |
| 5 | Объект есть с теми же параметрами (повтор): пока не все `Replica` сообщили `UpToDate`, живой список объектов проверяется на совпадение `minor` или `port` с другим объектом; ничего не удаляется | `ABORTED` при совпадении |
| 6 | Объекта нет: чтение `ConfigMap ambar-nodes` и живого списка объектов (`Volumes::list_fresh`, список с API server, включая удаляемые объекты), размещение (`placement::place`) | `INVALID_ARGUMENT`: `replicas` меньше 2, больше числа узлов, выбранный узел не в карте, `maxPeers` вне границ. `RESOURCE_EXHAUSTED`: не хватает бюджета, нет свободного индекса |
| 7 | Создание объекта со `initialSync: Skip` и финализаторами `replica-<узел>`. Если объект успел создать другой вызов, шаг 5 повторяется, не больше трёх раз | `ABORTED` после трёх раз |
| 7 | Сразу после создания, под тем же мьютексом, повторное чтение живого списка (`withdraw_if_lost`): другой объект с тем же `minor` или `port` и `creationTimestamp` не позже своего — созданный этим вызовом объект удаляется с предусловием по `uid`. Неясное состояние (своего объекта нет, у него другой `uid`, нет метки времени) ничего не удаляет | `ABORTED` |
| 8 | Ожидание вне мьютекса: объект читается раз в 500 мс, пока все записи `Replica` в `status.nodes` не покажут `disk: UpToDate`. Объект пропал или удаляется | `DEADLINE_EXCEEDED` через 60 с; `ABORTED`, если объект пропал или удаляется |
| 9 | Ответ: `volume_id` — имя тома, `capacity_bytes` — `sizeBytes`, без `volume_context` и `accessible_topology` | — |

Ошибка API server при любом шаге — `UNAVAILABLE`; запрос, который API server
отклонил как неверный, — `INTERNAL`. Каждый шаг повторяем: имя объекта равно
имени тома, повторный вызов находит объект и переходит к ожиданию.
`external-provisioner` повторяет вызов после ошибки `[проверить: повтор после
DEADLINE_EXCEEDED и ABORTED на стенде не записан]`; его тайм-аут — 90 с.

Размещение (`placement::place`, чистая функция карты узлов и списка объектов):

1. Проверить `replicas` (не меньше 2, не больше числа узлов) и `maxPeers`
   (не меньше числа узлов минус один, не больше 31).
2. Первая копия — на узле, выбранном планировщиком (R16), если он задан; у него
   должно хватить свободного бюджета, иначе `RESOURCE_EXHAUSTED`. Свободный
   бюджет узла — `capacityBytes` минус сумма `sizeBytes` объектов, где узел —
   `Replica`.
3. Остальные копии — на узлах с наибольшим свободным бюджетом, которого хватает
   на том; при равенстве — по имени.
4. При чётном N — свидетель: узел вне копий с наибольшим бюджетом. Если такого
   узла нет, свидетеля нет.
5. Индекс `i` — наименьший, для которого ни `1000 + i` среди `minor`, ни
   `7000 + i` среди `port` существующих объектов не заняты; `minor` не больше
   1048575, `port` не больше 65535, иначе `RESOURCE_EXHAUSTED`.
6. Записи `spec.nodes` отсортированы по имени; `address` и `nodeId` — из
   `ambar-nodes`.

На стенде (результаты, «Проверки CSI на стенде», шаги a и d) PVC класса
`ambar-r3` стал `Bound` через 3–10 с, объект получил три `Replica`,
`initialSync: Done` и три записи `UpToDate`; PVC класса `ambar-r2` — через
29–30 с, две `Replica` и один `Witness`.

Что делает агент узла с копией данных (`kind: Replica`) в проходе
согласования объекта:

1. Создать разреженный файл `/var/lib/rancher/ambar/volumes/<имя>.img`
   размером `sizeBytes` плюс место под внутренние метаданные DRBD. На стенде
   файл в 1 ГиБ при двух остальных сторонах с копией потерял на метаданных
   100 КиБ (`size` устройства 1048476 КиБ), при одной стороне с копией и одной
   без диска — 68 КиБ (1048508 КиБ); см. результаты, шаги 4 и 8. Метаданные создаются с запасом сторон под будущие узлы (`create-md --max-peers=<maxPeers>`, по умолчанию 7, R3); каждая сторона занимает 32 КиБ битовой карты на 1 ГиБ тома (шаги 4 и 8). С `create-md --max-peers=7` файл в 1 ГиБ даёт `size` устройства 1048316 КиБ (битовая карта 224 КиБ, 7 × 32 КиБ; опыт P2, один прогон, результаты, раздел «Опыты перед агентом (P1–P6)»). В опыте P5 узел без диска (`node-id` 2 при `--max-peers=7`), добавленный к работающему ресурсу из двух копий, после подключения сообщил `size` 1048316 КиБ, равный результату P2 (три стороны с диском); `size` на узлах с копией до добавления в P5 не записывался `[проверить: size на узлах с копией до и после добавления стороны]`. Формула для других размеров файла и значений `--max-peers` не проверялась `[проверить: другие размеры и значения]`.
2. Подключить файл как loop-устройство с прямым вводом-выводом
   (`losetup --direct-io=on`).
3. Сгенерировать из объекта файл ресурса `<имя>.res`. Если маркера
   `<имя>.img.ready` нет, выполнить `drbdadm create-md --force --max-peers=<maxPeers>`
   и записать маркер (раздел «Маркеры на узле»); для файла с маркером
   `create-md` не вызывается. Перед `create-md` агент читает метаданные файла
   командой `drbdadm dump-md` и решает по ним самим (опыт P10, результаты, раздел
   «Опыты перед CSI (P7–P10)»). `create-md` выполняется, если метаданных нет
   (код 255 и `No valid meta data found`, P7) либо они в состоянии сразу после
   `create-md` (P10 (1), оба прогона). Условия состояния: `version "v09"`,
   `max-peers` равен числу битовых карт; `node-id -1`, `current-uuid`
   `0x0000000000000004`, `flags 0x00000080`, `members 0x0000000000000000`,
   `features 0x0000000000000001`, `la-size-sect 0`, `bm-byte-per-bit 4096`,
   `la-peer-max-bio-size 0`, `al-stripes 1`, `al-stripe-size-4k 8`; во всех 32
   слотах `bitmap-index -1`, `bitmap-uuid`, `bitmap-dagtag` и `flags` равны
   нулю; все `history-uuids` и все битовые карты нулевые. Дампы состояний (2) и
   (3) (после `up` и `down`; `flags 0x00000480`, `members 0x0000000000000001`,
   `bitmap-index` 0 и 1 в слотах 1 и 2, `la-peer-max-bio-size 1048576`) этим
   условиям не удовлетворяют. Метаданные с кодом 255 и
   `Found meta data is "unclean"` на stderr (P10 (2)–(6), после `up` и `down`)
   считаются используемыми: проверка этой строки идёт раньше проверки
   `No valid meta data found`. Любой другой вывод при коде 0, в том числе вывод,
   который агент не разобрал, считается используемыми метаданными. Для
   используемых метаданных агент возвращает ошибку `MetadataPresent` и ничего не
   пишет. Любой другой код возврата `dump-md` (в P7 (3) — 20 при поднятом
   ресурсе) даёт ошибку проверки, `create-md` не выполняется. Затем выполнить `drbdadm up <имя>`, если ресурса
   нет в ядре (создание тома, узел без диска, старт после перезагрузки узла), и
   `drbdadm adjust <имя>`, если ресурс в ядре настроен. На стенде ресурс поднимался командой `drbdadm up`
   (`stand/spike/res.sh`). `drbdadm adjust` на ресурсе, которого в ядре нет, поднимает его: `rc=0`, ресурс настроен и соединён (опыт P4, один прогон, результаты, раздел «Опыты перед агентом (P1–P6)»); агент для такого ресурса вызывает `up`. `drbdadm up` для файла без метаданных возвращает `rc=1` и `No valid meta data found`, оставляя ресурс наполовину настроенным: ресурс присутствует в `drbdsetup status`, локальный диск `Diskless`, обе связи `StandAlone` (опыт P6).

Агент узла без копии (`Witness`, `Client`) не создаёт файл тома, loop-устройство и ссылку на устройство и не вызывает `create-md`. В секции этого узла файла ресурса стоит `disk none`; ресурс поднимается командой `drbdadm up`, если его нет в ядре, и приводится в соответствие командой `drbdadm adjust`, если он настроен. Первое применение на узле без диска печатает `[WriteRes, Up, MarkApplied]` (`stand/agent-smoke.sh`, шаг b). На стенде `adjust` с `disk none` на неподнятом ресурсе поднял сторону без диска (`disk:Diskless client:yes`, опыт P4, результаты, раздел «Опыты перед агентом (P1–P6)»).

Начальная полная синхронизация пустых копий пропускается: агент узла с
наименьшим `nodeId` среди узлов с копией выполняет
`drbdadm new-current-uuid --clear-bitmap <имя>/0` только если объект говорит
`initialSync: Skip`, все стороны `Connected` и диски всех копий `Inconsistent`
(полный список условий — «Маркеры на узле»). Проверено на стенде с DRBD 9.3.4
для трёх копий и для двух копий со стороной без диска: одна команда на одном
узле переводит все копии из `Inconsistent` в `UpToDate`, остальные стороны
пишут в `dmesg` `disk( Inconsistent -> UpToDate ) [skip-initial-sync]`, досылки
нет. Следующий проход лидера пишет маркер `.img.synced`, а проход, который
видит маркер при `initialSync: Skip`, меняет поле на `Done` JSON-патчем с
проверкой `uid` и прежнего значения (`Volumes::mark_initial_sync_done`).
После этого пропуск синхронизации для тома невозможен: правило CRD запрещает
возврат к `Skip`.

#### Маркеры на узле

Маркеры пишет `reconcile::Reconciler`: и в проходе цикла согласования, и в
команде `ambar apply`. Ниже «проход» — любой из этих вызовов.

Агент хранит четыре служебных файла на каждый том. Маркеры и копия файла
ресурса записываются так: текст пишется во временный файл `.<имя файла>.tmp`
в том же каталоге, файл синхронизируется (`fsync`), переименовывается в
целевое имя, затем синхронизируется каталог.

| Файл | Каталог | Когда создаётся | Как используется |
|---|---|---|---|
| `<том>.img.ready` | `/var/lib/rancher/ambar/volumes/` | После `drbdadm create-md` и `fsync` файла `<том>.img`: `create-md` пишет через loop-устройство, поэтому синхронизируется сам файл. Сразу после создания файла, до `create-md`, агент также выполняет `fsync` файла и каталога | `create-md` выполняется только для файла `<том>.img` без этого маркера |
| `<том>.img.synced` | `/var/lib/rancher/ambar/volumes/` | На узле с копией, в проходе, где не запланировано других шагов: статус совпадает с описанием тома, файл ресурса записан и применён. Условие на статус: `drbdsetup status` показывает диск тома 0 на этом узле как `UpToDate` либо диск тома 0 любой другой стороны как `UpToDate`, `Consistent` или `Outdated`. После `new-current-uuid --clear-bitmap` маркер пишет следующий проход, а не тот, что выполнил команду | Пока маркера нет, у тома на этом узле нет известного источника данных. При наличии маркера `new-current-uuid --clear-bitmap` не выполняется |
| `<том>.res.applied` | `/etc/drbd.d/` | После `drbdadm up`, если повторно прочитанный `drbdsetup status` показывает ресурс настроенным; после `drbdadm adjust`, если код возврата равен нулю, ресурс настроен и статус совпадает с описанием тома | Копия применённого `<том>.res`. Если она отличается от текста, построенного по описанию тома, агент выполняет `drbdadm adjust`. Под `include` по шаблону `*.res` файл не попадает |
| `<том>.lock` | `/var/lib/rancher/ambar/volumes/` | В начале прохода и удаления копии | Исключительная блокировка `flock` без ожидания на всё время вызова. Если блокировку держит другой процесс или файл блокировки заменён (удаление копии удаляет его под блокировкой), вызов завершается ошибкой `Busy` и ничего не делает; команды `ambar apply` и `ambar remove` выходят с кодом 75 (`EX_TEMPFAIL`), остальные ошибки — с кодом 1 |

Решение о `create-md` принимает не маркер, а содержимое метаданных: маркер
`.img.ready` отвечает только за то, что файл уже инициализирован, а для файла без
него агент читает `dump-md` (шаг 3 раздела «Создание»). Если процесс прервался
после `create-md` до записи `.img.ready`, метаданные остались в состоянии сразу
после `create-md` (P10 (1)): `up` агент выполняет только после записи маркера.
Следующий проход выполняет `create-md` заново, затем записывает маркер.
Метаданные, с которыми ресурс поднимался (P10 (2)–(6), в том числе «unclean»),
агент не перезаписывает. Файл `<том>.img.creating`, который оставила промежуточная
сборка агента, агент не читает; удаление копии и очистка устаревших маркеров
удаляют его.

Агент узла с наименьшим `nodeId` среди узлов с копией выполняет
`new-current-uuid --clear-bitmap` при одновременном выполнении всех условий:

- в описании тома `initialSync: Skip` (R7; без поля — `Done`);
- маркера `<том>.img.synced` на узле нет;
- в этом проходе не запланировано других шагов: файл тома готов, loop-устройство
  и ссылка на месте, `<том>.res` и `<том>.res.applied` совпадают с текстом,
  построенным по описанию тома;
- статус совпадает с описанием: `node-id` узла, `minor` тома 0, набор
  соединений (имя и `peer-node-id`) равен набору остальных сторон тома,
  локальный диск не `Diskless`;
- локально: роль `Secondary`, диск тома 0 `Inconsistent`, `client: false`,
  устройство не открыто (`open: false`), `suspended: false`;
- есть хотя бы одно соединение; все соединения `Connected`, все стороны
  `Secondary`; у каждой стороны устройство тома 0 в состоянии репликации
  `Established` с диском `Inconsistent` либо `Diskless` с `peer-client: true`
  (сторона без диска).

Вместо повторной инициализации копии агент завершается ошибкой и ничего не
делает в двух случаях:

| Состояние на узле с копией | Ошибка | Причина |
|---|---|---|
| `<том>.img` есть, `<том>.img.ready` нет, `<том>.img.synced` есть | `ReadyMarkerLost` | `<том>.img.synced` пишется только после создания метаданных, значит метаданные были созданы и у тома был источник данных |
| `<том>.img` нет или нет `<том>.img.ready`, ресурс присутствует в `drbdsetup status` | `UninitialisedFileWithLiveResource` | `create-md` не выполняется под настроенным ресурсом; ресурс снимает оператор (`drbdadm down <том>`) |

Если `<том>.img` нет, `<том>.img.ready` или `<том>.img.synced` есть и ресурс
не настроен (удаление копии прервано после удаления файла тома, файл удалён
вручную), агент удаляет оба маркера, синхронизирует каталог и создаёт копию
заново.

Ограничение: если содержимое каталога томов потеряно сразу на всех узлах с
копией, каждая копия создаётся заново пустой и маркеров нет ни на одном узле.
Отсутствующий каталог агент не создаёт и не стартует (R13). При
`initialSync: Done` начальная синхронизация не пропускается, диски остаются
`Inconsistent`, источника данных нет `[проверить: состояние тома, у которого
все копии созданы заново при initialSync: Done, на стенде не запускалось]`.
Пока поле ещё `Skip` (от создания объекта до прохода лидера после
`.img.synced`), узел с наименьшим `nodeId` пропускает синхронизацию, и том
поднимается пустым; аннотация `formatted`, если она уже стоит, запрещает
`mkfs` на таком томе (см. «Монтирование»).

Второе ограничение: маркер `<том>.img.synced` пишет первый проход, который
видит у тома источник данных. До этого прохода защита от повторного пропуска
синхронизации на узле не действует. Если копия ведущего узла создана заново и
до следующего `apply` на этом узле потеряна и создана заново ещё и копия, с
которой шла досылка, оба диска `Inconsistent`, маркера у ведущего узла нет, и
условие пропуска выполняется: неполная копия объявляется равной пустой. То же
при `apply`, выполненном, пока узел с данными недоступен (`peer-disk-state`
`DUnknown`): маркер не пишется. Цикл согласования повторяет проход через 1 с
после прохода с шагами и через 30 с после прохода без шагов (см. «Агент
`ambar`»). Оба окна закрываются, когда поле становится `Done`: после этого
лидер синхронизацию не пропускает.

Удаление копии (`Reconciler::remove` команды `ambar remove --name <том>` и
`Reconciler::remove_checked` агента после его проверки, см. «Удаление
(`DeleteVolume`)») проверяет имя тома, берёт блокировку и, если ресурс
настроен, выполняет `drbdadm down`, затем повторно читает `drbdsetup status`.
Если ресурс остался в статусе, вызов завершается ошибкой `NotApplied` и ничего
не удаляет. Иначе он отключает loop-устройства файла тома (для существующего
файла — найденные `losetup -j`, для удалённого — все, которые
`backing::loop_holders` относит к файлу тома) и удаляет файлы в таком
порядке:

1. `<том>.img`, затем `fsync` каталога томов.
2. `<том>.img.ready` и `<том>.img.synced`, затем `fsync` каталога томов.
3. Ссылку `/dev/ambar/<том>`, `<том>.res`, `<том>.res.applied`, затем `fsync`
   `/etc/drbd.d/`.
4. `<том>.lock`, последним, пока блокировка ещё взята.

Если удаление прервано после шага 1, на узле остаются маркеры без файла тома;
следующий проход их удаляет. Файл тома без `<том>.img.ready` после
прерванного удаления не остаётся.

### Монтирование (`NodeStageVolume`, `NodePublishVolume`)

`NodeStageVolume` (`src/csi/node.rs`) делает узел участником тома, если он им
не был, ждёт, пока устройство DRBD станет пригодным, создаёт файловую систему
только на новом томе и монтирует устройство в каталог staging.
`NodePublishVolume` делает bind-монтирование каталога staging в каталог пода.
kubelet повторяет вызов после ошибки (для `NodeStageVolume` с `UNAVAILABLE`
на стенде — 8 повторов за 77 с, «Повторная проверка CSI после второго раунда
исправлений»), а обработчик может быть прерван в любой точке ожидания,
поэтому каждый вызов безопасно повторить из любого промежуточного
состояния: сначала читается таблица монтирований, правки членства
идемпотентны, `mkfs` не выполняется дважды. Действия на узле выполняются в
отдельной задаче, которая держит блокировку тома, чтобы прерванный
обработчик не снял её, пока `mkfs`, `mount` или `drbdadm down` ещё работают.

`NodeStageVolume`, по порядку (первый неудачный шаг отвечает):

| Шаг | Условие | Код |
|---|---|---|
| 1 | Агент не закончил первый проход (`ready` ложен) | `UNAVAILABLE` |
| 2 | Пустой или относительный путь, имя не проходит правило имени тома, тип доступа не `mount`, `fs_type` не пустой и не `ext4`, флаг монтирования вне списка разрешённых | `INVALID_ARGUMENT` |
| 4 | Путь staging уже занят `/dev/drbd<minor>` этого тома: готово, даже если объект удаляется или его нет (проверяется до шага 3). Там смонтировано другое | `FAILED_PRECONDITION` |
| 3 | Объекта нет или он удаляется | `NOT_FOUND` |
| 5 | Узла нет в `spec.nodes`: агент добавляет его как `Client` (`membership::join_as_client`, JSON-патч с проверкой `uid` и прежнего списка узлов). Узла нет в `ambar-nodes` | `FAILED_PRECONDITION` |
| 5 | Нет места (участников уже `maxPeers + 1`), `nodeId` или адрес узла заняты другим участником | `RESOURCE_EXHAUSTED` |
| 6 | Проход согласования (`Agent::reconcile_one`) отказал | `FAILED_PRECONDITION` |

| 8 | Под блокировкой тома, свежее чтение: объекта нет | `NOT_FOUND` |
| 8 | У узла нет записи в `status.nodes` | `UNAVAILABLE` |
| 8 | Узел не участник свежего объекта | `FAILED_PRECONDITION` |

| 9 | Признак файловой системы, `mkfs`, аннотация: ниже | по таблице ошибок ниже |
| 10 | `mount` завершился ошибкой; путь staging занят другим источником | `FAILED_PRECONDITION` |

Перевод узла в `Primary` выполняет DRBD при открытии устройства
(`auto-promote yes`, шаг 5 протокола).

Признак файловой системы (`Mounter::signature`, `src/mount.rs`). Устройство
открывается только на чтение; `blkid -p -o value -s TYPE <устройство>`
выполняется после собственного чтения:

| Открытие | Магия ext4 по смещению 1080 | Магия резервного суперблока | `blkid` | Результат |
|---|---|---|---|---|
| ошибка открытия или чтения | | | не запускается | ошибка `Open` (`in_use` при `EMEDIUMTYPE`) |
| не блочное устройство | | | не запускается | ошибка `NotABlockDevice` |
| прочитано меньше 2 байт | | | не запускается | ошибка `AmbiguousSignature` |
| | нет | есть | не запускается | ошибка `AmbiguousSignature` |
| | `53 ef` | | код 0, `ext4` | `Ext4` |
| | нет | нет | код 2, stdout и stderr пусты | `Empty` |

| | любое другое сочетание | | | ошибка `AmbiguousSignature` |

Резервные суперблоки проверяются по смещениям для блоков 1, 2 и 4 КиБ (первая
резервная копия), если смещение внутри устройства. Основание (опыт P9,
результаты, раздел «Опыты перед CSI (P7–P10)»): код 2 у `blkid` был и на
устройстве без файловой системы, и на устройстве, открытом на другом узле
(stderr `Wrong medium type`), и для несуществующего устройства (stdout и stderr
пусты), поэтому один код возврата не означает «пусто»; чтение `dd` по смещению
1080 отличает пустое устройство (` 00 00`) от отсутствующего (ошибка
открытия). Поведение `blkid` на устройстве только с таблицей разделов и после
`wipefs` на стенде не проверялось `[проверить: признак на устройстве с GPT без
файловой системы и после wipefs]`.

`mkfs.ext4 -q -E nodiscard <устройство>` выполняется, только если выполнены
все три условия:

1. `Mounter::signature` вернул `Signature::Empty`. Любая ошибка признака,
   `Ext4` и `Other` — без `mkfs`.
2. На объекте нет аннотации `ambar.balookrd.github.io/formatted`. `Empty` при
   аннотации — `FAILED_PRECONDITION` («том форматировался, но файловой системы
   нет»), ничего не выполняется.
3. Устройство открыто и прочитано в этом же вызове, под блокировкой тома, на
   объекте, прочитанном в этом же критическом участке. Между вызовами ничего
   не запоминается.

Непосредственно перед `mkfs` объект читается снова: если его нет, он
удаляется, у него другой `uid` или на нём появилась аннотация, `mkfs` не
выполняется (`UNAVAILABLE`; повтор прочитает `Ext4`). После `mkfs` агент ставит
аннотацию (JSON-патч с проверкой `uid`) и читает её обратно; при ошибке вызов
отвечает ошибкой, повтор читает `Ext4`, ставит аннотацию и монтирует. `Ext4`
без аннотации (сбой между `mkfs` и аннотацией) тоже ставит её. `-E nodiscard`
не отправляет TRIM всего устройства; как `discard` проходит через DRBD и
loop-устройство, не измерялось `[проверить: discard через DRBD поверх
loop-устройства]`. На стенде `mkfs` выполнялся при первом монтировании каждого
тома сквозной проверки, и `blkid` на узле `Client` вернул `ext4` (результаты,
«Проверки CSI на стенде», «Наблюдения при живых томах», пункты 1 и 5).

Ошибки монтирования и их коды:

| Ошибка | Код |
|---|---|
| `Open { in_use: true }` (том открыт на другом узле, `EMEDIUMTYPE`) | `UNAVAILABLE` |
| другие `Open`, `AmbiguousSignature`, `NotABlockDevice`, `Io` | `UNAVAILABLE` |
| `WrongFilesystem`, `Busy`, `StillMounted` | `FAILED_PRECONDITION` |
| `Command` (с stderr) | `FAILED_PRECONDITION` |
| `ModeMismatch` | `ALREADY_EXISTS` |

«Том открыт на другом узле» — повторяемая ошибка: при переезде пода старый
узел ещё держит устройство. На стенде второй под с тем же PVC на другом узле
получал `FailedMount` с `code = Unavailable desc = the volume is open on
another node … Wrong medium type`, kubelet повторял стадию (результаты,
«Повторная проверка CSI после второго раунда исправлений»). Открытие на
другом узле при соединённых сторонах отклоняется ещё и потому, что
`allow-two-primaries no`: `mount` с кодом 32, `Can't open blockdev`, в `dmesg`
`Auto-promote failed: Multiple primaries not allowed by config` (шаг 5). Тот же
`mount` с кодом 32 наблюдался без кворума и без доступа к `UpToDate`-данным
(опыт C1); причина в этих случаях видна только в `dmesg` (`Auto-promote
failed: No quorum (-25)` или `Need access to UpToDate data (-2)`). Чтение через
узел `Client` без доступной копии на стенде не проверялось `[проверить:
открытие и чтение на узле без диска без UpToDate-стороны возвращает ошибку, а
не нули]`.

Флаги монтирования (`mount_flags`) — только из списка: `noatime`,
`nodiratime`, `relatime`, `strictatime`, `lazytime`, `discard`, `nodiscard`,
`ro`, `rw`, `nosuid`, `nodev`, `noexec`, `sync`, `dirsync`, `data=ordered`,
`barrier=1`, `errors=remount-ro` и `commit=<цифры>`. Флаг вне списка —
`INVALID_ARGUMENT`; такие флаги, как `loop`, `journal_dev=` или `offset=`,
меняли бы то, что открывает `mount`, а `barrier=0`, `errors=continue` и
`data=writeback` ослабляют обработку сбоев файловой системы.

Снятие членства после неудачной стадии. Членство `Client` этого узла создаёт
только стадия. После окончательной ошибки стадии kubelet `NodeUnstageVolume`
не вызывает `[проверить: поведение kubelet при окончательной ошибке
NodeStageVolume на стенде не проверялось]`, и членство занимало бы место в
`maxPeers` навсегда. При окончательной ошибке стадии (любой код, кроме
`UNAVAILABLE`, `ABORTED`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED`,
`CANCELLED`) агент под блокировкой тома, на свежем чтении, снимает членство,
если выполнены все три условия:

1. узел — `Client` в `spec.nodes`;
2. путь staging этого вызова не смонтирован;
3. ни одна запись таблицы монтирований не имеет источником
   `/dev/drbd<minor>` (том не смонтирован на узле для другого пода того же
   PVC).

Решение принимается по состоянию, а не по истории вызова: членство,
оставшееся от прежней попытки с повторяемой ошибкой, снимает следующая
попытка с окончательной ошибкой. `Replica` и `Witness` не трогаются. Снятие —
то же, что в `NodeUnstageVolume` (шаги 3–5 ниже); его ошибка пишется в журнал,
вызов возвращает исходную ошибку. После повторяемой ошибки членство остаётся.
Снятие опирается на то, что `drbdadm down` отказывает при открытом устройстве:
на стенде `rc=11`, `State change failed: (-12) Device is held open by someone`,
ресурс остался `Primary` и читаемым (один прогон, «Ручной сценарий: второй под
на узле вне тома»).

`NodePublishVolume`: пустые пути или неверная capability — `INVALID_ARGUMENT`;
объекта нет — `NOT_FOUND`; на пути staging ничего не смонтировано или
смонтировано не `/dev/drbd<minor>` этого тома (minor из свежего чтения объекта)
с `ext4` — `FAILED_PRECONDITION`. Каталог пода создаётся, staging
bind-монтируется в него, только на чтение, если запрос этого требует;
существующее bind-монтирование в другом режиме — `ALREADY_EXISTS`.

`NodeGetInfo` возвращает `node_id` — имя узла, и сегмент топологии
`ambar.balookrd.github.io/node=<имя узла>`. `NodeGetCapabilities` объявляет
`STAGE_UNSTAGE_VOLUME`. Остальные вызовы Node и Controller, кроме описанных,
отвечают `UNIMPLEMENTED`.

### Размонтирование

`NodeUnpublishVolume` снимает bind-монтирование пода и удаляет каталог, если он
пуст; если ничего не смонтировано — `OK`.

`NodeUnstageVolume`, под блокировкой тома, по порядку:

1. Размонтировать путь staging. Ошибка — `FAILED_PRECONDITION`, объект не
   трогается.
2. Прочитать объект. Объекта нет или узел в нём не `Client` (`Replica`,
   `Witness`, не участник): готово, кроме размонтирования ничего не делается.
3. Для `Client`: снять ресурс и удалить локальные файлы
   (`Reconciler::remove_checked`, условие под блокировкой: файла тома нет).
   Отказ `drbdadm down` (устройство ещё открыто) — `FAILED_PRECONDITION`,
   членство остаётся.
4. Удалить запись узла из `status.nodes` (`Agent::clear_entry`, удаление с
   проверкой, как в цикле согласования).
5. Удалить запись `Client` из `spec.nodes` (`membership::leave_as_client`).

Ресурс снимается первым, конфигурация сторон меняется последней: этот порядок
проверен опытом P8 (отключение стороны без диска от работающего ресурса с
писателем, один прогон, запись не прерывалась). DRBD возвращает узел в
`Secondary` при закрытии устройства: на стенде узел `Replica` после удаления
пода был `Secondary` при первой проверке через 1 с, запись `Client` после
удаления пода исчезала при первой проверке, ресурса на узле не оставалось
(`No such resource`), у сторон не оставалось соединения с ним (результаты,
«Проверки CSI на стенде», шаги c, e, f).

Если процесс агента завершился между шагами 3 и 5, цикл согласования видит
`Client` в `spec.nodes` и снова поднимает ресурс; такое членство без пода
остаётся до следующего `NodeUnstageVolume` или до удаления оператором.

Порядок блокировок: сначала блокировка тома внутри процесса (`Agent::locks`)
на шаги 8–10 стадии и на всё `NodeUnstageVolume`, внутри неё
`Reconciler::remove_checked` берёт `flock` файла тома. Ожидание стадии (шаги
6, 7) идёт без блокировки внутри процесса, потому что `Agent::reconcile_one`
берём её сам.

### Смена набора копий

Смена набора копий тома на работающем кластере выполняется утилитой `ambar replica`:
- `ambar replica add <том> <узел>` — добавление копии на узел кластера;
- `ambar replica remove <том> <узел>` — снятие копии с узла кластера;
- `ambar replica move <том> <с узла> <на узел>` — перенос копии с одного узла на другой.

Флаги команд:
- `--namespace <имя>`: пространство имён объекта тома и ConfigMap `ambar-nodes` (переменная `POD_NAMESPACE`, по умолчанию `ambar-system`);
- `--timeout <секунды>`: предел ожидания синхронизации и действий агентов (по умолчанию 0 — без ограничения). При истечении таймаута команда выходит с кодом 1 и сообщением `timed out; run the same command again to continue`, не откатывая уже применённые изменения в объекте тома.

Коды выхода:
- 0: смена набора копий успешно завершена;
- 1: отказ правил валидации, истечение таймаута или ошибка API-сервера.

Команда выполняется в цикле и на каждой итерации перечитывает объект тома, живой список объектов кластера (`list_fresh`) и карту узлов (`ConfigMapNodes::load`), обращаясь к чистым правилам планирования (`src/replicas.rs`). Вывод команды содержит строки `edit: <что изменено>` при каждом изменении объекта, строки ожидания `Wait` (не чаще раза в 30 с при неизменном тексте) и финальную строку `OK: ...`.

Таблица «состояние → следующий шаг» чистых правил (`next_add`, `next_remove`, `next_move`):

| Команда | Текущее состояние объекта | Следующий шаг (`Next`) |
|---|---|---|
| `add` | Узел вне тома, бюджет свободен, проверки R25 пройдены | `Edit`: добавляет узел как `Replica` с финализатором `replica-<узел>` и назначает свидетеля (R27), если N становится чётным |
| `add` | Узел уже `Replica`, но диск ещё не `UpToDate` | `Wait`: ждёт синхронизации диска копии агентом |
| `add` | Узел `Replica`, диск `UpToDate`, N нечётно, свидетель присутствует | `Edit`: убирает свидетеля (если свидетель в `Primary`, переводит его в `Client`, R27) |
| `add` | Узел `Replica`, диск `UpToDate`, правило свидетеля выполнено | `Done`: завершение с кодом 0 |
| `remove` | Узел `Replica`, N > 2, не `Primary`, проверки R25 пройдены | `Edit`: переводит узел в `Retiring` и назначает свидетеля, если остающееся N копий чётно |
| `remove` | Узел в виде `Retiring` (или исчез из `spec.nodes`, но финализатор ещё на объекте) | `Wait`: ждёт завершения снятия копии агентом узла |
| `remove` | Узел и его финализатор отсутствуют, N нечётно и есть лишний свидетель | `Edit`: убирает свидетеля |
| `remove` | Узел и его финализатор отсутствуют, N чётно и свидетеля нет | `Edit`: назначает свидетеля из доступных кандидатов |
| `remove` | Узел и его финализатор отсутствуют, правило свидетеля выполнено | `Done`: завершение с кодом 0 |
| `move` | Целевой узел вне тома, исходный не `Primary`, проверки R25 пройдены | `Edit`: добавляет целевой узел как `Replica` с финализатором (свидетель не меняется, R24) |
| `move` | Целевой узел `Replica`, но ещё не `UpToDate` | `Wait`: ждёт завершения начальной синхронизации новой копии |
| `move` | Целевой узел `Replica` со статусом `UpToDate`, исходный узел — `Replica` | `Edit`: переводит исходный узел в `Retiring` |
| `move` | Исходный узел в виде `Retiring` (или исчез, но финализатор есть) | `Wait`: ждёт завершения снятия исходной копии |
| `move` | Исходный узел и финализатор ушли, целевой узел — `Replica` и `UpToDate` | `Done`: завершение с кодом 0 |

Снятие копии агентом узла (`RetireReplica`, R19, R26):
1. Агент узла видит свою запись в виде `Retiring` на объекте тома без `deletionTimestamp`.
2. Выполняются проверки сторон (R18) или доказательство отсутствия данных (`prove_no_data`).
3. Под блокировкой тома агент останавливает ресурс (`drbdadm down`), отключает loop-устройство, удаляет файлы тома (`<том>.img`, маркеры `.img.ready`, `.img.synced`, ссылку `/dev/ambar/<том>`, файл ресурса `<том>.res`).
4. Снимает локальный финализатор `ambar.balookrd.github.io/replica-<узел>`.
5. JSON-патчем удаляет запись своего узла из `spec.nodes`.
6. На время нахождения узла в виде `Retiring` вызов `NodeStageVolume` на этом узле отклоняется с кодом `UNAVAILABLE` (R30).

Смена роли стороны на узле (R28):
Если узел был участником тома без диска (`Witness` или `Client`), при получении статуса `Replica` цикл согласования агента не может создать метаданные поверх работающего ресурса. Агент переводит ресурс в `down`, создаёт файл тома и метаданные `create-md`, после чего поднимает ресурс как полноправную копию.

Освобождение слотов битовой карты (`forget-peer`, R29):
Агент не выполняет `drbdadm forget-peer` при снятии копии. По опыту P13 (`2026-11-12-drbd9-spike-results.md`), `forget-peer` сбрасывает слот битовой карты, но требует остановки и полного пересчёта битовых карт всех пиров. Ресурсу тома хватает слотов битовой карты, пока общее число подключавшихся узлов с разными `nodeId` за всё время жизни тома не превышает `maxPeers + 1` (по умолчанию 8).

### Удаление (`DeleteVolume`)

`DeleteVolume` удаляет объект `ReplicatedVolume` и ждёт до 60 с, пока он
исчезнет. Пустой `volume_id` — `INVALID_ARGUMENT`; идентификатор, который не
проходит правило имени тома, и отсутствующий объект — `OK`; для объекта, который
уже удаляется, второй запрос на удаление не отправляется. Не исчез за 60 с —
`DEADLINE_EXCEEDED`, `external-provisioner` повторяет вызов. Объект исчезает,
когда агенты всех `Replica` сняли свои финализаторы (R9).

Что делает агент узла с объектом, у которого стоит `deletionTimestamp`
(`agent::decide::decide`, первая подходящая строка):

| Узел в объекте | Финализатор узла | На узле | Решение |
|---|---|---|---|
| указан в `spec.nodes` дважды | | | отказ `InvalidSpec` |
| `Replica` | есть | файл тома или следы | `DeleteReplica` |
| `Replica` | есть | ничего | `DropFinalizer` |
| `Replica` | нет | файл тома | отказ `DeletingWithoutFinalizer`, копия остаётся |
| `Replica` | нет | следы без файла | `CleanDiskless` |
| `Witness`, `Client`, не участник | | файл тома | отказ `ImageWithoutMembership` |
| `Witness`, `Client`, не участник | есть (лишний финализатор) | ничего | `DropFinalizer` |
| `Witness`, `Client`, не участник | | следы без файла | `CleanDiskless`; лишний финализатор снимается в следующем проходе |

Следы — файлы, которые пишет `ambar`: `<том>.res`, `<том>.res.applied`, ссылка
`/dev/ambar/<том>`. Ресурс, который есть только в ядре, без `<том>.res`, следом
не считается и не трогается (`agent::local`).

Копия удаляется только через `Reconciler::remove_checked`, который берёт
`flock` тома и под ним вызывает проверку. Пути к удалению (`src/agent/run.rs`):

| Путь | Задача | До блокировки | Под блокировкой |
|---|---|---|---|
| проверки сторон | `DeleteReplica`, `RetireReplica`, ресурс настроен в ядре | статус DRBD прочитан; правила проверок сторон на объекте, прочитанном в начале прохода | статус DRBD прочитан снова, правила проверок сторон |
| нет данных | `DeleteReplica`, `RetireReplica`, ресурс не настроен, и `prove_no_data` показал, что данных на узле нет | ресурс не настроен; `prove_no_data` | статус прочитан снова, ресурс не настроен; `prove_no_data` снова; затем `Reconciler::remove_unconfigured` ещё раз читает статус и отказывает, если ресурс появился |
| остатки узла без диска | `CleanDiskless` | ничего | файла тома нет |

При `RetireReplica` после успешного выполнения `remove_checked` агент узла
снимает свой финализатор `replica-<узел>` и JSON-патчем удаляет свою запись из
`spec.nodes`.

`DeleteReplica` по тому, что есть на узле (первая подходящая строка; состояние
без подходящей строки, ведущей к удалению, оставляет копию):

| Ресурс в ядре | Файл тома | Другие факты | Действие |
|---|---|---|---|
| настроен | любое состояние | | проверки сторон: диск держит DRBD, состояние файла не важно |
| не настроен | есть маркер `.img.ready` | | подъём: `Reconciler::apply` с описанием объекта и `initialSync: Done`, запись статуса, повтор через 1 с; ничего не удаляется. Описание не строится или `apply` не прошёл — копия остаётся, ошибка в `message`, повтор через 30 с |
| не настроен | нет | ни одно loop-устройство не держит путь файла | нет данных: удаление без проверок сторон |
| не настроен | нет | loop-устройство держит удалённый файл | копия остаётся: «the backing file is gone but a loop device still holds it» |
| не настроен | нет маркера `.img.ready` | маркера `.img.synced` нет, ссылка `/dev/ambar/<том>` указывает на loop-устройство, которое `backing::loop_holders` относит к файлу тома под живым путём (не `(deleted)`), и `dump-md` даёт `Absent` или `Fresh` | нет данных: удаление без проверок сторон |
| не настроен | нет маркера `.img.ready` | маркер `.img.synced` есть, ссылки нет или она указывает на другое устройство или на устройство удалённого файла, метаданные `Used`, или проверка не удалась | копия остаётся, причина в `message`; решение за оператором |

Каждый факт «нет данных» читается, а не предполагается. Путь, который нельзя
проверить, отказ `losetup` или `dump-md`, строка `losetup --list`, которая не
является устройством с файлом или чей файл кончается на `*` (util-linux
обрезает длинные имена), и нечитаемый статус означают «не доказано»: копия
остаётся.

Проверки сторон. Копия удаляется, только если выполнено всё:

1. локальный статус DRBD прочитан без ошибки;
2. этот узел не `Primary`;
3. для каждого другого узла `spec.nodes` любого вида: (а) в локальном статусе
   есть соединение с ним в состоянии `Connected` с `peer-role` `Secondary`, или
   (б) в `status.nodes` объекта, прочитанного в начале прохода, нет его записи.
   Узел удаляет свою запись, когда убрал копию или остатки, а узел, который ни
   разу не сообщил статус, тома не поднимал.

Несоединённый узел с записью блокирует удаление при любой роли в записи.
Соединение с `peer-role` `Primary` блокирует удаление в любом состоянии
соединения. Если правило не выполнено, копия остаётся, причина пишется в
`message` записи узла, проход повторяется через 5 с, если причина — состояние
DRBD (этот узел `Primary`, сторона `Primary`, сторона не соединена), и через
30 с в остальных случаях, а также сразу при изменении объекта. На стенде объект,
удалённый при работающем поде, исчез через 5 с после удаления пода, а при
обычном порядке (под, затем PVC) — через 2–3 с после удаления PVC (результаты,
«Повторная проверка CSI после второго раунда исправлений», «Удаление тома под,
работавшего до удаления»; «Проверки CSI на стенде», шаг j).

Подъём копии с маркером `.img.ready`. После перезагрузки ресурс удаляемого тома
не настроен: узел не видит сторон, стороны видят его несоединённым с записью в
`status.nodes`, и каждый ждёт другого. С поднятым ресурсом стороны видят узел
`Connected` и `Secondary`. `apply` готового файла планирует подключение
loop-устройства, ссылку, файл ресурса, `up` или `adjust`; `create-md` он не
планирует, а `new-current-uuid` отключён `initialSync: Done`. Через цикл
согласования после настоящей перезагрузки на стенде не проверялось
`[проверить: подъём копии удаляемого тома после перезагрузки узла]`.

Сопоставление loop-устройств с файлом тома (`backing::loop_holders`) читает
весь `losetup --list`: `losetup -j <путь>` ищет файл по пути и ничего не
находит для удалённого файла, а `losetup --list` показывает устройство с
`<путь> (deleted)` (результаты, «Проверки агента на стенде»). Строка относится
к файлу, если `BACK-FILE` без ` (deleted)` — путь файла как задан, путь с
разрешённым родительским каталогом или ровно `/<имя файла>`. Третья форма
появляется после замены пода агента: ядро строит путь от монтирования каталога
томов в старом поде, которое после выхода пода отсоединено (результаты,
«Путь файла в списке loop-устройств после замены пода агента»; механизм
`[проверить: не перепроверялось]`). Совпадение только по имени без `(deleted)`
при существующем файле подтверждается по inode (`losetup -j`); если файла нет
или строка помечена `(deleted)`, устройство считается держащим файл тома: это
сторона, при которой копия остаётся.

Запись узла в `status.nodes` удаляется через `Agent::clear_entry`: пустой
server-side apply, чтение объекта и, если запись осталась (ей совместно владеет
другой менеджер полей), JSON-патч подресурса `status` с проверками `uid` и
имени записи. Пока запись не удалена, проход возвращает `Kept`, финализатор
узла остаётся. Финализатор снимается только после успешного
`remove_checked` или (`DropFinalizer`), когда на узле ничего не осталось. Правки
объекта (финализатор, `initialSync`, `spec.nodes`, аннотация) — JSON-патчи с
`test` значения `/metadata/uid` того объекта, который видел проход.

**Внимание.** Запись в `status.nodes` вручную правится только JSON-патчем
подресурса `status` (`kubectl patch rv <том> --subresource=status --type=json`).
Merge-патч заменяет список целиком и удаляет записи других узлов `[проверить:
поведение merge-патча на списке с ключом name в CRD не записано в протоколе]`.
На удаляемом объекте стороны читают отсутствие записи как «узел убрал копию»
(правило 3б), и удаление копий начнётся, хотя узел, чью запись стёрли, может
держать том открытым. Увидеть это можно по `kubectl get rv <том> -o json`: в
`status.nodes` не хватает записей участников. Агенты живых узлов пишут свои
записи заново в следующем проходе (испорченное поле `message` агент вернул при
первой проверке, результаты, «Проверки CSI на стенде», шаг h); копии, удалённые
до этого, не восстанавливаются.

Узел, умерший навсегда, держит свою запись и блокирует удаление копий
остальных узлов. Выход ручной:

1. Убедитесь, что том никто не использует: ни один под не смонтировал его, у
   записей остальных узлов `role: Secondary`.
2. Удалите запись умершего узла из `status.nodes`, где `<номер>` — индекс
   записи в списке:

   ```bash
   kubectl patch rv <том> --subresource=status --type=json \
     -p '[{"op":"remove","path":"/status/nodes/<номер>"}]'
   ```

3. Удалите финализатор `ambar.balookrd.github.io/replica-<узел>` умершего узла
   из `metadata.finalizers` тем же способом (`--type=json`, без
   `--subresource`).

Остальные узлы после этого удаляют копии. Живой перезапущенный узел этого не
требует: он поднимает ресурс сам (подъём выше). На стенде при остановленном
агенте `dv-2` на объекте остался финализатор `replica-lima-dv-2`, остальные
узлы сняли свои; после ручного снятия финализатора вернувшийся агент отказал
`OrphanImage`, файл тома остался, его удалил `ambar remove` (результаты,
«Проверки CSI на стенде», шаг k).

Команда `ambar remove` (CLI) вызывает `Reconciler::remove` без проверок: это
решение оператора.

Если loop-устройство держит старый inode удалённого и заново созданного файла
тома, при существующем файле оно не находится (поиск идёт через `losetup -j`) и
не отключается.

### Старт агента после перезагрузки узла

После перезагрузки в ядре ресурсов нет. Агент проходит по всем объектам
`ReplicatedVolume` (первый список) и по локальным остаткам: для участника тома
проход подключает loop-устройство, выполняет `drbdadm up` для ресурса, которого
в ядре нет, и `drbdadm adjust` для настроенного. Пока каждое имя первого списка
не прошло один проход без ошибки API (или не завершилось ошибкой API трижды),
`NodeStageVolume` отвечает `UNAVAILABLE`. DRBD досылает блоки, изменённые за
время отсутствия узла, по битовой карте.

Проверка CLI фазы 1 `stand/agent-smoke.sh --reboot`, один узел (`dv-2`): после
`limactl stop --force dv-2` и запуска узла `ambar load-module` напечатал
`loaded drbd 9.3.4 …`, `ambar apply` напечатал `[AttachLoop, LinkDevice, Up,
MarkApplied]`, диск перешёл в `UpToDate` (результаты, раздел «Проверки агента
на стенде»). Перезагрузка узла с работающим агентом фазы 2а на стенде не
выполнялась `[проверить: подъём томов агентом после перезагрузки узла]`.
Перезапуск подов агента без перезагрузки (`rollout restart ds/ambar`) под
писателем не прервал запись, `restartCount` пода 0 (результаты, «Проверки CSI
на стенде», шаг h).

### Добавление узла в кластер

Узел, появившийся в кластере после создания томов, подключается к тому как
`Client`, когда на него назначен под с этим томом.

1. Добавьте запись узла (имя, адрес на `lan0`, постоянный `nodeId`,
   `capacityBytes`) в `ConfigMap ambar-nodes`. Перезапуск агентов не нужен:
   карта читается при каждом обращении.
2. Убедитесь, что на узле есть каталоги `/var/lib/rancher/ambar/volumes` и
   `/var/lib/rancher/ambar/res`: без них под агента не запустится (`hostPath`
   с `type: Directory`). DaemonSet запускает агент на узле.
3. Проверка: `kubectl -n ambar-system get pods -o wide` показывает под агента
   на узле в состоянии `Running`.

Когда под с томом назначен на узел, `NodeStageVolume` дописывает узел в
`spec.nodes` с `kind: Client`. Агенты остальных участников обновляют файл
ресурса и выполняют `drbdadm adjust`, агент нового узла поднимает ресурс с
`disk none`. На стенде четвёртая ВМ `dv-4` присоединена к k3s и к
`ambar-nodes` (`nodeId` 3), под на узле вне тома получил запись `Client`,
смонтировал том и прочитал данные (результаты, «Проверки CSI на стенде»,
«Четвёртая ВМ», шаг e). Без агентов, опыт P5 (один прогон, результаты, раздел
«Опыты перед агентом (P1–P6)»): после обновления файла ресурса `drbdadm adjust`
на двух работающих узлах и `drbdadm up` на новом соединили все три стороны
(`Connected`); в выборках счётчика через ~0.5 с запись на `Primary` росла и
ошибок не было; строк `quorum(` на узлах с копией при добавлении стороны не
появилось, отчёт о кворуме — `quorum:yes`; как добавление стороны меняет расчёт
кворума, не изучалось `[проверить: расчёт кворума при добавлении стороны]`.
Агенты выполняют `adjust` на каждом участнике; хватило бы `adjust` только на
части узлов, не проверялось `[проверить: adjust только на части узлов]`.

Узел подключается к тому, только пока участников не больше `maxPeers + 1`;
иначе `NodeStageVolume` отвечает `RESOURCE_EXHAUSTED`. При создании тома
`maxPeers` не меньше числа узлов в карте минус один, поэтому место есть у
каждого узла, который был в карте при создании тома. Узлу, добавленному позже,
места может не хватить: метаданные рассчитаны на число сторон, заданное при
`create-md`, и добавление стороны сверх запаса без пересоздания метаданных не
проверялось `[проверить: можно ли добавить сторону без пересоздания
метаданных]`.

## Параметры ресурса DRBD

| Параметр | Значение | Что делает | Когда менять |
|---|---|---|---|
| `protocol` | из StorageClass | Момент подтверждения записи | Задаётся при создании тома |
| `quorum` | `majority` | Узел принимает запись, только пока видит большинство сторон ресурса | Не менять |
| `on-no-quorum` | `io-error` | Без кворума `fsync` возвращает `EIO` (буферизованная запись без `fsync` при этом проходила); журнал ext4 прерывается (`Aborting journal`). При `Errors behavior: Continue` точка монтирования остаётся `rw` (`findmnt`), новые записи получают `Read-only file system` или `Input/output error` | Не менять. Строка обязательна в `.res`: значение по умолчанию в 9.3.4 — `suspend-io` |
| `auto-promote` | `yes` | Роль `Primary` берётся при открытии устройства | Не менять |
| `allow-two-primaries` | `no` | При соединённых сторонах второй узел не может открыть устройство. При разрыве связи `Primary` могут оказаться два узла одновременно (опыт E1: `dv-1` с `quorum:no` и `dv-2` с `quorum:yes`, оба `open:yes`); запись на изолированном узле останавливают только `quorum majority` и `on-no-quorum io-error` | Не менять |
| метаданные | `internal` | Метаданные DRBD лежат в конце файла тома | Не менять |

Выбор `io-error` против `suspend-io` проверен на стенде (DRBD 9.3.4, по одному
прогону). С `suspend-io` процесс на изолированном узле висит в `fsync` в
состоянии `D` до возврата сети, `SIGKILL` его не снимает, `umount` возвращает
`target is busy`, устройство остаётся открытым и узел остаётся `Primary` до
возврата сети. С `io-error` писатель получает `EIO` через 10–11 с после
изоляции, после чего `umount` проходит и узел уходит в `Secondary`.

Состояние соединений после возврата сети зависит не от политики, а от роли
изолированного узла в этот момент. Узел в `Secondary` соединился сам. Узел,
оставшийся `Primary` (при `suspend-io` всегда, при `io-error` — если том ещё
смонтирован), пишет в `dmesg` сам `I shall become SyncTarget, but I am primary!`,
и его соединения переходят в `StandAlone`; после размонтирования они сами не
восстанавливаются. Условие: к моменту возврата сети другой узел стал `Primary`
и писал на том (на стенде `dv-2`, опыт E1 и шаг 7). В шаге 7 в `StandAlone`
перешла одна связь из двух (`dv-1`↔`dv-3`), в опыте E1 обе. Их восстановил
`drbdadm adjust <имя>`: в E1 на `dv-1`, `dv-2`, `dv-3` после размонтирования
на `dv-1`, в шаге 7 на `dv-1` и `dv-3` — на обеих сторонах связи; `adjust`
только на вернувшемся узле оставил соединения в `StandAlone`. `adjust` на
трёх узлах при смонтированном томе и роли `Primary` вернул `rc=0`, связи снова
перешли в `StandAlone` с тем же сообщением (опыт C2, прогон 2, один прогон);
после `umount` на узле `adjust` на трёх узлах соединил всех за ~2 с. Если
другие узлы за время изоляции на том не писали, связи изолированного
`Primary` восстановились сами без `adjust` (опыт C2, прогон 1, один прогон).

Без кворума запись на узле получает `EIO`, том остаётся смонтированным до возврата связи. Остальные узлы видят узел как `NotReady`; по истечении `tolerationSeconds` Kubernetes создаёт замену пода, узел с кворумом открывает том. После возврата связи агент освобождает том и переподключает ресурс. Полная изоляция узла на стенде не запускалась (изоляция закрывала TCP 7000) [проверить: поведение при полной изоляции] | `kubectl get nodes`: `NotReady` |
| NVMe переполнен | Запись в файл тома возвращает ошибку, DRBD отключает локальный диск и работает через остальные копии [проверить: не проверялось на стенде; `on-io-error` по умолчанию в 9.3.4; поведение DRBD и ext4 при `ENOSPC` в файле тома, опыт на стенде в фазе 3] | `disk: Diskless` на узле с копией |

### Освобождение тома при потере кворума

Дизайн фазы 3, в коде нет.

Без кворума `on-no-quorum io-error` возвращает `EIO` на `fsync` через 10–11 с
после изоляции, но точка монтирования остаётся, устройство открыто, узел
остаётся `Primary` (шаг 6, опыт E1). Изоляция на стенде закрывала только
TCP 7000: kubelet и API оставались доступны, и под никто не трогал. Узел,
оставшийся `Primary` к возврату сети, переходит в `StandAlone`, если другой
узел за это время писал на том.

Порядок, который выполняет агент узла:

1. Агент читает `devices[].quorum` из `drbdsetup status --json` для томов,
   смонтированных на узле.
2. Если кворума нет дольше grace period (по умолчанию 30 с, параметр агента), агент удаляет через API поды на своём узле, которые используют этот том.
3. Агент ставит на свой узел taint `ambar.balookrd.github.io/no-quorum` с эффектом `NoSchedule`, пока узел не видит другие узлы по сети репликации. Запущенные поды остаются на узле. Новые поды на узел не планируются, в том числе поды без томов `ambar`; манифесты сервисов менять не нужно. Момент установки относительно grace period: «Открытые вопросы».
4. kubelet размонтирует том, DRBD переводит узел в `Secondary`. При
   исправном томе после удаления пода так и было: узел `Replica` стал
   `Secondary` при первой проверке через 1 с (результаты, «Проверки CSI на
   стенде», шаг c). Размонтирование kubelet у тома без кворума после `EIO`
   на стенде не проверялось, в опытах E1 и C2 `umount` выполнялся вручную
   `[проверить: размонтирование kubelet у тома без кворума]`
5. Контроллер пода (Deployment, StatefulSet) создаёт под на узле, где есть
   кворум.
6. После восстановления связи с другими узлами по сети репликации агент снимает taint. Условие снятия, если кворум вернулся не у всех томов узла: «Открытые вопросы».

Решение освобождать том подкреплено двумя записанными наблюдениями (опыт C2,
по одному прогону на случай):

- Другие узлы за время изоляции писали на том. `adjust` при ещё
  смонтированном томе и роли `Primary` вернул `rc=0`, связи снова ушли в
  `StandAlone` (`I shall become SyncTarget, but I am primary!`); после `umount`
  узел стал `Secondary`, `adjust` на трёх узлах соединил всех за ~2 с.
- Другие узлы на том не писали. Связи вернулись сами за ~2 с после снятия
  изоляции, но ext4 на изолированном узле осталась с прерванным журналом
  (`Detected aborted journal`) и возвращала `EIO` на запись и чтение, пока не
  выполнены `umount` и `mount`; после повторного `mount` ядро пишет `mounting
  fs with errors, running e2fsck is recommended`.

Если с изолированного узла недоступен API server, агент не может ни удалить под, ни поставить taint. Он ждёт возврата API и ничего не делает локально с подом и монтированием. Остальные узлы видят узел как `NotReady`; Kubernetes создаёт замену пода по истечении `tolerationSeconds`, узел с кворумом открывает том (шаг 6: `dv-2` смонтировал том, пока `dv-1` был изолирован). После возврата связи агент освобождает том (шаги 2–4) и переподключает ресурс, см. «StandAlone и split-brain».

Grace period и параметры `adjust` описаны в «Параметры агента», права на удаление подов и изменение узлов — в «Права агента (RBAC)».

### StandAlone и split-brain

Действия агента в этом разделе — дизайн фазы 3, в коде их нет. Наблюдения
на стенде записаны в протоколе.

`StandAlone` на стенде наблюдался в четырёх ситуациях
(`2026-11-12-drbd9-spike-results.md`). Настоящий split-brain получен один раз,
при `quorum off` (опыт C3); в проектной конфигурации (`quorum majority`) он не
получен и не проверялся.

| Ситуация | Что в `StandAlone` | Сообщение ядра | Что сняло |
|---|---|---|---|
| Шаг 7: `suspend-io`, узел `Primary` при возврате сети, другой узел писал | одна связь из двух (`dv-1`↔`dv-3`) | `Split-Brain detected` в `dmesg` нет | `drbdadm adjust` на обеих сторонах связи, данные не отбрасывались |
| Опыт E1: `io-error`, том не размонтирован до возврата сети, другой узел писал | обе связи `dv-1` | `I shall become SyncTarget, but I am primary!` | размонтирование и `drbdadm adjust` на трёх узлах, данные не отбрасывались |
| Опыт C2, прогон 2: то же, `adjust` сначала при смонтированном томе | обе связи `dv-1`, затем снова после `adjust` | `I shall become SyncTarget, but I am primary!` | `adjust` при смонтированном томе не помог; после `umount` `adjust` на трёх узлах соединил всех за ~2 с |
| Опыт C3: `quorum off`, обе стороны писали при изоляции, обе `Secondary` | обе связи жертвы `dv-1` и связи выживших с ней | `uuid_compare()=split-brain-auto-recover by rule=bitmap-both`, `Split-Brain detected but unresolved, dropping connection!` | на жертве `disconnect` и `connect --discard-my-data`, на двух других узлах `connect`; данные жертвы отброшены |

Агент каждого узла выполняет `drbdadm adjust <имя>` для ресурса, у которого
есть соединение в `StandAlone`, пока локальная роль узла — `Secondary`. На узле
в роли `Primary` (том смонтирован) агент `adjust` не вызывает: он выполняется
после освобождения тома. На стенде `adjust` потребовался на обеих сторонах
связи: в опыте E1 на трёх узлах, в шаге 7 на `dv-1` и `dv-3`; `adjust` только
на вернувшемся узле оставил соединения в `StandAlone`. Результат `adjust`
агент читает по `connection-state`, не по коду возврата (см. «Утилиты DRBD»).

Split-brain агент определяет по отказу `adjust`, журнал ядра не читает. Если соединение остаётся `StandAlone` после нескольких попыток `adjust`, пока том освобождён (локальная роль `Secondary`), агент выставляет метрику `ambar_volume_manual_check_needed` и прекращает попытки. Число попыток и интервал между ними — параметры агента, значения по умолчанию: «Открытые вопросы». Причину человек находит в `dmesg` на узлах; сообщения ядра, которыми различаются случаи, перечислены в таблице выше. Метрика не отличает split-brain от других причин, по которым `adjust` не снимает `StandAlone`.

Что записано о различении случаев (опыты E1 и C3, по одному прогону):

- В `drbdsetup status --json` нет поля, которым `StandAlone` после split-brain
  отличался бы от `StandAlone` из E1; набор ключей совпадает, различаются роль,
  `open`, `quorum` и счётчики.
- В захвате `events2` опыта C3 есть только `connection:Disconnecting` →
  `StandAlone`, отличающего признака нет; `events2` для E1 не снимался.
- Различие записано только в тексте сообщения ядра (см. таблицу).
- Гипотеза, не проверенная как признак: при split-brain у сторон разные
  текущие UUID при общем UUID битовой карты, в E1 текущий UUID одной стороны
  стоял в истории другой. `drbdadm get-gi` снимался только после C3
  `[проверить: годится ли сравнение UUID как признак split-brain]`.

### Разрешение split-brain вручную

Условие: метрика `ambar_volume_manual_check_needed` равна `1` (метрика — дизайн фазы 3; до неё условие — соединение, которое остаётся `StandAlone` после размонтирования тома и `drbdadm adjust` на обеих сторонах связи). Человек смотрит `dmesg` на узлах ресурса (в C3 — `Split-Brain detected but unresolved, dropping connection!`) и выбирает копию, которую нужно отбросить.

**Внимание.** `connect --discard-my-data` отбрасывает на выбранном узле все записи, которых нет на остальных узлах. В C3 потеряны записи 897–15875, подтверждённые писателем на выбранном узле после изоляции. Узел для отбрасывания выбирает человек, агент этого не проверяет.

Процедура, выполненная в C3:

```bash
# on the node whose data is discarded, inside the agent container
drbdadm disconnect <имя>
drbdadm connect --discard-my-data <имя>
# on every other node whose connection to it is StandAlone
drbdadm connect <имя>
```

В C3 одна пара команд на жертве оставила `dv-2` и `dv-3` в `StandAlone`
(~20 с, вывод проверки не записан); связь поднялась после `connect` на двух
других узлах. Потеряны записи 897–15875, подтверждённые писателем на жертве
после изоляции; это следствие `quorum off`.

### Принудительное повышение вручную

Случай: узел с новейшей копией потерян безвозвратно, оставшиеся устаревшая копия и узел без диска кворума не получают (`replicas: 2`, опыт C1: `1 of 2 nodes visible, need 2 for quorum`), `mount` и `drbdadm primary` отклонены. Если узел с новейшей копией вернётся, `--force` не нужен: кворум восстанавливается (`Restored quorum from before reboot`), split-brain в C1 не возник. Агент `drbdadm primary --force` не вызывает.

**Внимание.** Устаревшая копия после перезапуска показывает свой диск как `UpToDate` (опыт C1), поэтому состояние диска не говорит, актуальны ли данные. Принудительное повышение копии, которая старше потерянной, теряет все записи, сделанные после её последней синхронизации, в том числе записи, подтверждённые приложению. Агент условие не проверяет. ## Ограничения

- Время переезда пода с упавшего узла определяет Kubernetes: под выселяется
  через `tolerationSeconds` (по умолчанию 300 с). Поды с томами `ambar`
  задают меньшее значение для `node.kubernetes.io/unreachable` и
  `node.kubernetes.io/not-ready`.
- Deployment с томом `ambar` использует стратегию `Recreate`. При
  `RollingUpdate` с `maxSurge` новый под на другом узле не откроет том, пока
  жив старый: `NodeStageVolume` отвечает `UNAVAILABLE` («том открыт на другом
  узле»), пока старый под не уйдёт.
- Под StatefulSet на недоступном узле Kubernetes не пересоздаёт без
  принудительного удаления. Автоматическое принудительное удаление драйвер не
  выполняет.
- `replicas` не меньше 2; тома без репликации остаются на `local-path`.
- `drbdadm primary --force` выполняет только человек; потеря узла с новейшей копией при `replicas: 2` требует ручной процедуры.
- Узел подключается к тому, только пока участников не больше `maxPeers + 1`; добавление стороны сверх запаса метаданных без их пересоздания не проверялось `[проверить: возможно ли без пересоздания метаданных]`.
- Пока в кластере три узла, подключение по требованию не срабатывает: при `replicas: 3` все узлы — `Replica`, при `replicas: 2` третий — `Witness`.
- Сопоставление loop-устройств с файлом тома после замены пода агента опирается на то, что под монтирует ровно каталог томов (`hostPath` `/var/lib/rancher/ambar/volumes` в тот же путь): тогда `BACK-FILE` имеет вид `/<том>.img`. Если смонтировать родительский каталог, путь будет другим, и новый агент не найдёт loop-устройства своих томов.
- Длительность `create-md` на больших томах не измерялась; тайм-аут — 120 с плюс 1 с на ГиБ.
- При смене лидера `external-provisioner` запрос `CreateVolume` может выполняться в двух экземплярах Controller одновременно; мьютекс `placing` действует в одном процессе, совпадение индекса разрешает правило отзыва (см. «Создание (`CreateVolume`)»).
- Под каждую новую версию ядра нужен образ агента с модулем под неё. Порядок
  обновления узла: выкатить образ с новым модулем, затем `apt full-upgrade` и
  перезагрузка. При обратном порядке агент на узле завершится с ошибкой
  `no drbd module for kernel`, тома на узле не поднимутся, два других узла
  продолжат работу.
- В первую версию не входят: снапшоты, расширение тома, бэкап на NAS, тома
  `ReadWriteMany`, шифрование.

Ограничения дизайна фазы 3 (в коде этих механизмов нет):

- Агент удаляет поды только на своём узле при потере кворума; под без
  контроллера (Deployment, StatefulSet), удалённый агентом, не пересоздаётся.
- Если с изолированного узла недоступен API server, агент ждёт его возврата и ничего не делает с подом и монтированием: том остаётся смонтированным на изолированном узле, замена пода появляется на другом узле после `tolerationSeconds`.
- Taint `ambar.balookrd.github.io/no-quorum` с эффектом `NoSchedule` действует на все новые поды узла, а не только на поды с томами `ambar`.

  индекса; `NodeStageVolume` и остальные вызовы Node на подделках, в том числе
  условия `mkfs` и снятие членства.
- Признак файловой системы, разбор `mountinfo`, монтирование и размонтирование
  (часть тестов только под Linux: `docker run --rm -v "$PWD":/src -w /src
  rust:1-slim cargo test --locked`).
- Тайм-аут команд и группа процессов (`exec`), сопоставление loop-устройств
  (`backing::loop_holders`).
- Выбор каталога модуля по версии ядра и отказ при загруженном модуле 8.4
  (`image/test-loader.sh`).

Тестов для механизмов фазы 3 (освобождение тома, taint, `adjust` при
`StandAlone`, метрики) нет.

### Стенд

Четыре ВМ Debian trixie arm64 на маке с k3s (`dv-1`..`dv-3` — server,
`dv-4` — agent, см. `stand/README.md`). ВМ ставят тот же пакет ядра
`linux-image-6.12.116+deb13-arm64`, что и узлы, поэтому на стенде загружается
тот же `drbd.ko`. Драйвер ставит `stand/install.sh`, сквозную проверку
выполняет `stand/csi-e2e.sh` (шаги a–k, результаты, «Проверки CSI на стенде» и
«Повторная проверка CSI после второго раунда исправлений»).

Писатель-проба: под, который в цикле дописывает запись в файл, вызывает
`fsync` и после успешного `fsync` отправляет номер записи наружу (в журнал
вне тома). После каждого сценария все номера из журнала должны быть в файле.

### Замер на R5C перед вводом

Методика та же, что в замере Longhorn 2026-11-09: пять томов по 1 ГиБ с
писателем раз в 10 с.

| Показатель | Цель | Для сравнения |
|---|---|---|
| RSS подов `ambar` на узел | не больше 64 МиБ | Longhorn 145–348 МиБ |
| Прирост памяти `k3s server` | не больше 50 МиБ | Longhorn 180–450 МиБ |
| `fsync` 4 КиБ, `protocol: C` | не больше 5 мс | `local-path` 1.8 мс, Longhorn 13.6 мс |

Если цель по `fsync` не достигнута, отдельно замеряется вклад loop-устройства
(том без остальных копий) и вклад сети.

## Что проверяется первым

Пункты, от которых зависит остальная реализация; каждый закрывается на стенде
до написания CSI-части:

1. Модуль 9.3.4 загружается на ядре `6.12.116+deb13-arm64` с
   `usermode_helper=disabled`.
2. Ресурс из трёх сторон поверх loop-устройств с `--direct-io=on` поднимается
   и синхронизируется.
3. Пропуск начальной синхронизации через `new-current-uuid --clear-bitmap`.
4. Сторона без диска при `replicas: 2` может открыть устройство на запись и
   сохраняет кворум, который у неё уже был, при пропадании узла с копией.
5. Поведение `on-no-quorum io-error` против `suspend-io` для ext4 и kubelet
   (для kubelet не проверено: все проверки использовали `mount` на хосте).
6. `drbdadm` и `drbdsetup` работают из контейнера без установки на хост.

Результаты проверки на стенде: `2026-11-12-drbd9-spike-results.md`.
