# duovol: реплицируемые тома PVC для k3s поверх DRBD 9

Спека описывает CSI-драйвер `duovol`: что он делает, из чего состоит и как ведёт
себя при отказах узлов. Документ адресован тому, кто будет писать план
реализации и код. Дата: 2026-11-12.

## Окружение и требования

| Что | Значение |
|---|---|
| Кластер | k3s, сейчас три узла `k3s-1..3`, все три — server с etcd |
| Железо узла | NanoPi R5C: RK3568B2, 4 ГБ RAM, NVMe 128 ГБ |
| ОС и ядро | Debian 13 trixie, штатное ядро `6.12.116+deb13-arm64` |
| NVMe | один раздел ext4 `LABEL=k3s-data`, смонтирован в `/var/lib/rancher` |
| Сеть репликации | интерконнект `lan0`, `192.0.2.51–53/24`, 2.5GbE |
| Существующие StorageClass | `local-path` (том привязан к узлу), `nfs-client` (NAS `<nas_host>`) |

Требования владельца:

- Число копий тома задаёт параметр `replicas: N`: N копий лежат на N узлах.
- В исправном состоянии запись подтверждается приложению после того, как она
  легла на диски всех N узлов с копией (`protocol: C`). После отказа k узлов с
  копией остаётся N−k копий; при `replicas: 2` после отказа одного такого узла
  запись идёт на один диск (`2026-11-12-drbd9-spike-results.md`, шаг 8 и
  опыт E2). Исключение — `protocol: A`, см. «Принятые решения».
- В каждый момент том монтирует один узел. Тома с одновременной записью с
  нескольких узлов не нужны.
- Под с томом может запуститься на любом узле кластера: узлы без копии
  подключаются к ресурсу без диска.
- Потребление памяти и CPU ниже, чем у Longhorn 1.12.2 на этих же узлах
  (замер 2026-11-09: поды 145–348 МиБ на узел, `fsync` 4 КиБ 13.6 мс).

## Принятые решения

| Решение | Причина |
|---|---|
| Репликацию выполняет модуль ядра DRBD 9 | Запись не проходит через userspace; у ресурса до трёх и более сторон и встроенный кворум |
| Данные тома — разреженный файл на NVMe, подключённый как loop-устройство | NVMe занят одним ext4; переразметка требует остановки k3s на каждом узле |
| Модуль DRBD 9 собирается заранее и поставляется в образе агента | На узлах нет компилятора; `boot.scr` переписывается на последнее ядро без фолбэка, сборка на узле в момент обновления недопустима |
| Состояние томов хранится в CRD | Своей базы нет; etcd уже есть |
| Отдельный репозиторий | Драйвер не связан с wire-протоколом `outline-proxy` и его vendored-крейтами |
| `replicas: N` — произвольное целое число: N копий лежат на N узлах, все остальные узлы кластера подключены к ресурсу без диска | Решение владельца 2026-11-12: под запускается на любом узле. Сторона без диска в роли `Primary` писала и участвовала в кворуме при `replicas: 2` на трёх узлах (шаг 8, опыт E2); `replicas: 3` без стороны без диска — шаг 4. Другие сочетания на стенде не запускались |
| `protocol: A` остаётся параметром StorageClass как исключение из требования о записи на диски узлов с копией | Решение владельца 2026-11-12. При `protocol: A` запись, подтверждённая приложению, но не покинувшая сетевой буфер, теряется при отказе узла. [проверить: `protocol: A` на стенде не запускался] |
| Том при потере кворума освобождает агент `duovol`: по истечении grace period он удаляет поды с этим томом на своём узле и помечает узел, чтобы под не вернулся | Решение владельца 2026-11-12. На стенде изоляция закрывала только TCP 7000, kubelet и API оставались доступны; после `EIO` точка монтирования остаётся, узел остаётся `Primary`, `umount` вручную проходит и узел уходит в `Secondary` (шаг 6, опыт E1). Узел, оставшийся `Primary` к возврату сети, переходит в `StandAlone` (шаг 7, опыт E1) |
| Агент каждого узла выполняет `drbdadm adjust` для ресурса с соединением в `StandAlone`, пока локальная роль — `Secondary` | Решение владельца 2026-11-12. `adjust` снимал `StandAlone` без отбрасывания данных, `Split-Brain detected` в `dmesg` не было (шаг 7, опыт E1); понадобился на обеих сторонах связи, `adjust` только на вернувшемся узле не хватило |

Отвергнутые варианты:

- Longhorn: потребление по замеру выше допустимого.
- Свой движок репликации в userspace (ublk, NBD): повторяет Longhorn, путь
  записи идёт через процесс.
- DRBD 8.4 из штатного ядра с арбитром через Lease: у ресурса две стороны, под
  работает только на двух узлах из трёх.
- Асинхронная репликация снапшотами: изолированный узел продолжает подтверждать
  записи, которые после его возврата выбрасываются.

## Проверенные факты

- Конфиг штатного ядра Debian (`config-6.12.85+deb13-arm64` из образа
  `rk3568-nanopi-r5c_trixie-13.4.img.xz`): `CONFIG_BLK_DEV_DRBD=m` (версия 8.4),
  `CONFIG_MODULE_SIG=y`, `CONFIG_MODULE_SIG_FORCE` не задан (неподписанный
  модуль загружается).
- DRBD 9.3.4 (тег `drbd-9.3.4`, `github.com/LINBIT/drbd`) собирается под
  `linux-headers-6.12.116+deb13-arm64` в контейнере `debian:trixie` arm64 за
  30 с без предупреждений. Результат: `drbd.ko`, `drbd_transport_tcp.ko`;
  `vermagic: 6.12.116+deb13-arm64 SMP mod_unload modversions aarch64`;
  `depends: lru_cache,libcrc32c`.

Команда сборки:

```bash
apt-get install -y --no-install-recommends git ca-certificates build-essential \
  kmod coccinelle python3 linux-headers-6.12.116+deb13-arm64
git clone --depth 1 --branch drbd-9.3.4 --recursive --shallow-submodules \
  https://github.com/LINBIT/drbd /src
make -j4 -C /src/drbd KDIR=/lib/modules/6.12.116+deb13-arm64/build SPAAS=false
```

`SPAAS=false` запрещает сборке обращаться к сервису LINBIT за патчем
совместимости; патч генерирует локальный `coccinelle`.

На стенде с ядром `6.12.116+deb13-arm64` модуль загружается
(`2026-11-12-drbd9-spike-results.md`, допущение 1); на R5C загрузка не проверена.

## Компоненты

### Агент `duovol`

Один бинарь на Rust. Работает как DaemonSet на каждом узле кластера (сейчас три): привилегированный
контейнер, `hostNetwork: true`, `hostPID` не нужен. В одном процессе:

| Часть | Что делает |
|---|---|
| Загрузчик модуля | При старте загружает DRBD 9 из образа, см. «Загрузка модуля» |
| CSI Identity, Controller, Node | gRPC на unix-сокете `/var/lib/kubelet/plugins/duovol/csi.sock` |
| Согласование | Следит за объектами `ReplicatedVolume` и приводит файл, loop-устройство и ресурс DRBD на своём узле к описанному состоянию |
| Статус и метрики | Читает `drbdsetup status --json`, пишет статус в CR, отдаёт метрики Prometheus |
| Освобождение тома | Если у смонтированного тома нет кворума дольше grace period, удаляет поды с этим томом на своём узле и помечает узел, см. «Освобождение тома при потере кворума» |
| Переподключение | Выполняет `drbdadm adjust` для ресурса с соединением в `StandAlone`, пока локальная роль — `Secondary`, см. «StandAlone и split-brain» |

### Права агента (RBAC)

Манифесты RBAC лежат в `deploy/`. Для освобождения тома сервисному аккаунту
агента нужны права:

| Ресурс | Права | Зачем |
|---|---|---|
| `pods` | `delete`; чтение, чтобы найти поды, которые используют том на узле | Удалить поды при потере кворума |
| `nodes` | Изменение объекта `Node`; набор глаголов зависит от механизма пометки, см. «Открытые вопросы» | Пометить узел, чтобы под не вернулся |

CSI Controller отвечает на каждом узле, но запросы получает только от
`external-provisioner`, у которого включён выбор лидера.

### Сайдкары

Штатные образы Kubernetes CSI:

- `node-driver-registrar` — в каждом поде DaemonSet, регистрирует драйвер в kubelet;
- `external-provisioner` — в каждом поде DaemonSet с `--leader-election`,
  активен один.

`external-attacher` не используется: объект `CSIDriver` объявляет
`attachRequired: false`. Без `VolumeAttachment` Kubernetes не ждёт 6 минут
перед принудительным отсоединением тома от недоступного узла.

### Утилиты DRBD

`drbdadm`, `drbdsetup`, `drbdmeta` собираются из исходников `drbd-utils` и
кладутся в образ агента. На хост утилиты не ставятся. Версия `drbd-utils`
выбирается совместимой с модулем 9.3.4; проверено с 9.35.0 (в Debian trixie
пакет 9.22.0).

## Объекты Kubernetes

### `CSIDriver`

| Поле | Значение |
|---|---|
| `metadata.name` | `duovol.balookrd.github.io` |
| `attachRequired` | `false` |
| `podInfoOnMount` | `false` |
| `volumeLifecycleModes` | `Persistent` |
| `fsGroupPolicy` | `File` |

### `StorageClass`

| Параметр | Значения | По умолчанию | Что делает |
|---|---|---|---|
| `replicas` | целое число N | `3` | Число узлов с копией данных. Остальные узлы кластера подключаются к ресурсу без диска. Значение по умолчанию совпадает с числом узлов текущего кластера. Нижняя граница N и кворум при N, отличных от 2 и 3, см. «Открытые вопросы» |
| `protocol` | `C`, `A` | `C` | `C`: запись подтверждается после записи на диски сторон с копией. `A`: после локального диска и отправки в сокет; при падении узла теряется содержимое сетевого буфера, то есть записи, подтверждённые приложению, но не покинувшие узел. `A` — исключение из требования о записи на диски узлов с копией |
| `csi.storage.k8s.io/fstype` | `ext4` | `ext4` | Файловая система тома |

`volumeBindingMode: WaitForFirstConsumer`, чтобы одна из копий оказалась на
узле, куда назначен под. `allowVolumeExpansion: false`.

Поддерживаемые режимы доступа: `ReadWriteOnce`, `ReadWriteOncePod`.

### `ReplicatedVolume` (CRD, cluster-scoped, группа `duovol.balookrd.github.io/v1alpha1`)

```yaml
spec:
  sizeBytes: 2147483648
  protocol: C
  minor: 1000          # номер устройства: /dev/drbd1000
  port: 7000           # TCP-порт ресурса на lan0
  nodes:             # пример: replicas: 2 в кластере из трёх узлов
    - name: k3s-1
      nodeId: 0
      diskful: true
    - name: k3s-2
      nodeId: 1
      diskful: true
    - name: k3s-3
      nodeId: 2
      diskful: false
status:
  nodes:
    - name: k3s-1
      disk: UpToDate
      role: Primary
      connections: {k3s-2: Connected, k3s-3: Connected}
```

В `spec.nodes` перечислены все узлы кластера: N узлов с `diskful: true`,
остальные с `diskful: false`.

`minor` и `port` выделяет CSI Controller при создании: наименьшее свободное
значение среди существующих объектов, начиная с 1000 и 7000. Имя объекта
совпадает с идентификатором тома CSI. На объекте стоит финализатор
`duovol.balookrd.github.io/cleanup`.

### `ConfigMap duovol-nodes`

Карта узлов: имя узла Kubernetes, адрес на `lan0`, постоянный `nodeId` и бюджет
места под тома. Запись есть на каждый узел кластера; в примере кластер из трёх
узлов.

```yaml
nodes:
  - {name: k3s-1, address: 192.0.2.51, nodeId: 0, capacityBytes: 42949672960}
  - {name: k3s-2, address: 192.0.2.52, nodeId: 1, capacityBytes: 42949672960}
  - {name: k3s-3, address: 192.0.2.53, nodeId: 2, capacityBytes: 42949672960}
```

`capacityBytes` — предел суммы объявленных размеров томов с копией на узле.
Файлы томов разреженные, поэтому без предела сумма размеров может превысить
свободное место на NVMe, и тогда запись в том получит ошибку ввода-вывода
вместе с etcd и containerd на том же разделе.

## Загрузка модуля

Образ агента содержит модули по пути `/opt/duovol/modules/<версия ядра>/`:
`drbd.ko`, `drbd_transport_tcp.ko`. Под каждую версию ядра Debian, которая
стоит или будет стоять на узлах, в образе лежит свой каталог.

Порядок при старте агента:

1. Если существует `/sys/module/drbd`, прочитать `/sys/module/drbd/version`.
   Версия `9.*` — модуль drbd уже загружен: если нет
   `/sys/module/drbd_transport_tcp`, загрузить `drbd_transport_tcp.ko` из
   каталога под версию ядра (`insmod`; без файла — ошибка
   `no drbd_transport_tcp module for kernel <версия>`), затем перейти к шагу 5.
   Версия `8.*` —
   завершиться с ошибкой `in-tree drbd 8.4 is loaded`; тома на узле не
   обслуживаются.
2. Определить версию ядра (`uname -r`). Если каталога с модулем под неё нет,
   завершиться с ошибкой `no drbd module for kernel <версия>`.
3. Загрузить зависимости из дерева модулей хоста: `modprobe lru_cache`,
   `modprobe libcrc32c` (`/lib/modules` хоста смонтирован в контейнер только
   на чтение).
4. `insmod drbd.ko usermode_helper=disabled`, затем
   `insmod drbd_transport_tcp.ko`. `usermode_helper=disabled` отключает запуск
   `/sbin/drbdadm` ядром на хосте: обработчики событий драйвер не использует.
5. Продолжить запуск.

На каждом узле при установке создаётся файл
`/etc/modprobe.d/duovol-blacklist-drbd.conf`:

```text
blacklist drbd
install drbd /bin/false
```

Без него любой вызов `modprobe drbd` на узле загрузит штатный модуль версии
8.4. Метаданные томов версии 9 он не читает, а имя модуля то же, поэтому
модуль версии 9 после этого не загрузится до перезагрузки узла. [проверить:
не проверялось на стенде; файл на стенде создаёт `stand/k3s.sh`, `modprobe drbd`
не вызывался] Чёрный список хоста не действует на `modprobe` внутри
контейнера (`/etc/modprobe.d` в поде `toolbox` пуст), поэтому тот же файл
нужен в образе агента.

## Жизненный цикл тома

### Создание (`CreateVolume`)

1. Выбрать N узлов с копией данных: узел из `selected-node` (его передаёт
   планировщик) и N−1 узлов с наибольшим свободным бюджетом `capacityBytes`
   среди остальных. Все прочие узлы кластера становятся сторонами без диска.
   Если узлов в кластере меньше N, вернуть ошибку [проверить: код ошибки].
2. Проверить бюджет на выбранных узлах. При нехватке вернуть
   `RESOURCE_EXHAUSTED`.
3. Создать объект `ReplicatedVolume` с выделенными `minor` и `port`.
4. Дождаться, пока агенты всех узлов поднимут ресурс и диски копий перейдут в
   `UpToDate`. Срок ожидания — 60 с, затем `DEADLINE_EXCEEDED`; provisioner
   повторит вызов, операция идемпотентна по имени тома.

Что делает агент узла с копией данных, увидев новый объект:

1. Создать разреженный файл `/var/lib/rancher/duovol/volumes/<имя>.img`
   размером `sizeBytes` плюс место под внутренние метаданные DRBD. На стенде
   файл в 1 ГиБ при двух остальных сторонах с копией потерял на метаданных
   100 КиБ (`size` устройства 1048476 КиБ), при одной стороне с копией и одной
   без диска — 68 КиБ (1048508 КиБ); см. результаты, шаги 4 и 8. [проверить:
   формула размера внутренних метаданных; `create-md --max-peers` зависит от числа узлов кластера, см. «Открытые вопросы»]
2. Подключить файл как loop-устройство с прямым вводом-выводом
   (`losetup --direct-io=on`).
3. Сгенерировать из объекта файл ресурса `<имя>.res` и выполнить
   `drbdadm create-md`, затем `drbdadm adjust <имя>`. `create-md` выполняется
   только для файла, созданного на шаге 1; для существующего файла тома он не
   вызывается. На стенде ресурс поднимался командой `drbdadm up`
   (`stand/spike/res.sh`); `adjust` на неподнятом ресурсе не проверялся
   [проверить: поведение `drbdadm adjust` на ресурсе, который не поднят].

Агент узла без копии выполняет только `drbdadm adjust` с `disk none` [проверить:
на стенде для стороны без диска использовался `drbdadm up`].

Начальная полная синхронизация пустых копий пропускается: агент узла с
наименьшим `nodeId` среди узлов с копией выполняет
`drbdadm new-current-uuid --clear-bitmap <имя>/0` только если все стороны
`Connected` и диски всех копий `Inconsistent`. Проверено на стенде с DRBD 9.3.4
для трёх копий и для двух копий со стороной без диска: одна команда на одном
узле переводит все копии из `Inconsistent` в `UpToDate`, остальные стороны
пишут в `dmesg` `disk( Inconsistent -> UpToDate ) [skip-initial-sync]`, досылки
нет.

### Монтирование (`NodeStageVolume`, `NodePublishVolume`)

1. `NodeStageVolume`: если на `/dev/drbd<minor>` нет файловой системы, создать
   ext4. Признак «нет файловой системы»: устройство открылось без ошибки, и
   сигнатуры файловой системы на нём нет [проверить: способ чтения сигнатуры].
   При любой ошибке открытия, включая `EMEDIUMTYPE`, `mkfs` не выполняется.
   Смонтировать устройство в каталог staging. Перевод узла в `Primary`
   выполняет DRBD при открытии устройства (`auto-promote yes`). Если том
   открыт на другом узле, открытие завершается ошибкой, и агент возвращает
   `FAILED_PRECONDITION`; kubelet повторяет вызов. Признак: `open(2)` на
   `/dev/drbd<minor>` возвращает `EMEDIUMTYPE` (в том числе только на чтение),
   `mount` завершается с кодом 32 и текстом `Can't open blockdev`, в `dmesg`
   `Auto-promote failed: Multiple primaries not allowed by config`.
2. `NodePublishVolume`: bind-монтирование каталога staging в каталог пода.

### Размонтирование

`NodeUnpublishVolume` снимает bind-монтирование, `NodeUnstageVolume`
размонтирует устройство. DRBD возвращает узел в `Secondary` при закрытии
устройства.

### Удаление (`DeleteVolume`)

Controller удаляет объект `ReplicatedVolume`. Агент каждого узла по
финализатору выполняет `drbdadm down`, отключает loop-устройство, удаляет файл
и убирает запись своего узла из `status.nodes`. Controller снимает финализатор,
когда `status.nodes` пуст. Если узел недоступен, удаление ждёт его возврата.

### Старт агента после перезагрузки узла

Агент проходит по всем объектам `ReplicatedVolume`, где есть его узел,
подключает loop-устройства и выполняет `drbdadm adjust` [проверить: на стенде
после перезапуска узла ресурсы поднимались `drbdadm up`, `adjust` на неподнятом
ресурсе не проверялся]. DRBD досылает блоки,
изменённые за время отсутствия узла, по битовой карте. До завершения этого
прохода CSI Node отвечает на `NodeStageVolume` кодом `UNAVAILABLE`.

## Параметры ресурса DRBD

| Параметр | Значение | Что делает | Когда менять |
|---|---|---|---|
| `protocol` | из StorageClass | Момент подтверждения записи | Задаётся при создании тома |
| `quorum` | `majority` | Узел принимает запись, только пока видит большинство сторон ресурса | Не менять |
| `on-no-quorum` | `io-error` | Без кворума `fsync` возвращает `EIO` (буферизованная запись без `fsync` при этом проходила); журнал ext4 прерывается (`Aborting journal`). При `Errors behavior: Continue` точка монтирования остаётся `rw` (`findmnt`), новые записи получают `Read-only file system` или `Input/output error` | Не менять. Строка обязательна в `.res`: значение по умолчанию в 9.3.4 — `suspend-io` |
| `auto-promote` | `yes` | Роль `Primary` берётся при открытии устройства | Не менять |
| `allow-two-primaries` | `no` | При соединённых сторонах второй узел не может открыть устройство. При разрыве связи `Primary` могут оказаться два узла одновременно (опыт E1: `dv-1` с `quorum:no` и `dv-2` с `quorum:yes`, оба `open:yes`); запись на изолированном узле останавливают только `quorum majority` и `on-no-quorum io-error` | Не менять |
| метаданные | `internal` | Метаданные DRBD лежат в конце файла тома | Не менять |

Выбор `io-error` против `suspend-io` проверен на стенде (DRBD 9.3.4, по одному
прогону). С `suspend-io` процесс на изолированном узле висит в `fsync` в
состоянии `D` до возврата сети, `SIGKILL` его не снимает, `umount` возвращает
`target is busy`, устройство остаётся открытым и узел остаётся `Primary` до
возврата сети. С `io-error` писатель получает `EIO` через 10–11 с после
изоляции, после чего `umount` проходит и узел уходит в `Secondary`.

Состояние соединений после возврата сети зависит не от политики, а от роли
изолированного узла в этот момент. Узел в `Secondary` соединился сам. Узел,
оставшийся `Primary` (при `suspend-io` всегда, при `io-error` — если том ещё
смонтирован), пишет в `dmesg` сам `I shall become SyncTarget, but I am primary!`,
и его соединения переходят в `StandAlone`; после размонтирования они сами не
восстанавливаются. Условие: к моменту возврата сети другой узел стал `Primary`
и писал на том (на стенде `dv-2`, опыт E1 и шаг 7). В шаге 7 в `StandAlone`
перешла одна связь из двух (`dv-1`↔`dv-3`), в опыте E1 обе. Их восстановил
`drbdadm adjust <имя>`: в E1 на `dv-1`, `dv-2`, `dv-3` после размонтирования
на `dv-1`, в шаге 7 на `dv-1` и `dv-3` — на обеих сторонах связи; `adjust`
только на вернувшемся узле оставил соединения в `StandAlone`. Проверен один
порядок: размонтирование, затем `adjust`; `adjust` без размонтирования не
пробовали.

## Поведение при отказах

| Событие | Что происходит | Как увидеть |
|---|---|---|
| Упал узел, на котором под | В кластере из трёх узлов оставшиеся два сохраняют кворум; кворум при других N см. «Открытые вопросы». Под пересоздаётся на другом узле, открытие устройства переводит его в `Primary`. [проверить: не проверялось на стенде; потеря диска `Primary` при `replicas: 2` не проверялась] | `status.nodes[].connections` показывает разрыв |
| Упал узел без пода | Запись продолжается на оставшихся сторонах после паузы, которая кончается сообщением `PingAck did not arrive in time` об упавшем узле: на стенде 4.6–5.6 с и при штатной остановке узла (`limactl stop`), и при принудительной (`limactl stop --force`) [проверить: какой из параметров `ping-int 10` с, `ping-timeout 0.5` с, `timeout 6` с задаёт длину паузы]. Пауза измерена только при `replicas: 2` (сторона без диска и две стороны с копией); на простаивающем ресурсе с тремя копиями `PingAck did not arrive in time` пришёл через 0.7–2.9 с после остановки (`dmesg -T` с точностью до секунды) (опыт E2, ресурс `spike`) [проверить: зависимость паузы от записи]. После отказа k узлов с копией остаётся N−k копий, запись идёт на их диски. При `replicas: 2` после отказа узла с копией остаётся одна копия: узел с копией и сторона без диска сохраняют кворум (`Would lose quorum, but using tiebreaker logic to keep`), запись продолжается на один диск (шаг 8, опыт E2). Кворум при других N и числе сторон без диска см. «Открытые вопросы». | Метрика `duovol_volume_uptodate_replicas` |
| Узел с подом изолирован по `lan0` | Через ~10 с узел теряет кворум [проверить: механизм ~10 с], `fsync` возвращает `EIO` через 10–11 с после изоляции. Изоляция на стенде закрывала только TCP 7000; kubelet и API оставались доступны, поэтому под Kubernetes kubelet перезапустил бы под на том же узле [проверить: не проверялось под Kubernetes]: точка монтирования остаётся, узел остаётся `Primary` (опыт E1). Том освобождает агент, см. «Освобождение тома при потере кворума». В кластере из трёх узлов (стенд, `replicas: 3`) остальные два узла держат кворум. Если сеть вернулась, пока том на изолированном узле ещё смонтирован, его соединения переходят в `StandAlone` (см. «Параметры ресурса DRBD»); агент снимает `StandAlone` после размонтирования, см. «StandAlone и split-brain» | В `dmesg` изолированного узла: `drbd <имя>/0 drbd<minor>: quorum( yes -> no )` |
| Убит агент, узел жив | Репликация идёт в ядре и не прерывается. Новые тома на узле не монтируются до рестарта агента; освобождение тома при потере кворума и `adjust` при `StandAlone` на этом узле тоже не выполняются | Под агента не `Ready` |
| Узел вернулся | DRBD досылает изменённые блоки по битовой карте. Наблюдалось: изолированный узел после возврата сети — `UpToDate` → `Outdated` → `Inconsistent` → `UpToDate`; узел после перезапуска, если за время отсутствия на томе была запись, — `Diskless` → `Attaching` → `UpToDate` при `drbdadm up`, затем при соединении `UpToDate` → `Outdated` → `Inconsistent` → `UpToDate`; без записи — `Attaching` → `UpToDate`, досылки нет | `status.nodes[].disk` |
| Упали два узла | В кластере из трёх узлов оставшийся узел без кворума, запись возвращает ошибку. etcd тоже без кворума, k3s не работает [проверить: не проверялось на стенде] | — |
| Отключение питания всех узлов | После старта стороны соединяются, кворум восстанавливается, тома монтируются. Узел, поднявшийся один, ждёт второго [проверить: не проверялось на стенде] | — |
| NVMe переполнен | Запись в файл тома возвращает ошибку, DRBD отключает локальный диск и работает через остальные копии [проверить: не проверялось на стенде; `on-io-error` по умолчанию в 9.3.4] | `disk: Diskless` на узле с копией |

### Освобождение тома при потере кворума

Без кворума `on-no-quorum io-error` возвращает `EIO` на `fsync` через 10–11 с
после изоляции, но точка монтирования остаётся, устройство открыто, узел
остаётся `Primary` (шаг 6, опыт E1). Изоляция на стенде закрывала только
TCP 7000: kubelet и API оставались доступны, и под никто не трогал. Узел,
оставшийся `Primary` к возврату сети, переходит в `StandAlone`, если другой
узел за это время писал на том.

Порядок, который выполняет агент узла:

1. Агент читает `devices[].quorum` из `drbdsetup status --json` для томов,
   смонтированных на узле.
2. Если кворума нет дольше grace period, агент удаляет через API поды на своём
   узле, которые используют этот том.
3. Агент помечает узел, чтобы под не вернулся на него.
4. kubelet размонтирует том, DRBD переводит узел в `Secondary`. [проверить:
   размонтирование kubelet после удаления пода не проверялось, на стенде
   `umount` выполнялся вручную]
5. Контроллер пода (Deployment, StatefulSet) создаёт под на узле, где есть
   кворум.

Длина grace period, механизм пометки узла и поведение агента при недоступном
API server см. «Открытые вопросы». Права агента на удаление подов и изменение
узлов описаны в «Права агента (RBAC)».

### StandAlone и split-brain

Split-brain при работающем кворуме возникать не должен. `StandAlone` на стенде
наблюдался в двух ситуациях, ни в одной нет `Split-Brain detected` в `dmesg`
(`2026-11-12-drbd9-spike-results.md`):

| Ситуация | Что в `StandAlone` | Что сняло |
|---|---|---|
| Шаг 7: `suspend-io`, узел `Primary` при возврате сети, другой узел писал | одна связь из двух (`dv-1`↔`dv-3`) | `drbdadm adjust` на обеих сторонах связи, данные не отбрасывались |
| Опыт E1: `io-error`, том не размонтирован до возврата сети, другой узел писал | обе связи `dv-1` | размонтирование и `drbdadm adjust` на трёх узлах, данные не отбрасывались |

Агент каждого узла выполняет `drbdadm adjust <имя>` для ресурса, у которого
есть соединение в `StandAlone`, пока локальная роль узла — `Secondary`. На узле
в роли `Primary` (том смонтирован) агент `adjust` не вызывает: он выполняется
после освобождения тома. На стенде `adjust` потребовался на обеих сторонах
связи: в опыте E1 на трёх узлах, в шаге 7 на `dv-1` и `dv-3`; `adjust` только
на вернувшемся узле оставил соединения в `StandAlone`. Проверен один порядок:
размонтирование, затем `adjust`.

Признак `StandAlone` сам по себе не отличает эти случаи от split-brain. При
настоящем split-brain DRBD, по ожиданию владельца, снова разрывает соединение
после `adjust`; только тогда агент выставляет метрику
`duovol_volume_split_brain` в `1` и применяется процедура ниже. Настоящий
split-brain на стенде не воспроизводился [проверить: как DRBD 9.3.4 сообщает
split-brain (`events2`, сообщение ядра); как часто агент повторяет `adjust` при
повторном разрыве]. Копию, которую нужно отбросить, оператор выбирает вручную:

```bash
# on the node whose data is discarded, inside the agent container
drbdadm disconnect <имя>
drbdadm connect --discard-my-data <имя>
```

## Ограничения

- Время переезда пода с упавшего узла определяет Kubernetes: под выселяется
  через `tolerationSeconds` (по умолчанию 300 с). Поды с томами `duovol`
  задают меньшее значение для `node.kubernetes.io/unreachable` и
  `node.kubernetes.io/not-ready`.
- Deployment с томом `duovol` использует стратегию `Recreate`. При
  `RollingUpdate` с `maxSurge` новый под на другом узле не откроет том, пока
  жив старый.
- Под StatefulSet на недоступном узле Kubernetes не пересоздаёт без
  принудительного удаления. Автоматическое принудительное удаление драйвер не
  выполняет; агент удаляет поды только на своём узле при потере кворума.
- Под без контроллера (Deployment, StatefulSet), удалённый агентом при потере
  кворума, не пересоздаётся.
- Если с изолированного узла недоступен API server, агент не может удалить под;
  поведение в этом случае см. «Открытые вопросы».
- Под каждую новую версию ядра нужен образ агента с модулем под неё. Порядок
  обновления узла: выкатить образ с новым модулем, затем `apt full-upgrade` и
  перезагрузка. При обратном порядке агент на узле завершится с ошибкой
  `no drbd module for kernel`, тома на узле не поднимутся, два других узла
  продолжат работу.
- В первую версию не входят: снапшоты, расширение тома, бэкап на NAS, тома
  `ReadWriteMany`, шифрование.

## Проверка

### Модульные тесты

- Генерация файла ресурса из `ReplicatedVolume`: N копий и M сторон без диска
  (три копии; две копии и сторона без диска), протоколы `C` и `A`.
- Разбор `drbdsetup status --json` на записанных образцах вывода.
- Выбор узлов и проверка бюджета в `CreateVolume`: узел из `selected-node`
  плюс N−1 узлов с наибольшим свободным бюджетом, остальные без диска.
- Условие запуска `drbdadm adjust` агентом: `StandAlone` и роль `Secondary`.
- Выделение `minor` и `port`.
- Выбор каталога модуля по версии ядра и отказ при загруженном модуле 8.4.

### Стенд

Три ВМ Debian trixie arm64 на маке с k3s. ВМ ставят тот же пакет ядра
`linux-image-6.12.116+deb13-arm64`, что и узлы, поэтому на стенде загружается
тот же `drbd.ko`.

Писатель-проба: под, который в цикле дописывает запись в файл, вызывает
`fsync` и после успешного `fsync` отправляет номер записи наружу (в журнал
вне тома). После каждого сценария все номера из журнала должны быть в файле.

Сценарии:

1. Создание, монтирование, запись, удаление тома при `replicas: 3` и `2`.
2. Выключение ВМ с подом: под поднимается на другом узле, подтверждённые
   записи на месте.
3. Блокировка `lan0` на узле с подом: запись получает ошибку, под поднимается
   на другом узле, после снятия блокировки узел досинхронизируется.
4. Убийство агента на узле с подом: запись не прерывается.
5. Перезагрузка узла без пода: досылка по битовой карте, без полной
   синхронизации.
6. Одновременное выключение всех ВМ и старт: тома монтируются.
7. Загрузка узла с заранее загруженным штатным `drbd` 8.4: агент завершается
   с ошибкой, остальные узлы работают.
8. N копий и стороны без диска: при `replicas: 2` под запускается на узле без
   копии, открывает устройство и пишет. Стенд состоит из трёх ВМ, поэтому
   другие сочетания N и числа сторон без диска, кроме 3 копий без стороны без
   диска и 2 копий с одной, на нём не воспроизвести.
9. Освобождение тома агентом: блокировка TCP 7000 на узле с подом; после grace
   period агент удаляет под и помечает узел, kubelet размонтирует том, узел
   уходит в `Secondary`, под поднимается на узле с кворумом, подтверждённые
   записи на месте.
10. Автоматический `adjust` после `StandAlone`: после сценария 9 снять
    блокировку; агенты выполняют `adjust`, все соединения `Connected` без
    команд оператора.

### Замер на R5C перед вводом

Методика та же, что в замере Longhorn 2026-11-09: пять томов по 1 ГиБ с
писателем раз в 10 с.

| Показатель | Цель | Для сравнения |
|---|---|---|
| RSS подов `duovol` на узел | не больше 64 МиБ | Longhorn 145–348 МиБ |
| Прирост памяти `k3s server` | не больше 50 МиБ | Longhorn 180–450 МиБ |
| `fsync` 4 КиБ, `protocol: C` | не больше 5 мс | `local-path` 1.8 мс, Longhorn 13.6 мс |

Если цель по `fsync` не достигнута, отдельно замеряется вклад loop-устройства
(том без остальных копий) и вклад сети.

## Что проверяется первым

Пункты, от которых зависит остальная реализация; каждый закрывается на стенде
до написания CSI-части:

1. Модуль 9.3.4 загружается на ядре `6.12.116+deb13-arm64` с
   `usermode_helper=disabled`.
2. Ресурс из трёх сторон поверх loop-устройств с `--direct-io=on` поднимается
   и синхронизируется.
3. Пропуск начальной синхронизации через `new-current-uuid --clear-bitmap`.
4. Сторона без диска при `replicas: 2` участвует в кворуме и может открыть
   устройство на запись.
5. Поведение `on-no-quorum io-error` против `suspend-io` для ext4 и kubelet
   (для kubelet не проверено: все проверки использовали `mount` на хосте).
6. `drbdadm` и `drbdsetup` работают из контейнера без установки на хост.

Результаты проверки на стенде: `2026-11-12-drbd9-spike-results.md`.

## Открытые вопросы

Решения владельца от 2026-11-12 перенесены в «Принятые решения»; в таблице
остались вопросы, которые они не закрывают.

| Вопрос | Что наблюдалось | Варианты |
|---|---|---|
| Нижняя граница `replicas` | При N = 1 у ресурса одна сторона с копией, репликации нет. На стенде не запускалось | Минимум 2; допустить 1 как том без репликации |
| Кворум DRBD при N копиях и M узлах без диска, N не равно 2 и 3 | Запускались только N = 3 без стороны без диска (шаги 4–7: изолированный узел теряет кворум, остальные два сохраняют) и N = 2 с одной стороной без диска (шаг 8, опыт E2: при отказе узла с копией кворум сохраняется по tiebreaker). `quorum-minimum-redundancy` в 9.3.4 по умолчанию `off` (шаг 7). Остальные сочетания не запускались | Проверить сочетания на стенде с числом ВМ больше трёх; ограничить допустимые N проверенными значениями |
| `create-md --max-peers` | Шаг 8: `create-md` без `--max-peers` отвёл битовую карту 32 КиБ для ресурса с одной стороной с копией и одной без диска против 64 КиБ для ресурса из трёх копий; перевод стороны без диска в сторону с копией на таких метаданных не проверялся. Число сторон ресурса теперь равно числу узлов кластера, а не N | `--max-peers` по числу узлов кластера на момент создания тома; `--max-peers` с запасом сверх числа узлов; значение `create-md` по умолчанию |
| Узел добавлен в кластер после создания тома | Не проверялось. `spec.nodes` существующих объектов `ReplicatedVolume` перечисляет узлы, бывшие в кластере при создании тома | Агент добавляет сторону без диска во все существующие ресурсы; добавление по команде оператора; тома, созданные до появления узла, на нём не запускаются |
| Длина grace period перед освобождением тома | После изоляции `fsync` получает `EIO` через 10–11 с (шаг 6, опыт E1); длина grace period не определена | Значение в конфигурации агента; параметр StorageClass |
| Механизм пометки узла и её снятие | Taint узла действует и на поды, которые не используют тома `duovol`. На стенде пометка не проверялась | Taint узла; метка или аннотация узла, которую учитывают только поды с томами `duovol` [проверить: как выразить это правило планировщику]; условие и момент снятия пометки не определены |
| Агент не может обратиться к API server с изолированного узла | На стенде изоляция закрывала только TCP 7000, API оставался доступен (шаг 6, опыт E1); полная изоляция узла не запускалась | Агент ждёт возврата связи с API, том остаётся на узле, запись получает `EIO`; агент освобождает том локально без API [проверить: способ] |
| Разреженный файл или `fallocate`, поведение при `ENOSPC` | На стенде файлы создавались как разреженные (`truncate -s` в `stand/spike/res.sh`); заполнение NVMe не проверялось | Разреженный файл с бюджетом `capacityBytes`; `fallocate` при создании тома |
